## 1. 总体结论

**Octopus 的核心架构方向合理，已经具备较扎实的工程基础，但目前还不能评价为“足够精简、接口完全一致、可以无成本扩展新运行时”。我的建议是保留现有主体，先修复已经证实的契约缺口，再收束少数关键边界。没有证据支持推倒重写。**

最值得保留的是：`SessionOwner` 对会话执行状态的单写者约束、持久化输入与原始完成收据、业务结果和通知交付的区分、明确的进程退出责任，以及 Wiki 对正文、身份、历史和派生索引的区分。这些机制对应真实的取消、断线、晚到结果和文件写入失败场景，不能仅因代码多而删除。[会话所有权][src-owner] [收据][src-receipt] [数据库事务][src-dbtx] [Wiki 写入][src-wiki-write]

当前主要问题有三类：

1. **同一个契约在不同入口解释不一致。** 普通 turn 会验证凭据所有权，部分 one-shot 路径不会；列表和详情对同一个能力返回不同值；配置可以保存，但某些后端并不执行它。这里已经有实际 bug。
2. **文件拆分多于边界收束。** `SessionManager` 已拆成多个文件，但仍由九个 Mixin 共享一个对象；调度器和 Wiki 会读取会话私有字段；Wiki 的 App 入口通过 FastAPI 内部解析逻辑调用 HTTP handler。新增后端或客户端时，仍需理解较大的内部状态面。[SessionManager 组合][src-session-mixins] [调度读取内部状态][src-schedule-state] [Wiki worker 边界][src-wiki-session] [App 网关][src-wiki-app]
3. **测试数量可观，跨模块合同仍有漏测。** 本次所选的 216 个后端测试、115 个前端测试及类型检查均通过；另外构造的场景仍复现了凭据边界、热进程配置、连接器并发和 Wiki 事件连续性等问题。它们不是“再多加几个空值判断”能系统解决的。

### 1.1 对用户问题的直接回答

| 关注点 | 判断 | 需要采取的行动 |
|---|---|---|
| 是否符合软件工程原则 | 主要方向符合，尤其是所有权、原子事务、原始结果消费 | 把同一原则落实到 one-shot、配置更新和缓存生命周期等旁路 |
| 是否精简 | 基础设施选择精简，核心业务代码和跨模块状态关系偏复杂 | 以减少状态解释和私有访问为目标，避免继续按行数拆文件 |
| 接口是否有扩展性 | 对相似的 CLI + JSONL 后端较好；对 RPC/SDK 后端不充分 | 拆开真实能力与传输方式，增加最小运行时适配边界 |
| 是否有 bug | 有，本文列出 12 项已通过代码或确定性探针确认的问题 | 先处理 F01/F02，再按用户使用路径处理其余问题 |
| 是否需要全面架构大改 | 当前不需要 | 用几个有验收目标的纵向改动修复薄弱边界 |
| 之后应该加什么 | 优先运行时交互、可恢复任务体验、引用定位和材料导入 | 先稳定事实与权限合同，再增加新后端和新客户端 |

## 6. 设计限制与风险：不要混同于已经证明的 bug

### 6.1 多账户数据归属不等于不可信用户之间的执行隔离

项目的多租户计划明确选择同一个 OS 用户运行所有 agent，用于互相信任的少数人；文档也明确承认这不是租户间安全边界。一般 CLI 任务会跳过原生权限确认/沙箱。因此，HTTP 的 user_id、路径检查和每账户 DEK 不能阻止拥有主机 shell 能力的 agent 读取同一 OS 用户可读的文件。[明确的部署边界][src-tenancy] [CLI 启动][src-codex-argv]

这不是本次新发现的“忘记开启容器”bug，而是当前产品范围。应把 README 中容易被理解为完全隔离的表述与该限制对齐。F01 仍应修复：即使用户彼此信任，产品 API 也应遵守它明确表达的账户归属。

### 6.2 named delegation 当前已经不因完成回复而自动归档

实际 lifecycle 明确区分“完成已接受的一轮工作”和“用户结束/归档会话”。本次不把旧的自动归档描述当成当前运行 bug。`docs/architecture.md` 中仍能找到旧描述，说明文档内容更新未完全同步；索引检查通过不会发现这类漂移。[当前 lifecycle][src-delegation-lifecycle] [旧架构说明][src-architecture-delegation]

### 6.3 Codex 业务对话仍使用 exec，app-server 是局部使用

当前普通 turn 由 `codex exec --json` 执行。恢复前已有一个短时 app-server 控制步骤，用来恢复 thread、核对 controller checkpoint、必要时注入指令，然后关闭该进程再启动 exec。[业务运行][src-codex-argv] [恢复控制步骤][src-codex-control]

因此两个极端说法都不准确：不能说“完全没有用 app-server”，也不能说“已经完成 app-server 对话迁移”。额外启动和握手会带来成本，但本次没有测量，不承诺迁移能提升多少速度。

### 6.4 原生子任务的可见性不等于完整尾部交付

已有原生 subagent 的观察和卡片，也有 Octopus 自己的 named delegation 收据。这与“父 turn 结束后继续接收所有原生后代结果，再唤醒父代理汇总直到整项任务闭合”是不同能力。仓库最新可行性文档已经把 app-server 迁移范围 A 与完整尾部交付 B 分开；后者仍需真实运行证据，不能仅从 schema 字段推断保证成立。[迁移范围定义][src-appserver-plan]

### 6.5 Python 依赖与 CLI 版本的可重复性还可加强

前端有锁文件；Python 依赖主要给下限或范围，测试/lint/type 工具也没有统一的完整环境锁定。当前类型配置还全局关闭 `union-attr`、`arg-type`、`misc` 等错误类别。这不是“现在安装必然失败”，但会削弱跨机器复现和新增接口错误的发现能力。[配置][src-deps]

建议记录经过验证的 Python 解析结果与实际 CLI 版本，发布时使用同一套；接口收束过程中逐项缩小全局类型豁免，而不是一次启用 strict 造成海量无关修改。直接使用的依赖也应直接声明，避免长期依赖某个第三方包碰巧间接安装它们。

### 6.6 Wiki 的性能和大文档范围需要测量后再决策

代码中有运行时恢复状态检查，也有一些固定 schema/protocol 检查。前者有必要，后者可能适合由启动/发布统一保证；是否值得优化需要测量。部分文本读取会完整读入并解析，未发现对应单文档大小上限；巨型日志或导出文件是条件性风险，本次没有做 OOM 或大规模压力实验。[Wiki 读取][src-wiki-read]

不要直接把这两点写成性能 bug，也不要在没有漏召回证据时替换为向量数据库。先使用现有评估脚本与实际语料识别问题。[已有检索评估入口][src-wiki-eval]

## 7. 建议的接口边界

本节描述目标合同，不要求按表格新增对应类，更不要求重写所有调用方。

### 7.1 执行授权：所有模型入口共用一次事实解释

| 输入/事实 | 应由谁负责 | 调用方可以做什么 |
|---|---|---|
| 账户当前是否可用 | 现有账户/凭据存储 | 显式传入捕获的 owner |
| credential 属于谁、适配哪个 backend、当前是否有效 | 统一 credential binding/resolution 边界 | 请求解析结果；不能绕过 owner 直接拼 home |
| 本次请求采用哪个配置 | SessionOwner 捕获 | 消费该配置，不在异步途中拼接新旧版本 |
| 实际启动/发送时是否仍被授权 | 统一执行授权检查 | 普通 turn 与 one-shot 都调用 |
| 历史工件定位 | 专门的受限读取语义 | 不把“无需认证文件”扩大为“无需所有权” |

这里要复用已有 `validate_credential_binding`、`require_run_authority` 和执行身份，不再持久化一份“授权通过”布尔值。保存配置时验证与实际启动前验证解决不同的时间问题，都应从同一事实来源读取。[既有绑定验证][src-binding] [运行授权][src-run-authority]

### 7.2 后端能力：根据真实实现公开

最少应能区分下列合同：

| 能力 | 要回答的问题 | 不应采用的替代判断 |
|---|---|---|
| 本轮追加输入 | 运行中的当前 turn 是否可接收输入？ | stdin 是否保持打开 |
| 接受确认 | 可以明确区分 accepted、rejected、unknown 吗？ | `drain()` 成功或暂时没有输出 |
| 原生问题回复 | 能否保留 question ID 并发送结构化答案？ | 把所有答案拼成普通 prompt |
| 跨请求复用 | 哪些配置可以更新，哪些需要重启？ | 所有流式 runtime 都可热复用 |
| 工具策略 | 可强制执行哪些 allow/deny 规则？ | UI 有字段就视为支持 |
| 历史/fork | 能否恢复或复制原生历史，适用什么边界？ | 有一个 history ID 就宣称完整 fork |

`RuntimeProfile` 可以继续保留值对象形式，不必改成继承层次。各后端只提供已经实现的能力。公共业务层消费语义，Claude JSON、Codex RPC 和将来的 SDK/ACP 放在对应 adapter 中。

### 7.3 读取投影与事件

- Session 列表、详情、创建、更新共享一个基础投影，避免 F06。
- WS 建立有限的判别联合类型，覆盖实际使用的事件，和后端字段保持一个定义来源；无需泛化成任意事件系统。
- 首屏与重连共用必要快照读取入口，保留现有 account/service generation 检查。
- UI 只投影已确认的命令结果；没有确认成功的 reset/归档/重试不先清除原始交互。

### 7.4 Wiki 的观察器与缓存

注册是长期身份责任，Store 是可以重建的读写访问对象，两者生命周期不应由同一个 LRU 策略决定。保留现有 durable inbox 和恢复协议，让观察器归注册所有者管理；缓存淘汰只释放查询相关缓存。若确需暂时停止观察，以显式连续性中断进入恢复，而不是重新打开后假定没有变化。

## 8. Future Plan：可以增加什么，是否可行

### 8.1 先校准已有功能，避免重复建设

当前已经有：多账户、长期 Agent、记忆目录、调度、named delegation、原生子代理卡片、后台任务、深度研究、Applications、Connector、Wiki 检索/维护/历史、输入恢复和 Monitor。它们不能再作为“准备从零实现”的路线图条目。[启动与组件][src-main] [架构概览][src-architecture]

真正值得增加的是现有能力的闭环和当前缺少的接口，而不是继续堆更多同级管理器。

### 8.2 功能优先级、可行性与验收

以下工作量是规划区间，假设一名熟悉代码的开发者，包含必要测试和文档，不包含外部平台出现未知协议限制后的研究时间。它不是交付承诺。

| 方向 | 新增用户价值 | 已有基础与主要前置 | 可行性 / 工作量 | 验收标准 |
|---|---|---|---|---|
| **可恢复任务中心** | 直接看清任务在排队、执行、已完成待交付，还是需要人工恢复 | durable input、receipt、recoverable inputs；先统一投影 | 高，约 3–6 人日 | 刷新/断线/服务重启后同一请求可追踪；操作使用原 request ID，不重复执行 |
| **Codex app-server 请求内交互** | 运行中追加输入、原生问题、明确取消及接受事实 | 保留 SessionOwner/输入账本；先完成 F01–F03 和能力拆分 | 中，约 1–3 周 | 当前活动 turn 的输入/取消/问答协议实验通过；历史连续、Claude 不退化 |
| **完整原生子任务尾部交付** | 父回复后继续收齐原生子任务，并完成父级总结 | 依赖上项和真实原生后代生命周期证据 | 条件性中低；先安排 3–5 人日协议实验，再估实施 | 后代发现、结果消费、再次派生、全树停止和最终汇总均有运行证据 |
| **统一耗时与用量归因** | 知道慢在排队、controller 准备、首 token、工具还是退出 | 现有 Monitor、request/attempt/work/provider IDs | 高，约 3–5 人日 | 分段耗时可解释、usage 不重复累加；凭据和内容不进入日志 |
| **第三个后端，例如 DeepSeek harness** | 更多模型/运行时选择，降低单后端绑定 | 能力合同和资源退出接口；先核验其实际官方接口 | 中，约 1–3 周起，取决于接口 | start/events/stop/resume/授权矩阵通过；明确不支持的功能，不静默降级 |
| **Wiki 标签筛选与 facet** | 按研究主题快速查找，普通点击不调用模型 | 已有 tags、FTS metadata、分页 | 高，约 2–4 人日 | 过滤先于分页/排名；cursor 绑定过滤；章节不能重复计算文档数量 |
| **回答引用直达段落** | 从回答回到正确原文位置，适合论文精读 | 已有 doc ID、revision、章节与 raw 定位 | 中高，约 1–2 周 | 文件移动、旧版本、重复句、中文/emoji 坐标均正确；失效时明确提示 |
| **PDF/网页材料导入** | 把论文和网页变成有来源、可定位的知识材料 | content hash、history、sources、任务回执 | 中，约 1–3 周；OCR 另定范围 | 原件保留、页码/文本映射、提取版本、可恢复失败；摘要不能替代原文 |
| **SmartReader 等受限 Wiki 客户端** | 阅读时提问、选中内容提交入库，Sapphire 管理主库 | App bridge/grants；当前单 app 绑定需扩展 principal 与能力 | 中，约 1–2 周，依赖 Wiki 用例接口 | 每个 App 读/提交/发布权限明确，撤权及时，跨 App 不混淆任务归属 |
| **有证据驱动的混合检索** | 改善同义表达、跨语言概念的漏召回 | 现有 FTS/jieba 基线及评估入口 | 条件性中；先约 3–5 人日评估 | 固定查询集上证明收益，同时记录延迟/成本；向量失败时词法检索可用 |
| **来源变化后的定向维护** | 原文更新后列出受影响知识条目，避免过时结论 | 稳定来源、历史与维护授权 | 中，约 1–2 周 | 只更新有明确来源依赖的条目；可看 diff、可回滚、不全库自主重写 |
| **不可信应用/用户的执行隔离** | 若未来服务陌生用户或安装第三方应用，提供真正隔离 | 目前同 OS 用户与同源应用不满足该目标 | 低至中、成本高，通常数周以上 | 文件/网络/进程/凭据/配额均隔离，有明确威胁模型及越界测试 |

其中 Wiki 的引用、标签和导入最接近当前研究使用需求；向量检索只有在词法召回确实不足时才值得增加。单机可信使用场景可以继续维持简洁部署，最后一项不应被强行变成所有其他功能的前置。

### 8.3 app-server 的推荐实施方式

**范围 A：先完成请求内双向协议。** 继续让 `SessionOwner` 拥有输入、授权和最终结算，让现有 `HarnessRun` 拥有 attempt 的进程与退出；Codex 私有 adapter 处理握手、RPC 请求关联、单一读取/写入路径和事件归一。把已有 resume 前 controller 更新并入同一宿主，避免维护两套并行业务流程。[当前控制步骤][src-codex-control] [已有可行性设计][src-appserver-plan]

第一阶段可以保持“请求结束退出宿主，下一请求恢复历史”的明确策略。跨请求进程池应等到配置更新、凭据切换、闲置回收的合同被验证后再决定；不是 RPC 必须附带的复杂度。

必须单独验证以下边界：

1. 接受 ACK 与展示通知乱序；发送后断线时，区分拒绝与执行未知。
2. 慢 UI 的展示队列不能阻塞 RPC reader 接收 ACK、问题或取消结果。
3. 原生问题保留问题身份和结构化答案；过期答案不能写入另一轮。
4. interrupt 发出、模型 turn 终结、子进程实际退出是不同事实。
5. 原有 exec 历史能在目标版本恢复；模型、凭据、工具和知识约束实际生效。
6. Research 依赖的完整 text、前端 delta、Monitor usage 等都由 mapper 正确提供，避免只修聊天主界面。

**范围 B：最后证明完整原生尾部交付。** 根 turn 完成后，能否发现所有活动后代、读取其结果、让父代理消费并再次工作，是协议行为问题。必须针对目标 CLI 版本做真实试验。`turn/completed` 或一张子代理完成卡片都不能单独证明整项请求已经闭合。[仓库 A/B 边界][src-appserver-plan]

这里沿用的是仓库已有方案的范围划分，没有把那份文档里基于某一 CLI schema 的分析升级成“本次已验证最新官方实现支持全部行为”。

### 8.4 第三后端如何扩展而不拖累现有架构

对 DeepSeek 或其他 harness，先确定真正使用的 SDK、ACP 或 headless 接口，核验它是否能交出可取消、可等待退出的资源 handle。不能为了“兼容未来所有 backend”先造一个巨型 Transport 框架。[现有后端选型计划][src-deepseek-plan]

建议共享 `start / events / stop` 的业务语义，按实际实现另外暴露 steer、问题回复、one-shot、fork 等能力。新后端仍使用现有输入账本和 Owner；不维护自己的第二套业务请求表。`BackendKind`、认证、生成契约和 UI 能力都要同步更新，所以新增 backend 并不是仅调用一次 `register()`。

## 9. 可直接排期的实施顺序

### 阶段一：修复当前已证实的问题

| Ticket | 范围 | 依赖 | 完成定义 |
|---|---|---|---|
| CR-01 统一凭据绑定与模型执行授权 | F01；覆盖正常 turn 与 one-shot | 无，优先执行 | 跨 owner、停用账户、撤销凭据都不能通过实际启动边界；合法路径不受损 |
| CR-02 真实后端能力与会话投影 | F02、F06 | 无，可与 CR-01 并行 | 不支持的策略明确拒绝；所有 session 表达的能力一致 |
| CR-03 完整启动配置与输入大小 | F03、F11 | 保持当前后端协议 | 热配置变化能生效；超限系统输入不再运行时才失败 |
| CR-04 Connector 业务原子性 | F04、F05 | 无 | 集合替换全成或全不成；旧刷新不覆盖新授权；无重复状态表 |
| CR-05 Wiki 观察和退役责任 | F09、F10、F12 | F09/F10 联合设计 | 缓存淘汰不破坏事件连续性；已退役对象回收；坏 cursor 明确拒绝 |
| CR-06 前端命令确认和重连补偿 | F07、F08 | 可复用 CR-02 投影 | 失败 reset 不丢交互；重连补回离线期间的 Agent 变化 |

上述是按完整用户行为拆出的六项工作，不应进一步把每个 `await`、flag 或防御分支拆成独立 ticket。每项在同一改动中完成必要的调用方、回归测试和文档修正。

### 阶段二：用两三次纵向重构降低扩展成本

- 建立模型入口共用的执行授权接口，消除凭据旁路。
- 收束真正被其他模块读取的会话事实，减少 Wiki/调度的私有字段访问。
- 统一 session capability 投影和实际使用的 WS 事件合同。
- 只提取 Wiki 已经被 HTTP/MCP/App 多入口使用的服务用例。
- 固定可复现的验证环境，清理已与代码冲突的文档；逐步缩小全局类型豁免。

**重构验收是删掉重复解释和旁路，而不是类/文件数量增加。** 如果只是把旧函数搬到新文件、调用方仍传入整个 SessionManager 并访问私有状态，扩展性没有实质改善。

### 阶段三：选择有实际价值的新功能

建议并行两条可独立交付的线：

- **运行时线：**可观测性 → app-server A → 在协议实验支持后决定 B/第三后端。
- **知识工作线：**标签与稳定引用 → PDF/网页导入 → 受限阅读器接入 → 有证据需要时增加混合检索。

每个阶段交付完整范围，不以“后续再补权限/恢复/文档”为条件上线。协议能力尚未证实的范围可以明确不承诺，不能用代码先假装支持。

## 10. 如何持续审查而不陷入无休止补丁

建议下一轮开发沿用下列简短约束：

1. **先写被破坏的合同。** 例如“替换集合必须原子”“新请求看到新配置”“全部模型入口使用同一账户权限”。不要先列要添加哪些锁和状态。
2. **画清一个事实由谁写、谁读。** 只有确实跨生命周期的事实才持久化；观察/通知失败不能回头改写原业务结果。
3. **在真实交界处复现。** 比起只测试 hash 字段，更重要的是编辑配置后热进程是否替换；比起只测试 resolver 返回值，更重要的是实际子进程收到哪一个 credential 环境。
4. **优先缩小不支持的能力面。** 不能执行的 policy 就拒绝，无法确认接受的输入就保持 unknown；不要用猜测、自动重试和提示词补足不存在的协议保证。
5. **让一次 ticket 完成一个行为闭环。** 入口、owner、持久事实、投影和测试一并完成；不靠下一张票修复当前半成品。
6. **只针对真实风险扩大测试。** 修复时先跑失败场景和相邻边界，提交/发布按仓库既有门禁执行。不要每次文案或简单字段修改都重复一套无关故障演练。

对当前 Octopus，最有价值的下一步不是继续增加 Manager、状态码和恢复分支，而是把已经存在的原则贯彻到所有入口，并使调用方只依赖它真正需要的事实。
