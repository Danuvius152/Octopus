01

整体架构：部署骨架延续，内部责任改变

同样是单机、单 FastAPI 进程的模块化单体；下面的框表示进程内职责，没有新增分布式网络层。

已有 module / 关系新增或显著强化的职责集中复杂规则的 deep module箭头＝调用 / 数据流；双向＝读写或事件返回；虚线框＝进程范围
保留的核心

Agent / Session、Harness + RuntimeProfile、两种 CLI、后台任务、委派、Research、应用、账户隔离都在旧版存在。

执行责任更集中

新版 Manager 负责入口与跨会话资源；原 SessionOwner 串行维护一个会话的活动状态。消息广播不再承担业务终结权威。

新的知识领域

Wiki 引入独立对象准入、身份修订、维护授权、文件效果与结果交付；它有自己的持久边界。

02

请求与完成：从任务和事件，走向原请求的责任链

最实质的变化是：接管、模型收到、业务结论、记录、通知和资源退役各自凭什么成立。

A · ADMISSION请求接管

完整输入事务确认后才承诺接管；不是模型已读取。

B · OUTCOME业务与记录

精确 terminal 关联原请求；缺提交确认时保留 unavailable。

C · NOTIFICATION订阅发布

发布状态不改写业务结论；delivered 不证明浏览器已收到、显示或消费。

D · RETIREMENT执行资源

本轮 I/O 与已发起退休须收束；正常可复用进程可 held。Stop 等要求真实退役。

图示职责依赖，不规定所有路径的提交先后。正常可复用 backend 可保持 held；完成前收束本轮 I/O 与已发起的退休，不等于每轮都停止进程。terminal、订阅发布和退休各自取证；完整原生尾部、强送达与 held 权限切换仍有暂停范围。

03

知识架构：新增完整的共享 Wiki 领域

旧版只有通用资料与工具路径；当前版增加了知识身份、受控维护与效果恢复责任。

当前实现的交接顺序：主库先持久接收；需要自动汇报时再交付结果输入；最后 ACK Wiki outbox。它不是跨数据库事务，也不等待后续模型答复才 ACK。

Registry 的 locality

决定准入、归属、创建与恢复；普通 Store 借用已准入对象，避免每次读写重新选择 owner 或触发全库恢复。

History 的 depth

复杂性在真实的文件效果：原像、prepared / applied、receipt 与 observer。删除它会把恢复规则散回所有写者。

多提交点的代价

主库、Wiki SQLite 与 Markdown 不构成总事务。通过持久效果和恢复协议对齐，不能把 job 的“完成”文字当作发布证据。

代码依据：Registry · History · Jobs · 维护准入 · 当前 Wiki 工具

04

账户与存储：收敛身份路径，明确格式交接

旧版已具备多账户。新版退出旧安装接管路径，将普通运行与当次发布转换分开。

取舍已经明确：长期只维护一种当前表示；格式不匹配就拒绝启动。账户归属、知识正文、有效效果与用户配置要保全，但不承诺任意旧库或旧包都能由当前程序自动升级。

06

当前仍可深化的地方

从这里开始，“右图”表示设计或建议，不是 before-takeover 到当前版本已经发生的变化。

01 · 待处理返回的请求接管

Strong已有确认设计 · 未实施in-process

server/sessions/turns.py:594 · server/research/manager.py:332 · server/delegations.py:1093,1264 · server/sessions/lifecycle.py:745

BG、Research、委派终态和问题各自组合原回执、归属检查、正文准备、唤醒与提交；理解一次返回必须跨多个 module。

沿已有合同，把共同接管协议集中在会话职责里；来源继续拥有正文、重试和来源结算。当前尚未落地，本文不再设计新 interface。

  • locality：接管顺序集中
  • leverage：服务多个真实来源
  • 测试：同一竞争矩阵跨来源

Deletion test：若删除深化后的共同模块，这些规则会重新散回真实来源，说明它确有深度。需要验证同返回竞争、ACK 丢失、正文读取期间归属变化、Stop 保留和 Owner 失败；仅测正文格式化不足。

与现有约定一致：architecture-contract：待处理返回接管设计已确认、未实施。唤醒与输入接管仍是两个提交点；Wiki 聚合 / outbox、Schedule、App 与人工输入不扩进此候选。

02 · 配置变更与请求捕获的 locality

Worth exploring建议 · 未设计接口local-substitutable

server/routers/agents.py:135 · server/routers/sessions.py:91 · server/routers/credentials.py:158 · server/agent_manager.py:171 · server/sessions/owner_runtime.py:1175

一致性仍要求多个路由主动持共享锁、校验继承并安排提交后刷新；请求准备再协同捕获，调用者要知道较多实现规则。

探索将配置变更、关联校验、提交后刷新与一致捕获收进配置职责；保持实际执行处的授权复核，不顺带重构 Owner。

  • locality：配置规则集中
  • leverage：变更与捕获复用
  • 测试：观察实际生效配置

Deletion test：目标是删除路由侧的协调协议，保留所属 implementation 内的锁与顺序；若删除新的配置职责会让规则重散回路由，才算深化。现有锁与 tests/test_request_configuration.py 已保障关键行为，收益主要是知识归属，优先级低于返回接管。

不重开现有暂停事项，不把 connector、prompt、memory 与慢运行准备塞进配置职责。当前没有足够依据把 Wiki History / Registry 或大文件一概判为 shallow。
