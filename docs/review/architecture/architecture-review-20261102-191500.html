CASE 01 · 已实现

返回接管：把“先做什么”收回模块

深模块不只替调用者执行几步；它承担这些步骤必须以什么顺序发生的责任。

具体走一遍：提交成功，但确认丢失

步骤当前代码做什么为什么必须这样
① 同 delivery 重入observe() 先查询原 source / delivery / session 的 receipt。此前已接管时，即使原材料已删除或 Owner 失败，也应观察原输入。
② 没有原回执prepare() 按需读取材料；准备期间不占 mailbox、生命周期锁或事务。材料读取可能很慢，也可能并发重复；不能为“只准备一次”阻塞人工输入。
③ 准备结束再次 observe / eligibility，恢复后再检验资格。任一 await 期间都可能被其他调用接管，或原 work 已取消。
④ 真正接管admit_client_submission 后才写入内存派发队列、构造 receipt。唤醒与输入 COMMIT 是两个事实，不能假装有跨阶段原子性。
⑤ 提交处丢确认ReturnUnconfirmed → reconcile 只核实原回执。确认不了就保留不确定，不换 delivery 重新执行来源。

为什么是现有 prepare 回调？

会话模块决定何时需要正文，但无需认识 BG 文件、Research 报告或委派记录的存储方式。若公开“先检查、再提交”两个阶段，顺序知识会留在调用者；若让会话模块接收所有来源材料的联合类型，它又必须理解所有存储。

什么没有合并？

来源业务成功与父模型处理成功仍是两件事；来源决定是否继续重试，Owner 决定接管与派发。Wiki outbox、Schedule 首次触发和人工输入没有被硬塞进统一 Job。

现存回归：丢 ACK + Owner 失败仍读原回执；并发准备可重复，输入只接管一次；不同正文保留真实 digest 冲突。本轮阅读这些测试，未重新执行。
  • locality：顺序归会话
  • leverage：三个真实来源
  • 测试面：一次完整接管

删除检验：删掉公共操作，复杂顺序会重新回到多个来源；只删一个转发函数不会产生这种后果。这就是它取得 depth 的依据。

CASE 02 · 已实现

原请求结算：把独立事实分开，再组合

业务成功、记录成功、通知成功和资源退出没有同一个证明，不能塞进一个含糊的 done。

一个比正常成功更有教学价值的场景

T0模型产生 success，原 Owner 选定结论。T1terminal 事务真实提交成功。T2刷新消息投影时抛错，后续通知不可用。应保留success + committed + notification unavailable；不能改判模型失败，也不能重跑。

CASE 03 · 已实现

RunDriver：只统一共同责任，保留真实协议差异

接缝是否成立，看是否有真实变化跨过它；Claude 与 Codex 的协议差异已经存在。

driver.py 的职责声明 明确写出：driver 拥有协议状态，不拥有进程、lease 或产品结论。普通 Codex 的 AppServerDriver 关联原 request / attempt / thread / turn；根 turn/completed 是后端事实，由 Harness 关闭准入并开始退休，产品结论仍由原 Owner 形成。

为什么检查必须贴近真正的写入？

①问题出现，用户答案已保存在本地。②回答等待 write lock；此时 Stop、根终态或问题 resolved 到达。③取得锁后，再检查原问题和原连接资格；关闭的目标不再收到迟到回答。规则本地答案已保存 ≠ 后端收到答案；之前合法 ≠ 现在仍可发送。

CASE 06 · 已实现

前端读取：数据仍有效，不代表原视图仍有效

同一次异步读取至少涉及两件事：能否更新数据，以及能否结束当前视图的等待。

当前 observeOlderMessages 记录读取归属，Store 在一次更新中检验窗口和游标；ChatView 校验原 read 身份 后才结束自己的加载状态。视图保留消息锚点和像素偏移，因为这属于可见位置的业务，而不是数据模块应该接管的知识。

交错需要的判断不能粗暴处理成
A 旧页返回，当前已切到 B缓存是否仍有效与 B 的视图状态分别判断。任何成功结果都更新当前 loading / 滚动。
读旧页时 WS 追加新消息原窗口与游标仍匹配时，旧页依然可以合入。只要 Store 发生变化，就拒绝全部旧读取。
同任务 WS 已 completed，旧 HTTP 返回 running保留终态；若 HTTP 带来完整 stdout，可补齐输出。整行覆盖，或整行丢弃。
观察被取消后新观察开始，旧结果迟到旧读取不能释放新读取的进行中状态。清空一个共享 loading 布尔值。

BG 卡片目前也经过 observeSessionAuxiliary，共享身份与代次保护；领域合并仍在 Store。SnapshotReads 只管理在途观察顺序，不复制实体或服务器 revision。这种小模块有明确职责，但它的调用方式仍可能混用不同范围，后面的候选展示了一个具体例子。

现存回归：换窗口拒绝旧页；WS 尾部追加不使合法旧页失效；旧观察不能释放后继读取；终态保留并补全 stdout。测试源码已阅读，本轮没有运行浏览器产品测试。

删除检验：删去原观察责任，组件又要理解账户换代、连接失效、游标和任务事件的交错；若把滚动锚点也全部搬入通用读取模块，反而扩大 interface。优秀设计把真正共享的时序收回，同时保留视图自己的职责。

从同一 text 计算片段 / 页 / 行text → window → LineCoordinates正文与坐标来自同一读取表示。
返回内部完整快照_DocumentRead内部快照含完整事实；公共 read 仍仅返回选定片段。
应用各自政策batch_read · Tasks · raw_blocks读取预算、来源覆盖、原文坐标等价分别归业务。

用带 BOM、CRLF、emoji 或 HTML 的正文就能理解这个 seam：原文 Unicode 码点坐标不一定等于提取正文坐标。如果每个消费者都重新查询全文，它们必须分别知道这些表示怎样对应。现在这份表示知识归 Store；内部拿到全文也不能冒充用户实际读过全文，阅读凭据仍按实际返回范围登记。

现存回归：raw / text / revision / 坐标与公共返回范围；外部编辑后的当前正文；revision 冲突不污染下一读取。旧路径已有外层 History 保护，不能凭两次连接就宣称过去存在并发版本混用；本项的可靠收益是知识归属，不是未测过的性能数字。

这就是 locality

编码、提取或坐标表示变更，优先集中修改 Store 的同次读取责任；无需让三个业务分别理解底层配对。

这就是 leverage

同一个内部 snapshot 为三个实际消费者提供完整能力；不是为未来可能出现的 Repository 提前造通用抽象。

另一个“小而深”的例子：content_mutations._authorized 只有少量代码，却隐藏原 Store 借用、History 锁、注册重验与当前授权的顺序。删除后，多入口要重新掌握这套协议，不能仅因它看起来像转发就判为 shallow。
