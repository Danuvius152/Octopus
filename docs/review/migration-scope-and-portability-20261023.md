# 迁移机制审查：取消旧版兼容，保留当前账户跨机器搬迁

> 日期：2026-10-23。状态：只读审查与修改建议，尚未实施代码整改或搬迁。
> 本次仅新增报告及文档入口；没有修改业务代码、生产数据库、服务配置或运行中的安装。

## 1. 结论

**按本次明确的产品边界，首次账户接管旧安装、旧目录 memory handoff、旧 schema 升级链、安装时代 token 轮换，已经属于应删除的历史兼容需求。** 不应继续为了这些场景增加恢复阶段、迁移日志和测试，也不必另做一个维护旧版本的离线升级工具。

这些机制并非从来没有用途：多租户设计当时明确要把无账户安装的数据接给第一个用户，见 [multi-tenancy.md §9](../plans/multi-tenancy.md)。但过去成立的过渡需求，不应成为当前版本永久维护的合同。memory handoff 的复制、校验和原子发布，在原需求下有合理性；现在应该删除这个过渡操作及其专属保护，而非保留操作、只拆掉数据保护。

**用户真正需要的是：将当前正在使用的账户、数据和必要的原生会话状态，从机器 A 搬到机器 B，并继续使用。** 这不要求理解更老的数据库或目录布局，也不要求把无账户数据转成账户数据。

审查同时发现两个已经存在的行为问题：备份文档建议排除可能包含独有修改的 fork 工作目录；启动迁移会重新添加用户移除的工具并改回特定 agent 名称。另一个主要缺口是：当前实现没有完整处理换机后的绝对路径、安装归属和 Wiki 文件系统身份重绑定。

## 2. 支持边界与审查基线

### 2.1 四种操作应当分开

| 操作 | 输入与结果 | 本次结论 |
| --- | --- | --- |
| 旧版本升级兼容 | 老 schema、旧目录、NULL-owner 数据，转换成当前结构 | 不再支持；删除对应执行路径及专属测试 |
| 空安装首次开户 | 空数据库创建第一个账户、密钥和有归属的默认资源 | 保留；不承担旧安装接管 |
| 当前版本故障恢复 | 当前数据因崩溃、中断、丢失文件事件等恢复到可判定状态 | 保留；按真实故障检查必要性 |
| 当前版本跨机器搬迁 | 已有账户及当前数据搬到空目标安装，账户和业务身份不变 | 需要实现并验收；允许用户名、根目录和文件系统变化 |

“首次创建账户”只是入口名称，不能据此把旧数据收编当成必要功能。新安装先开户，再产生业务数据，就没有无主 agent、无主会话和旧记忆目录需要接管。

“旧数据可丢弃”在本报告中指不再承诺导入旧格式；**不是清空当前正在使用的数据，更不是按创建日期删除较早的消息、记忆或 Wiki 历史。** 不支持的旧安装可以拒绝打开，提示使用新的空目录；无需为了拒绝兼容而自动删除原文件。

## 3. 具体发现

下列问题均为当前实现或文档的存量问题；本次不是对某个新提交的增量审查。P1 表示存在数据损失风险；P2 表示行为错误、需求取消后的维护负担或真实搬迁需求缺口。

### F1 · P1：备份文档错误地把 fork 工作目录当成可重建数据

**位置：** [backup-and-migrate.md:120](../backup-and-migrate.md#L120)、[恢复步骤:139](../backup-and-migrate.md#L139)；[forking.py:455](../../server/sessions/forking.py#L455)、[forking.py:536](../../server/sessions/forking.py#L536)、[forking.py:567](../../server/sessions/forking.py#L567)。

**触发与影响：** 用户在 fork 会话的独立工作目录中产生文件修改，再按文档排除 fork/ 备份并迁往另一台机器。目标库仍有会话，但独有文件没有备份，无法从会话记录恢复原工作树。

**证据：** 文档以“fork 的 session 仍在数据库里”为依据称目录可再生；实现却是 shutil.copytree 创建完整独立工作树，再将该目录保存为新会话的 working_dir。数据库不是这棵文件树的副本。后续修改、未跟踪文件和二进制文件不保证存在于消息中。

**修改意见：** 删除“通常应排除 fork/”及恢复步骤中的统一排除。按持久会话引用收集工作树，包括 fork 和需要保留的归档会话工作目录；只有明确确认可丢弃且不再被需要的目录才排除。不要把普通文件数据当缓存。

**验收：** fork 后新增独有文件并修改原文件；备份、恢复到不同根目录后，逐文件比较内容并验证该会话使用恢复后的工作树。本轮没有运行实际换机实验，也没有发现本机已经发生这类损失。

### F2 · P2：历史 backfill 在普通重启时覆盖当前配置

**位置：** [base.py:707](../../server/db/base.py#L707) 的内置 MCP backfill；[base.py:991](../../server/db/base.py#L991) 的系统 agent 改名。

**触发与影响：** 用户移除 ask_agent、research 或 schedule，或者把系统 agent 命名为 Default，随后重启。工具会被重新添加，名称会被改为 Octo。启动过程把“当前用户选择”继续当成“待升级旧默认值”。

**证据：** _apply_migrations 每次执行 backfill；写入迁移 stamp 并不阻止下次执行。改名分支虽标为 One-time，实际每次初始化都会检查并执行。临时数据库复现如下，未使用生产库：

| 状态 | mcp_servers | 系统 agent 名称 |
| --- | --- | --- |
| 已初始化，迁移 stamp 存在，用户修改后 | ask、bg | Default |
| 关闭后重新 initialize | ask、bg、ask_agent、research、schedule | Octo |

**修改意见：** 在不再支持旧基线后，删除这些历史回填和改名路径；新建资源直接使用当前默认值。不要再增加一套标志来维持已经取消的历史需求。现有用户配置在普通启动时只读取和校验。

**验收：** 当前 schema 新建账户，修改工具集合和名称，关闭并重新打开数据库，断言选择保持不变。

### F3 · P2：memory handoff 和首次账户接管维护的是已取消的业务路径

**位置：** [memory_handoff.py:310](../../server/memory_handoff.py#L310)、[main.py:102](../../server/main.py#L102)、[bootstrap.py:191](../../server/bootstrap.py#L191)、[bootstrap.py:217](../../server/bootstrap.py#L217)、[wiki/account_upgrade.py:229](../../server/wiki/account_upgrade.py#L229)。

**触发与影响：** 无账户安装升级为账户安装；或重启时重试遗留的记忆交接。当前产品为这个历史入口保留两套路径、孤儿行收编、旧密钥重加密、运行中会话接管、Wiki 分阶段日志及恢复入口。

**证据：** memory handoff 将本机旧 agents 根下的 agent/memory 搬到 users/<user>/agents/<agent>/memory；bootstrap 收编 NULL-owner 行并转换秘密的加密归属；Wiki account_upgrade 用 .first-account-upgrade.json 协调复制、发布、归属交接与清理。这些操作没有提供跨机器导出、目标安装配置或路径重绑定。

**修改意见：** 删除这条旧业务路径及其完整依赖：记忆搬移器及启动钩子、orphan adoption、旧账户升级日志/恢复 API/界面、仅服务该路径的 legacy_transition 和 vault transfer。首次开户缩为在空安装创建用户、DEK 和有 owner 的初始资源；业务入口要求账户身份。普通注册、邀请和当前账户数据继续保留。

删除前核对当前库没有该操作的未完成记录即可；本次已检查的安装没有待完成账户升级。不得把“迁移 owner”逻辑留下来仅为重跑已被取消的旧安装测试。

**验收：** 空安装能完成首次开户并产生有 owner 的资源；当前账户重启后记忆路径和内容不变。删除 [test_agent_memory_handoff.py](../../tests/test_agent_memory_handoff.py) 中只为旧目录搬移存在的测试；保留当前记忆读写、账户隔离和模型使用记忆的行为测试。

### F4 · P2：主库与 Wiki 仍承担多个不再支持的旧格式转换

**位置：** [db/base.py:530](../../server/db/base.py#L530)、[db/base.py:932](../../server/db/base.py#L932)、[wiki/schema.py:56](../../server/wiki/schema.py#L56)、[wiki/schema.py:188](../../server/wiki/schema.py#L188)、[wiki/protocols.py:65](../../server/wiki/protocols.py#L65)。

**触发与影响：** 普通初始化入口同时支持空库、当前库和多代旧库，必须长期保留旧表结构判断、列补齐、数据解释和中断后的恢复语义。新需求只需要前两者，历史分支增加维护和验证成本，还会产生 F2 这种实际配置覆盖。

**证据：** 主库仍处理引入 agents 以前的 session、旧 schedule 表达、内置工具与 pin 回填及已删除 bridge 表；[test_migration_backfill.py](../../tests/test_migration_backfill.py) 构造旧 schema 验证这些转换。Wiki 则从早期版本逐级走到 schema 11，包括 source binding 转换、adopt_legacy_jobs、migrate_legacy grants，以及缺 registration_generation 时的旧注册补写。

**修改意见：** 新空库直接建立当前完整 schema；已有库只验证明确支持的当前结构和协议。删除低于基线的逐级转换器与对应旧 fixture。发现不支持的非空库时，在写入前拒绝，不自动修复或清空。

这不是机械删除所有 initialize 或含 legacy 字样的代码：

- 当前新库仍需要 jobs、grants、event inbox、recovery 等表的 DDL；从迁移函数中提取到当前 schema 初始化。
- 当前生产到开发候选的输入账本变化必须按 §2.2 单独判定；不能整块删除混有当前必要变换的函数。
- 当前库中已经保存的 legacy_edge、legacy-explicit 等历史事实仍是当前数据；取消“导入旧格式”不等于删除这些事实或使现存记录无法读取。
- 当前协议不匹配时拒绝写入的检查仍需保留。版本校验不是旧版兼容。

**验收：** 空库直接达到基线；当前库反复打开不改写业务记录；旧 schema 在任何变更之前明确拒绝；当前 Wiki 历史、身份、授权和恢复流程仍可读取并工作。

### F5 · P2：已进入账户模式，设置页仍暴露旧安装 token 轮换

**位置：** [SettingsDialog.tsx:122](../../web/src/components/SettingsDialog.tsx#L122)、[SettingsDialog.tsx:173](../../web/src/components/SettingsDialog.tsx#L173)、[token_rotation.py:302](../../server/token_rotation.py#L302)、[main.py:100](../../server/main.py#L100)。

**触发与影响：** 当前用户进入设置页执行 token 轮换；界面提供操作，后端在存在账户时返回 409，说明 installation token 已退休。仍维护的环境文件替换、旧秘密重加密、rotation intent 与启动恢复，没有服务当前账户的这个入口。

**证据：** RotateTokenPanel 无条件渲染并调用 /api/auth/rotate；后端在 users 非空时拒绝。前端成功响应 mock 不能证明当前账户能实际使用该功能。

**修改意见：** 在只支持账户模式的合同下，删除旧轮换 UI、API、专属恢复状态与测试；保留账户密码修改、登录 token 撤销、master key 和账户 DEK。相关文档、计划状态也应同步标明旧功能退役。

不能据此全局删除 settings.auth_token：当前 harness/MCP 回调、首次 setup 和若干遗留分支仍引用它。实施时按用途拆清身份来源，删除旧业务登录和旧秘密密钥用途，同时保持当前受限 MCP 调用身份正确；不要把内部认证也当作过时兼容移除。

**验收：** 账户界面没有无法使用的安装轮换入口；密码修改和 token 撤销正常；真实账户运行中的 MCP 工具仍通过当前会话身份鉴权。

### F6 · P2：换机缺少一致的路径与身份重绑定入口

**位置：** [backup-and-migrate.md:108](../backup-and-migrate.md#L108)、[service_installation.py:306](../../server/service_installation.py#L306)、[wiki/registry.py:222](../../server/wiki/registry.py#L222)、[wiki/event_inbox.py:40](../../server/wiki/event_inbox.py#L40)、[wiki/store.py:408](../../server/wiki/store.py#L408)。

**触发与影响：** 搬到不同用户名、目录或磁盘，按现有文档复制状态并只修改 session.working_dir/Claude slug。安装归属标记仍引用源机器的 profile 绝对路径；Wiki 注册与事件账本仍绑定旧 root；文件 dev/inode 改变。可能被正确的保护检查拒绝，或留下未完整迁移的原生会话与路径引用。

**证据：** read_service_profile 检查资源标记指向的 profile 和当前配置必须一致；Wiki configure 明确拒绝改变已有 vault root；event inbox 对 root、vault_id、protocol 做精确绑定检查；文档文件身份含设备号、inode 和修改时间。现有 CLI 的 handoff/pull 是会话转交，不是完整账户备份恢复接口。

**修改意见：** 增加一次明确的当前版本离线导出/恢复操作，在目标副本上处理类型明确的路径与本机绑定；源数据保持不动，目标校验完成后才启用。普通运行时的归属和身份检查保留。不要让每次启动猜测“可能换了机器”，也不要通过删除 Wiki 账本或所有 ownership 标记来绕过检查。

**验收：** 两个临时根模拟不同 home、不同工作区和不同文件系统身份；恢复后账户、会话、Wiki 文档身份与历史不变，路径和目标安装归属正确。再在隔离环境进行当前 Codex 的真实恢复验证。当前代码静态检查足以证明存在这些绑定，但本轮未实测完整换机失败或成功。

## 5. 真正的跨机器迁移应交付什么

### 5.1 范围与接口

第一份完整合同可以严格限定为：**当前支持版本 → 同版本空目标；停机冷迁移；保留账户和业务身份；允许目录变化。** 不需要同时引入热迁移、双机同步、账户合并、任意旧版本导入或常驻迁移服务。

建议用一个内部模块承接数据清单、导出检查、恢复检查和发布；CLI 只提供导出、恢复两个薄入口。具体命令名不是合同重点，目前尚未实现。不要把路径修复散到 bootstrap、每次启动和多个 manager 中。

### 5.2 必须带走的内容

| 内容 | 搬迁要求 |
| --- | --- |
| 主数据库 | 保留账户 ID、密码校验材料、包装后的 DEK、agent/session/app ID、消息、配置、任务和当前持久输入/回执等；做一致快照 |
| 有效 master key | 无论来自文件还是环境，必须有受保护的转移与校验方式；密码不能代替它解开账户 DEK |
| 用户目录 | agent 长期记忆、附件、应用代码及 .data、其他持久用户文件；不能只复制数据库 |
| 实际会话工作目录 | 包括 fork、状态根之外的项目、未跟踪文件，以及需要保留的归档会话工作树 |
| Harness 登录与原生会话 | 按实际 credential home 收集，而非只复制默认 ~/.codex；保留用于原生 resume 的记录与相关索引 |
| Wiki | 实际 vault、注册、index.sqlite3 中的持久账本、历史/快照等文件；vault 可以位于状态根之外 |
| 安装配置 | 记录来源及目标路径映射；密钥受保护传递，本机端口、代理、服务环境等在目标重建或明确配置 |
| 可再生内容 | 仅排除确认可重建的依赖、缓存、运行日志等；日志是否保留单列选择，不影响账户和会话恢复 |

重要实现依据：

- [crypto.py:83](../../server/crypto.py#L83) 在 key 文件不存在时可生成新 master key。恢复预检不能调用这个有创建副作用的函数来“检查 key 是否存在”；应先只读验证所提供 key 能解包导出账户的 DEK。缺 key 时停止，不能先启动成一个新安装。
- [codex_login.py:79](../../server/codex_login.py#L79) 从 codex_home_dir 和 credential ID 决定专用 home；[harness/codex.py:842](../../server/harness/codex.py#L842) 从实际 CODEX_HOME 找原生会话。只备份 auth.json 或重新登录，不会恢复丢失的原生上下文。
- [sessions/credentials.py:81](../../server/sessions/credentials.py#L81) 的凭据选择存在缺少认证文件时的回退路径；验收需要证明用的是恢复后的预期 credential/session，不能因目标默认登录恰好能回答就视为搬迁成功。
- Wiki 的 index.sqlite3 名字含 index，但内含身份、历史关系、授权和任务等持久事实；不能整库删掉后重建来处理根目录变化。

### 5.3 路径变化与执行状态

建立明确的源根到目标根映射，只变更被定义为路径引用的配置和字段：会话 working_dir、用户可访问根、实际凭据 home、Wiki 注册/账本绑定、服务 profile 及 ownership 引用等。CLI 自身的路径索引按对应 backend 的实际协议处理。不要对所有 JSON、消息或历史文本做全局字符串替换。

应用代码或用户配置内自行写死的绝对路径，应在检查结果中指出，由对应配置调整；不能保证任意程序只凭搬文件就适配新机器。

Wiki 保留 vault/document/change 等业务身份；目标机器的文件键和观察器本地状态需要通过受控恢复重新建立。当前事件若未完成，应在导出前收敛或记录为明确的未完成状态；不能通过丢弃未解释的事件、历史或授权来伪造一致。现有 recovery 机制可作为实现依据，但目前没有证据说明它直接支持 root 改址。

不复制“活着的进程”：PID、socket、cgroup、临时锁和内存 owner 不会随数据继续存在。保留它们关联的业务结果与恢复证据，按当前恢复规则重新判断；不得自动重放已完成的模型请求、委派结果或定时任务。目标启用前确认源端不再写同一份业务状态，避免两个调度器都开始运行。

### 5.4 足够而不过度的失败保护

1. 从实际安装配置发现数据集合，停写并确认快照包含主库、Wiki 与文件的同一稳定状态；仅对主库做 SQLite backup 不代表所有外部文件已一致。
2. 导出当前格式声明、必要版本、文件清单/摘要、路径引用和密钥交付要求；敏感值不进入普通日志或仓库。
3. 恢复前验证格式、完整性、key、路径覆盖、空间与空目标约束；不支持的版本在写入前拒绝。
4. 在目标暂存区准备、重绑定和校验；验证通过后再发布和启用服务。中断后能明确清理或重试本次暂存，不触碰源安装、不半覆盖已有目标。
5. 目标通过数据检查和实际会话续用验证后，才由用户决定源机器数据如何处置。

这里的暂存、摘要和失败保留服务于一次真实的跨机器操作，属于必要数据保护。无需为从未支持的历史格式建立无限兼容链，也无需为冷迁移建立一个长期在主服务启动时接管的多阶段升级状态机。

## 6. 修改顺序与测试调整

### 6.1 建议实施顺序

1. **固定边界。** 以当前生产数据和当前版本作为支持基线；核对并行开发的 schema 差异。把“不支持更早版本”和“当前数据必须保留”写入负责当前行为的文档。
2. **先修正会导致错误操作的说明与行为。** 修正 fork 排除指引，删除启动时覆盖用户选择的旧 backfill，移除当前账户不可用的 token 轮换入口。
3. **整体退役历史业务。** 删除无账户业务运行、旧安装接管、memory handoff、专属日志/恢复/UI/API；建立清晰的空库开户入口，再删掉仅用于旧 schema 的转换代码和测试。
4. **交付当前版本冷迁移。** 在单一模块中完成数据发现、导出、受控目标恢复、路径重绑定和失败处理；覆盖必要数据，不能把“剩下手动改库”当成完整交付。
5. **同步文档和门禁。** 更新 backup-and-migrate、当前架构/账户说明及相关计划状态；将旧升级测试从默认门禁移除，换成当前版本重启和跨根目录恢复验收。

这是一份实施建议，不表示本轮已开始上述代码修改，也不把旧兼容清理作为擅自删除生产文件的依据。
