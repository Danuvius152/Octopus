### F15 · [P1] 转义 OAuth 回调页中的外部错误内容 — server/routers/connectors.py:266

**位置：** [connectors.py:266](../../server/routers/connectors.py#L266)、[connectors.py:96](../../server/routers/connectors.py#L96)；浏览器令牌存储见 [sessionStore.ts:472](../../web/src/stores/sessionStore.ts#L472)。

**触发与影响：** 攻击者能够在已配置 Connector 的安装中发起自己的 OAuth 登录，取得一个有效且未消费的 `state`，再让另一个已登录用户打开带该 `state` 和恶意 `error` 参数的回调链接。回调不要求浏览器携带 bearer，也没有将 state 绑定到发起登录的浏览器；错误值直接拼进 HTML，在受害者的 Octopus 同源页面执行脚本，可读取 `localStorage.octopus_token` 并以其身份调用 API。

**证据与复现：** 用真实 `ConnectorLoginManager` 建立测试登录，经实际 ASGI 回调路由传入含脚本标签的 `error`，返回 `200 text/html`，脚本原样存在，响应没有 CSP。再把这份响应装载到 Chromium 的隔离虚拟域，预置合成测试令牌，脚本成功读取到该值。没有真实 OAuth 交换、真实令牌或外部网络请求。state 校验能阻止随意伪造的回调，但不能使一个合法 state 后面的错误文本成为可信 HTML。

**修复与补测建议：** 在 `_callback_page()` 统一对标题和正文做 HTML 转义，所有 provider error、异常消息和标签都按文本呈现。补带合法 state 的 HTML/脚本错误参数回归，断言显示原文字面内容且不执行；同时保留非法 state 的现有拒绝行为。该缺陷破坏 [multi-tenancy.md 的账户隔离约定](../plans/multi-tenancy.md)，不能仅靠前端提示或 state 随机性规避。

### F12 · [P1] 确认整个进程组退出后再释放执行权 — server/harness/run.py:760

**位置：** [run.py:760](../../server/harness/run.py#L760)、[run.py:814](../../server/harness/run.py#L814)；相同问题也存在于 [app_backends.py:437](../../server/app_backends.py#L437)。

**触发与影响：** 主进程派生同组子进程，子进程将标准输入输出重定向并继续执行。主进程先退出时，Harness 可以成功返回 `stop()` 并清空 `_process`，而子进程仍能继续写文件。应用后端的子进程忽略 SIGTERM 时也会发生：父进程退出后，监督器报告 `STOPPED` 并释放所有权。后续新执行、应用重建或清理因此可能与旧写入者重叠。

**证据与复现：** 使用真实 Python 父子进程，子进程重定向到 `DEVNULL`，记录 PID 并停留在原进程组。Harness 父进程输出结果后等待 stdin EOF；调用实际 `HarnessRun.stop()` 后 `_process is None`，但 `/proc/<child>/stat` 显示子进程仍存活，且 `os.getpgid(child) == original_parent_pid`。应用路径中，子进程忽略 SIGTERM，调用实际 `BackendSupervisor.stop()` 后同样存活，而状态已为 `STOPPED`。两条隔离复现都成立；测试最后显式 SIGKILL 清理自己创建的进程组。

**执行路径：** Harness 只有等待直接子进程超时才发送组信号；正常退出不会检查剩余组成员，且 `_terminate_process_group()` 在 `proc.returncode != None` 时直接返回。应用监督器虽先发组 SIGTERM，但是否升级 SIGKILL 仍只取决于父进程的 `wait()`。读取到管道 EOF 也不能证明重定向后的子进程已经退出。[app_bridge.py:101](../../server/wiki/app_bridge.py#L101) 在 `backend_supervisor.stop()` 返回后直接 `finish()` 释放 Wiki 写锁，因此这里还破坏了失败写入者退休的前提。

**修复与补测建议：** 在启动时捕获进程组身份；停止过程在确认组内无存活写入者之前保留执行所有权，父进程先退出也应完成必要的信号升级与有界等待。补正常退出、取消、父进程先退出、子进程忽略 TERM 且关闭输出管道的用例；断言旧进程不能在停止成功后继续写临时文件，不能只断言父进程退出或 reader 结束。

### F01 · [P2] 在省略关联时保留原有关联段 — server/wiki/curation.py:330

**位置：** [curation.py:268](../../server/wiki/curation.py#L268)、[curation.py:330](../../server/wiki/curation.py#L330)。

**触发与影响：** 不带 `frontmatter_patch` 的 `organize` 分支，先建立关联，再以当前 revision 整理同一篇文章，仅修改标签并省略 `relations`。第二次整理会删除第一次生成的关联链接和解释，且不报冲突。

**证据与执行路径：** `_organize()` 先调用 `original_text()` 去掉旧生成区，并从字节变换记录中删除全部旧区；随后分别恢复省略的标签、别名及其他保留区，但 `relations` 只在本次 `linked` 非空时重新生成。省略关联时，旧关联区没有恢复路径。

**最小复现：** 第一次整理传入一个有效的关联文档、revision、location 和 explanation；读取整理后的 revision；第二次只传入标签更新。比较两次文件内容，原关联链接及解释消失。

**修复与补测建议：** 在请求形状和实现中区分“省略关联”与“明确清空关联”；省略时保留已有区及其解释。补连续整理回归，分别覆盖省略、显式清空、更新关联以及人工编辑生成区的情况。

### F02 · [P2] 正确识别代码围栏结束位置 — server/wiki/extract.py:271

**位置：** [extract.py:263](../../server/wiki/extract.py#L263)、[extract.py:271](../../server/wiki/extract.py#L271)；消费方为 [curation.py 的 restructure](../../server/wiki/curation.py#L440)。

**触发与影响：** 合法代码块内部出现以围栏字符开头、但带有尾部文字的代码行。分块器把它误判为围栏结束；后续重排接受拆开的块，导致原代码变成普通正文，或原普通正文进入代码块。

### F19 · [P2] 成功登录状态的重复读取应继续返回凭据 — server/routers/credentials.py:505

**位置：** [credentials.py:505](../../server/routers/credentials.py#L505)、[credentials.py:515](../../server/routers/credentials.py#L515)；消费方为 [HarnessPage.tsx:293](../../web/src/components/HarnessPage.tsx#L293)。

**触发与影响：** Codex 授权成功后，第一次 status 请求已将凭据落库并设置 `session.persisted=True`，但响应在到达浏览器前丢失，或页面在处理响应前卸载。浏览器重试同一登录状态时得到 `state=success, credential=null`。前端只有同时拿到成功状态和 credential 才结束登录，因此继续每两秒轮询，凭据已保存却一直停留在设备授权界面。

**证据与复现：** 使用当前账户 fixture、真实 ASGI 路由及临时数据库，仅把登录驱动状态设为合成的成功结果。首次 GET 返回新建的 credential；丢弃该响应后连续读取三次，均返回 HTTP 200、`success` 和 `credential=null`，而对应数据库行仍存在。`_persist_codex_login()` 本身有已持久化时的读取分支，但路由的 `and not session.persisted` 使它不可达。没有调用真实 CLI 或 OAuth 服务。这一路径在原报告基线中已经存在。

**修复与补测建议：** 对成功状态每次都按当前账户读取并返回已保存凭据；首次持久化仍需幂等，凭据随后被删除时要返回明确的终态。补首次成功响应丢失后的重复 GET、并发轮询及前端从重试响应正常退出登录的测试。

### F20 · [P2] HTTP 等待结束后继续计入未完成的应用执行 — server/app_agent.py:258

**位置：** [app_agent.py:258](../../server/app_agent.py#L258)、[app_agent.py:324](../../server/app_agent.py#L324)、[app_agent.py:134](../../server/app_agent.py#L134)；运行状态读取见 [app_agent.py:554](../../server/app_agent.py#L554)。

**触发与影响：** `/agent/ask` 等待超时或调用方取消等待，原已接收请求按约定继续运行，但 `finally` 立即调用 `_release_turn()`，删除应用级执行记录并取消完成观察者。会话列表随后返回 `running=false`；应用的并发检查也不再计入这些真实执行。SSE 的迭代器退出有相同释放路径。账户总额度高于应用上限时，依次超时即可超过每应用 4 个执行的限制，不需要 F11 中的并发创建竞态。

**证据与复现：** 使用真实 `SessionManager`/SessionOwner、真实数据库与受控假 Harness，先完成独立的初始构建，再顺序提交 5 个保持未完成的问答。仅缩短 HTTP 等待时间，并将可配置的账户总额度设为 6，以单独观察应用上限。五次均已实际开始且返回 504；最终 `session_is_executing()` 对这 5 个会话均为真，`_turns` 却为空，应用会话列表全部返回 `running=false`。最后释放假 Harness 并完成退休。账户总额度仍独立生效，本项不声称绕过该额度；默认额度下的错误空闲状态仍存在。

**违反约定与修复建议：** [app-agent-access.md §2、§6](../plans/app-agent-access.md) 分别要求取消等待不取消已接收命令，以及按执行限制每应用并发。HTTP/SSE 消费者退出不应释放实际执行的计数；从原请求的完成和退休事实维护该计数及列表状态，并单独解除已离开的响应消费者。补超时、调用方取消、SSE 断连后仍计数，原执行结束后释放，且不重复执行的测试。本项是既有生命周期缺陷，与 F11 的接收前并发预留缺口分开修复。
