## 2. Ticket22：Codex app-server与原生尾部

**依赖：** 20。\
**规范：** A、P、L1–L2、N；当前attempt的G1–G8。\
**最终结果：** 同一request的主输出、原生子结果及相应父后续处理正确归属，真实结束或明确失败/停止后只交付一次结果。

### 22-P0：实际版本运行合同与可行性调查

**首个反例：** 用旧exec历史cold resume；主turn先结束、child仍工作；子结果触发父处理；父再委派一个验证任务；最终汇总。分别在根turn结束后及父续跑中Stop。

- [ ] 记录实际CLI版本、生成schema、认证方式、multi-agent模式和相关实验配置；okou/官方main的版本不能替代部署版本。
- [ ] 分别列出基础RPC、活动输入、问题/审批、恢复、原生尾部和停止的实际能力与证据。
- [ ] 写清本request后代范围的发现依据、同child再次执行的身份、快速/孙任务/晚到事件与cold resume覆盖。
- [ ] 证明结果进入父处理输入及父后续阶段的关联；child completed、wait返回和UI卡片为空均不单独算完成。
- [ ] 评估原生wake与必要宿主报告，选择一条可证明的驱动策略；不预设关wake，也不并行保留两套报告触发器。
- [ ] 若使用显式报告，验证工具数据身份、parent/root因果关系、活动turn竞争、hook拒绝/改变及发送未知。
- [ ] 说明结束依据与受管Stop范围；不以重复list为空、静默窗口或一个成功回答替代范围证明。
- [ ] 标明稳定接口、实验能力与内部行为；缺少必要能力时保留具体阻断项，不缩小原需求后改称完成。

**退出条件：** 一页可执行的运行合同及针对性录制/源码依据。基础可行与强尾部可行分别给结论；只有基础通过可继续开发协议模块，强尾部未通过则22/最终切换仍未验收。

### 22-P1：小型RPC客户端与兼容事件映射

- [ ] 保持Harness公共入口和原JSONL路径；在现有profile/registry接缝选择Codex私有实现，不新建业务Owner或通用传输平台。
- [ ] 明确一个process owner；由HarnessRun提供受管I/O或完整移交并删除旧责任，不能两方各自stop同一资源。
- [ ] initialize/initialized、RPC关联、response/notification/server request分派及完整帧writer职责明确；ACK等待不锁住控制通道。
- [ ] 对已使用方法建必要的typed边界与fixtures，不维护未使用的全量协议镜像。
- [ ] 映射正文、工具、问题、错误和usage到现有合同；保持当前delta/最终快照行为，不把所有消费者改成解析原始RPC。
- [ ] 已支持关键事件字段缺失准确失败；未知可选通知兼容忽略；必要native完成事实不因展示映射被丢弃。
- [ ] 原生turn终态单独保留，不直接生成可结算request的result/EOS。
- [ ] 复用原交付队列；控制不受展示背压阻塞，实际容量耗尽准确失败，不使用无界通知缓存。

**首个反例：** 等待一次RPC响应时，通知、server question、Stop与未知可选事件交错。客户端持续分派，映射不重复正文，不能把支持事件的缺失身份默认成当前请求。

**退出条件：** 纯映射fixture与协议替身证明相关行为；旧公共事件消费者仍能读。该阶段不切生产、不算原生尾部通过。

### 22-P2：执行接线、历史、配置与基本控制

- [ ] 一个request attempt独占stdio宿主；同请求多个原生turn仍用原宿主/原binding，保留late spawn与原停止/join职责。
- [ ] 初始化和配置确认后start/resume；验证旧exec history，保持现有session/thread字段和fork/rewind合同。
- [ ] 将controller更新并入同一宿主并按原检查点生效；删除被替代临时writer，不同时写同一thread。
- [ ] 验证真实每凭据CODEX_HOME、登录/API-key方式、cwd、model/effort/tier、memory、MCP bearer与工具名、connector及instructions。
- [ ] Research web leaf进入交互RPC但保留只读/工具范围；oneshot继续exec，不宣称原有轻量路径已强制tool-free。
- [ ] 初始输入、局部活动输入与控制区分写入、provider接受、未知；ACK丢失不重发，不自动回exec。
- [ ] 使用expectedTurnId；只有明确未接受的拒绝才可沿原规则排队。取消在途RPC后不复用失信连接继续执行。
- [ ] 原生问题有明确归属/答复接口；未知审批与elicitation准确拒绝或失败。当前权限策略不因迁移改变。
- [ ] 正常、错误、EOF、取消使用捕获资源收尾；输出/诊断按原机制交付，usage不重算恢复历史。

**首个反例：** 恢复旧history后更新controller，再启动turn；steer写出但响应丢失，随后Stop。不能重复输入、换身份、重复统计或让第二个writer接管未知执行。

**退出条件：** 固定attempt的基础协议与原功能兼容证据齐备。可以报告transport parity通过；22整票仍等待P3，公共输入完整接线由24验证。

### 22-P3：主结果、原生续跑与最终完成

- [ ] 主结果作为候选立即展示；native turn结束不关闭原scope/WikiTask或直接完成receipt。
- [ ] 依P0合同跟踪本request受支持execution与父后续阶段；其他请求/账号的thread排除，本request后代不能一概过滤。
- [ ] 保留原生多轮处理与再委派；无固定一次报告上限，也不隐式关闭原生wake。
- [ ] 只实现P0选定续跑方式。必要显式报告由原request授权、使用真实收集结果和工具数据身份；不成为新human输入，不获取新授权。
- [ ] 报告接受、输入生效、阶段终态与范围覆盖分别确认；失证、hook拒绝和发送未知不能用正文或ACK补齐。
- [ ] 复用原总预算、停止与资源上限；不加无限人工汇总循环、持久任务树或新的通用监督器。
- [ ] 按L2先关闭原准入/撤lease并发起停止，不等待未结清ACK；再按既有退出政策join捕获I/O、工具、宿主及受管资源，确认退役后向原Owner提交最终结果一次。
- [ ] 根turn已结束时仍能Stop；已显示主输出保留，最终结果体现取消/失败，不提前锁成功。
- [ ] 原生子失败保留来源与原因；独立bg/Research/delegation work不被此宿主退出取消。

**首个反例：** 主turn结束→子结果→父处理→新验证子任务→父最终报告；交错晚到旧事件和根idle时Stop。不能第二轮即失败、提前结算、双报告或把停止ACK当退出。

**退出条件：** G1–G6及当前attempt的G7/G8依据齐备，所需native范围确实可证。23再验证跨request，24/28接公共输入与结算，31验证所有消费者；不要求22等待这些整票，亦不把其组合结果写成已通过。

**本票不做：** 全局宿主池、子线程浏览器、定向子agent steer、自动崩溃续做、新审批产品、DeepSeek backend、第二份业务完成账本。

## 3. Ticket23：跨请求绑定与原隔离计划

**依赖：** 22、52。\
**规范：** L、C；G7、G9。

- [ ] 捕获原request/attempt/work、backend handle、配置/凭据引用与lease；异步回调不查最新session上下文。
- [ ] 同request主处理、native尾部和必要报告保持原授权；result候选不早关WikiTask，动态撤权即时有效。
- [ ] 真正结束或明确终止后按L2关闭原准入、撤lease并发起停止，再join原工具/输入及宿主；不能先等需靠停止才能结束的I/O。确认退役后才建立下一request的新lease/进程，不保留跨请求动态重绑路径。
- [ ] 新普通Submit进入队列，不构成停止旧native尾部的依据；旧Stop/问题答案/事件只能作用旧实例。
- [ ] Claude保留stream-json、同轮steer和原生功能；调整共享EOS/Owner完成边界，必要时局部归一事件，不新增Claude RPC或agent loop。
- [ ] Claude旧result/idle只是基线；完整候选仍保留已知原native工作及父后续回合，旧request真结束后才冷恢复下一轮。已结算旧receipt/已关闭WikiTask不能被迟到idle重新打开。
- [ ] 区分WikiTask关闭与run lease撤销，不能因一个发生就假设另一个也发生；不延长或重新授予已失效权限。
- [ ] 无法确认退出时保留handle和原隔离事实，不丢引用后启动新writer；不调用独立work的close/cancel。

**首个反例：** R1父结果已显示但native工作未完，R2到达；同时发生旧Wiki调用、授权撤回和旧定向Stop。R2须排队，R1不取得R2权限，新输入不截断R1。

**退出条件：** G7/G9跨请求身份与权限成立；分别报告Codex与Claude证据。记录取消热复用的启动成本；Claude缺少原生结束证据时明确未验收，不能以关闭后台功能通过。

## 4. Ticket24：公共输入、Question与控制

**依赖：** 21、23。\
**规范：** A3、P2–P3、L；G4–G5、G7/G9的公共输入部分。

| 输入 | 路由与确认 |
| --- | --- |
| Codex初始输入 | 当前宿主turn/start；确认provider接受与对应turn。 |
| Codex活动追加 | 已验证阶段的turn/steer，携带expectedTurnId；接受、明确拒绝、未知分开。 |
| 尾部/内部报告期间新human输入 | 原权威队列，后续request；不混入内部结果交付。 |
| Claude同请求追加 | 原stream-json协议；只报告实际可得的送达证据，不伪造RPC ACK。 |
| Octopus AskUserQuestion | 原问题通道和原问题身份。 |
| provider原生问题 | 原连接/server request/thread/turn上的typed答复；不是steer。 |

- [ ] 公共can_steer取实际能力与阶段，维持原API字段；input与跨request复用能力分开。
- [ ] Octopus持久接纳、provider送达与请求完成分别投影；复用既有输入账本，不复制一套okou输入状态机。
- [ ] 明确未提交才可回队；unknown不恢复pending、不自动POST或换协议；迟到ACK只更新原输入事实。
- [ ] Stop/Answer不被展示或无限ACK等待阻塞；旧连接复用相同RPC数字ID时仍不能串答。
- [ ] 问题生命周期接原Question Owner。未支持审批有明确关闭结果；必须人工审批的策略先补typed契约/UI，普通超时回答不能代批准。
- [ ] 正文、附件、UTF-8和实际RPC帧边界验证；尚未支持的mid-turn附件按既有明确排队策略处理。

**首个反例：** steer写出、turn结束、ACK丢失和Stop并发；不产生第二次输入。尾部中另一个Submit到达，不能唤起新request权限或混入父报告。

## 5. Ticket25：独立后台返回

**依赖：** 21。\
**规范：** 第8节；G10–G11相关返回。

- [ ] 独立bg、Research和named delegation使用原来源/工作身份；持久接纳在来源ACK之前，重送只接纳一次。
- [ ] 父request完成或CLI退出不撤销manager-owned work及其合法返回归属。
- [ ] 返回形成后续输入或原返回事件，不复活旧receipt；父request不等待只能由下一run消费的返回。
- [ ] native子结果与legacy idle不伪装为本票持久返回；各走原native归属/会话投影。
- [ ] 人工追问与parent新round区分，不因人工继续重发旧caller回报。

**首个反例：** 父已完成，独立任务返回的接纳响应丢失；重送后仅一次后续输入，工作与会话仍按原合同存续。

## 6. Ticket28：输入与唯一最终结果结算

**依赖：** 21、24。\
**规范：** A2、L2、N4。

- [ ] 根据真实送达事实结算原输入，主turn成功不推导所有追加输入都已接受或处理。
- [ ] 首result为候选；强尾部满足22合同且原资源退役后，才进入唯一terminal/receipt。
- [ ] 内部原生续跑/collect/report不生成新human submission；来源与阶段关系复用原记录，不增第二账本。
- [ ] 不因旧legacy idle修改已完成receipt或旧App/委托回传；完整候选的活动尾部应始终归原request。
- [ ] Owner按原事务提交，之后通知；通知失败不撤销已提交结果，重复终态不覆盖新request。

**首个反例：** 主输出成功、某追加输入unknown、父后续处理结束、旧终态重复到达；只结算证据支持的事实，unknown保留，最终完成一次。

## 7. Ticket30：普通委托会话保留与继续

**完整验收依赖：** 25、26、28、29。\
**规范：** 第8节；G11。

- [ ] 移除普通委托成功/失败/取消后的自动归档决定，并修正启动按delegation origin扫归档。
- [ ] 本round终态、原caller一次回传与配额/资源正常收束；conversation保持未归档，不靠永久running或进程维持可见。
- [ ] 已打开视图不跳走，保留输入及从原委托卡片访问；侧栏沿原过滤偏好。
- [ ] 人工追问新建human request；parent显式follow-up按29新建round/work，延续原conversation与来源约束。
- [ ] 旧Stop/旧回调/资源退出不能归档或取消新轮次；新request经过23的真实退役屏障。
- [ ] 保留会话、完成回传或人工继续不自动close/cancel独立work；晚到返回仍按25处理。
- [ ] 显式Archive、schedule临时会话、setup失败清理和历史归档访问保持原合法策略；不全量unarchive或改origin绕开规则。
- [ ] single-turn/no-follow-up提示约束该委托round，不误禁同request的原生后续处理或后续人工追问。

**首个反例：** 完整结果回传、原CLI退出并重启服务后，普通委托会话仍可访问和追问；再交错parent follow-up、独立后台返回与显式Archive。

**退出条件：** 正常保留、启动恢复和合法归档都成立。只改前端、只延迟归档或仅修成功路径均不完成。

## 8. Ticket31：公共消费者、后端与竞争组合

**依赖：** 27、30。\
**规范：** G1–G12及各责任票。
