修订：2026-10-13，Asia/Shanghai。设计版本为 v2.1，沿用 `v2` 文件名。适用代码：`Danuvius152/Octopus` commit `453a7995bd6c54df33b0fc41dec09d370b4b40aa`；原隔离探针的事实和日期不变。本文件给 Vera 一套可执行的验收依据，也约束 Octo 的优化取舍和 Weber 的阅读策略。它不改变已确认的维护范围、正文保全、人工编辑保护与恢复规则。

## 1. 问题与目标

本轮先回答四个可观察的问题：能否正确找到目标；能否读到支持答案的当前段落；宽泛问题是否覆盖不同材料；达到相同证据质量时是否更快、更省上下文。不能把“搜到一篇”“模型回答听起来正确”或“总 token 下降”单独当作完成。

知识库长期使用还要回答：旧知识能否在新问题中复用；一次整理需要多少人工改正；用户、外部作者与模型推断的归属是否明确；改正一处信息是否引发不必要的多篇重写。Concept 和 Topic 以实际复用价值评价，不按新增页数评价。首批整理不等待完美 persona、语言实验或 app UI，执行顺序见[迁移方案](local-shared-wiki-migration-v2.md)。

真实资料盘点中，`Library` 下约 37 份 Markdown，包含一篇很短的个人信息、两篇长技术报告、课程材料与文章，其中两份是 assets 项目说明，不能把 37 直接当作默认知识候选数。另有库根目录导航等文件。隔离基线提取了 40 份 Markdown，合计 628,455 字节；不是全量生产环境副本，未包含 HTML/TXT/PDF、媒体和生产索引中的 managed metadata。

当前实现已经具备中文分词、连续中文 bigram、大小写与全角规范化、章节定位、跨章节词组覆盖、文档级去重、目录过滤和当前 revision 读取。保留这些能力，重点解决以下缺口：

- 原生 OKF `title/description/type/sources/generated` 与本地扩展 `uid` 尚未完整接入现有索引与身份层，模板、导航、摘要与正文的角色不够清楚。
- 每次新建 `WikiStore` 和查询时刷新文件树，存在与结果数量无关的遍历开销；只测复用 store 的内部查询会漏掉实际入口成本。
- 宽泛问题需要主题覆盖；同一来源的多个总结不能挤掉独立材料。
- 词法未命中可能来自问法差异，也可能是资料根本不存在，必须先区分。

这些现状以当前源码和隔离探针为依据：[索引实现][repo-search]、[store][repo-store]、[registry][repo-registry]。现有测试能证明其各自覆盖的机械性质，不能代替本轮端到端评估。

## 2. Vera 的职责与评估边界

Octo 实现与自测，Vera 用同一份查询集独立检查结果和回归，Weber 提供符合实际阅读目的的期望行为与少量人工相关性标注。普通 `/wiki` 查询不默认启动三个 agent；否则增加的验证、重复检索与上下文复制会抵消优化。

实际迁移由 Octo 统一组织，现有 Vera 在首次生产写入前参与讨论试点样本、基线与验收证据，首个 1～2 篇写入任务后检查实际 diff，完整试点后给出放行依据，批次结束或重要规则变化后复核，最后核对全量覆盖。当前用户要求 Library 下所有 Markdown 参与整理、入库与检索验证，pika_vault 优先；Me、Research、课程笔记、导航和模板同属最终范围。逐篇身份/索引/精确定位/当前内容读取由全量清单验证，领域内容另做内容检索，特殊角色按相应范围检查；Vera 的语义抽查不替代逐篇检索覆盖，也不冒称全库语义逐篇认证。

Vera 分开评三层：

| 层次 | 输入与观察结果 | 失败示例 |
| --- | --- | --- |
| 检索 | 问题、scope、候选文档与章节 | 找到 Vidu 模板示例，没找到 Vidu 报告 |
| 阅读 | 当前文件、revision、读取片段与覆盖 | 命中正确报告，却引用旧版本或只读摘要 |
| 回答 | 用户问题、实际已读证据、答案 | 把“有条件地有效”写成“总是有效”，把转载作者的“我”认作用户 |

确定性契约、文件不变性、去重和版本检查用程序验证；观点归属、证据支持与主题覆盖用明确 rubric 的人工/独立模型抽查。结构 lint 不冒充事实核验。已有 AI 总结也不因此自动获得 `verified`。

## 3. 语料、标注与基线

### 3.1 固定真实语料快照

在隔离目录复现输入，记录文件清单、内容 hash、索引版本、代码 commit、运行环境、解析器版本；不将私人正文提交到公开仓库。生产库不注入测试材料。

每条查询保存 `id/query/intent/scope/gold_documents/gold_sections/answerability/required_facets/forbidden_claims`。gold 文档优先使用已有 server doc ID；已有 OKF 扩展 `uid` 记录其映射，路径用于显示。仅在隔离输入没有运行时身份记录时，以快照路径和 hash 暂定标识，导入后保存映射。没有 UID 不等于没有稳定身份，不要求用户先手工补完元数据。章节位置按本轮内容重新解析。

个人信息 gold 只来自 `Library/Me/information.md`。当前它仅明确院校、博士研究生在读身份与学科；不能借聊天记忆、研究报告题目或参考文章补出职业、研究课题、联系方式或偏好。

### 3.2 已完成的有限基线

下表来自隔离 Python 探针；每项热操作运行 5 次，列中位数。stat 计数本身带来测量开销。结果只说明当前代码的访问形态，不能当作用户 WSL、HTTP/MCP 或模型回答耗时。

| 操作 | 本次中位数 | Vault 内 stat 次数 | 解释 |
| --- | ---: | ---: | --- |
| 热 `WikiStore` 构造 | 31.5 ms | 276 | 每请求构造有全库相关成本 |
| 未变化库的 `refresh` | 42.9 ms | 335 | 没有重读全部正文，但仍遍历并检查文件 |

| 新 store 后搜索 Vidu | 74.0 ms | 623 | 未包含 HTTP/MCP、CLI 和模型耗时 |

### 3.3 后续对照方式

先保留当前实现为 A；再分别比较 B（解析/身份/角色接入）、C（常驻 store 与增量刷新）、D（overview/compare 选材）、E（可选语义召回）。不要一次改完全部模块后只报一个总分。相同查询、相同语料、相同回答模型与同一硬件对照；至少保留一组没有用于调权重的改写问法。记录 prompt 版本、实际装配版本与工具能力，避免将多个变量的变化都解释成检索收益。保留原 30 条诊断题，另加 10 条分期场景；这个规模不足以宣称普遍 SOTA。

## 4. 查询模式、接口与阅读预算

拟议查询接口统一使用 `intent: lookup | question | overview | compare` 和 `view: compact`；保留现有 full 返回形式以兼容旧调用方。用户未显式指定 intent 时，由入口中的轻量规则与当前任务语义确定；精确路径、server doc ID、无歧义 UID 映射、题名与真实别名查找不用 LLM 扩写、向量或重排。

| intent | 起步读取策略 | 必须观察的质量 |
| --- | --- | --- |
| `lookup` | 先解析 UID/路径/题名/别名；唯一命中直接返回可打开位置；需要内容时再读目标 | 精确定位不被广义相似度覆盖；重名保留歧义 |
| `question` | 少量候选卡片，读取最相关正文和必要上下文 | 证据支持问题中的实体、条件、否定与时间 |
| `overview` | 先看不同材料/主题的候选卡，再选代表材料读正文 | 主题覆盖和来源多样性；不把 Top-K 宣称成全部相关资料 |
| `compare` | 分别检索比较对象，再读各方对应维度 | 两方都有依据；缺项明确留空，不拿一个来源代替全部 |

`compact` 卡片包含稳定 ID、当前路径、显示标题、简短 description、文档角色、命中章节、revision 与必要状态。Key note 可按需取，不在每张卡片重复发送完整 frontmatter、sources、多个大 snippet 和 history。不能为减少 token 把可回查的身份和证据位置删掉。

批量读取使用 `read_many`：每个 item 是 `doc/start/length/expected_revision`，整体以 `budget_chars` 限制返回量。每个 item 独立返回成功、冲突或失踪；明确 `truncated`、实际范围和可继续位置。坐标沿用当前 `read` 的提取文本坐标，客户端不得混用字节、UTF-16 code unit 和服务端字符坐标。字符预算便于服务端执行，但不能宣称它等于模型 token；token 用实际 tokenizer 或 provider usage 另记。

建议的初始预算只用于试跑：lookup 通常 0–1 张卡；question 先看 6 张卡、读 1–3 处正文；overview/compare 先看 8–12 张卡，再读 3–6 个有独立价值的文档。证据正文可从 8,000 字符起步，复杂比较可提高到 16,000 字符。以上是 **proposed 起点，不是总阅读上限**。整篇总结或论证评价应读完整目标文章；证据缺口尚在时按缺口继续，不能因额度到了就把部分阅读写成全面结论。

“真实”表示目标与内容已在附件 Markdown 中确认；“注入”表示只在隔离副本构造。未填完的准确 gold 段落在正式运行前从当前正文标注，不能由答案模型自己生成 gold 再自评。

| Q34 | 先“讨论这篇如何帮助我的研究”，再明确“把刚才我的结论保存到指定笔记” | V2-06/08 / 两步同主题任务 | 讨论阶段无写入；保存阶段按明确目标和当前 revision 写入，标清用户观点与文章依据；不改写原 Reference，不自动发起全库维护 |
| Q35 | 在 Sapphire 只看同时有“数字人”“实时”标签的文章，再改成任一标签 | V2-05 后续 / 固定 tags fixture | `tags: string[]` 与 `tag_match: all/any` 行为一致，默认 all；标签与用户 scope、query 同时生效，分页结果不漏用过滤条件 |
| Q36 | 显示当前目录标签计数，再给同一篇增到 50 个章节，移动或修改它的标签 | V2-05 后续 / 注入标签、章节和变更 | `GET /api/wiki/tags` 与 app `wiki/tags` 统计按当前 scope 的 doc ID 去重，章节数不多计，变更后可观察地更新；两份同源文档的计数不声称是两个独立来源 |
| Q37 | 在 SmartReader 对同一篇资料连续两次执行后续设计中的保存/入库动作 | V2-09 后续 / 相同资源与已存在主文 | 复用同一当前知识对象或明确版本关系；不复制主文和模型总结；已有人工作品时不因 URL 相同就覆盖；返回真实目标与状态 |
| Q38 | 读文时选中一句话、写下个人批注，再问“这句话有什么限制？” | V2-09 后续 / 明确原文与批注 fixture | 传实际文档/revision/范围，原文和个人批注可区分；读取足够上下文，批注和临时讨论不自动成为共享知识或用户长期画像 |
| Q39 | 整理 6 篇时，第三篇被我外部修改；中断后继续，并恢复其中一篇自动修改 | V2-06/08 / 6 篇副本与 revision 冲突 | 冲突目标重读/跳过并记录，其他成功回执可复用；续跑不重写已完成全文；恢复检查当前 revision，不能抹掉后来的人工改动 |
| Q40 | 用中文、英文、混合三版等义任务规则处理同一组小任务 | 可选语言实验 / 6 任务×3 版本 | 模型/推理配置/工具/语料/要求固定，观察归属、保全、参数、实际 token 和改正量；仅重复不稳定项，不以单次结果或字节长度认定某语言最优 |

另做一组非问句接口契约检查：`read_many` 部分冲突、预算刚好截断、emoji 与中文坐标、无效 ID、空结果、旧 full 客户端兼容。Sapphire 点开同一引用的实际位置在 V2-05 后续检查。它们验证接口，不另造一批相同意义的检索题。

## 6. 库膨胀与 AI 总结污染实验

### 6.1 先定义什么算“同源”

`generated` 只表示某次生成/整理事件。此前 `article-v1` 的 Reference 也有该字段，但保留原文，因此不能一律判成二手总结。文档 `doc_role` 沿用内容合约的 reference / source / synthesis / concept / navigation / personal / template / unknown 投影；段落 `section_role` 沿用检索合约的 summary / body / relation / editorial / example / metadata。原稿快照依据导入登记与来源关系识别，不依靠文件名猜测。

同一文档的 description、Key note 和正文不是三项证据。按 Q57，本期检查实际出处可回查、已知直接依赖可提示变化、明确重复表示/摘要不放大支持；不同文章不因共享参考文献被合并。来源未知不补造，本地报告可作为“该报告如何判断”的直接依据，有价值的综合继续可用。完整 root_source_ids 闭包和自动独立证据数不作为核心放行门槛。

### 6.2 注入矩阵

| 变量 | 建议规模 | 必须保持的性质 |
| --- | --- | --- |
| 同一原稿的近似摘要 | 0 / 5 / 20 / 100 份 | 原稿可找到；重复复述不增加独立证据数量；不挤掉另一条相关来源 |
| 无关但高频提“AI/数字人”的摘要 | 0 / 100 / 1,000 份 | Q03–Q12 的实体与证据命中不退化；overview 不被词频淹没 |
| 同一长报告的章节数 | 5 / 50 / 200 节 | 文档不占多个结果槽；所需不同章节仍能展开 |
| 旧摘要与当前原稿冲突 | 原文含条件 C，摘要漏 C | 回答以可追溯的当前正文为依据；显式标注冲突，不按出现次数投票 |
| 人工分析与有价值多源综合 | 原稿 A+B；人工观点；综合页各一份 | 保留原创分析与综合的检索价值；不把“排除 AI”当粗暴过滤器 |
| 总语料规模 | 真实快照 / 1,000 / 10,000 文档 | 热 lookup 不随全库 stat/正文读取线性增长；质量与资源成本分别报告 |

合成扩容保留固定 seed 和生成清单，测试材料显式标记为 fixture。只复制相同原文不能代表真实规模分布；同时保留长度不同、主题分布不均和真实无关词项的材料。10,000 文档试验是扩展性探针，不是上线前必须搭建的大工程。

### 6.3 选材策略的可验证边界

先用文档/来源身份做确定性归并，再按主题选择代表材料。宽泛问题可采用 MMR 的“相关性与新增信息兼顾”思想，但本库先用来源、主题与章节覆盖即可；没有必要为了去重先部署向量系统。[MMR 原始研究][mmr]

RRF 只在有不同检索后端时作为候选融合方法；不把 BM25、cosine 与人工质量分直接按未经校准的数值相加。精确身份命中保留独立优先级。QMD 已经融合的结果不要再次无理由做一遍相同融合。[RRF 原始研究][rrf]

## 7. 度量：质量、速度与 token 必须一起报

| 指标 | 统计口径 | 为什么需要 |
| --- | --- | --- |
| ExactHit@1 / ambiguity accuracy | 唯一题名/UID/路径是否第一；真正重名是否保留选择 | 防语义排序覆盖精确对象 |
| Document Recall@K 与 precision@K | gold 文档是否在候选；相关文档占比 | 分开定位能力和噪声成本 |
| EvidenceHit@K | 实际读取是否包含 gold 论述及其必要条件 | 找到文档不代表读对证据 |
| FacetCoverage@K | 仅对 overview/compare，覆盖人工标注的实际主题或比较维度 | 不能用更多同类摘要冒充覆盖 |
| 明确重复与出处回查 | 固定语料中已知重复表示/摘要是否占满候选，实际引用能否回到依据；未知单列 | 重复摘要不制造共识，不以自动完整来源根作为门槛 |
| 证据支持率 / 错误断言 | 逐项检查有实质内容的回答断言是否被已读证据支持 | 评价最终答案而不只是排名 |
| 不可回答判断 | 资料不存在、只有二手转述、证据相互冲突分开记录 | 防“无命中”与“不知道”混淆 |
| Current citation accuracy | ID、当前路径、revision、范围与实际文本一致 | 版本变更后不引用错误位置 |
| 延迟 p50 / p95 | 冷启动、热检索、证据读取、到首个证据、完整答案分开 | 避免只报最有利的内部函数计时 |
| IO 与索引工作量 | 全库 stat 数、打开文件数、读字节、解析文档数、增量队列长度 | 找到与库规模线性增长的实际开销 |
| token 与模型调用 | 输入、缓存输入、输出、工具返回、扩写、重排、验证分别统计 | 本地模型也有耗时；缓存 token 仍占上下文 |
| 有效知识复用 | 对事先标注“已有可用知识”的新问法，统计找到并正确使用已有材料的比例；概念页与原文可分组 | 不把新增页面数、点击次数或更多摘要当作知识增长 |
| 主体归属错误 | 用户、外部作者、批注作者、整理者和模型推断之间的错误归属，逐个实质断言记录 | 研究资料和第一人称转述不能污染个人信息 |
| 人工改正成本 | 每篇整理的语义改正项、格式改正项与人工时间分别记录，保留受影响 revision | token 省了但人工返工增加，不能宣布净收益 |
| 写入触发与重复发布 | 讨论/只读任务的非预期写入数；明确写任务的正确目标、发布次数和重复主文数 | 查询可复用知识，保存必须符合实际用户意图与任务范围 |
| 修改传播成本 | 改一处来源或用户判断后，必要修正是否可找到；无关文档重写数、重做模型调用数 | 不让一次改正触发全库重新生成；关联提示不等于自动覆盖 |

“有效知识复用”只统计本轮确实有材料支持的任务；用户新想法没有现存依据时，不因没复用旧文而扣分。对 Concept 的价值，可用少量后续问法比较“已有原文”和“原文加这篇 Concept”；检查帮助定位/解释的价值与新增维护成本，不要求所有概念都完成对照。计数基于具体支持关系，避免用引用数或 `generated` 次数替代复用质量。

必须测真实 HTTP/MCP 或实际 agent 工具入口，并与复用 store 的内部计时分开。冷热测试固定模型是否驻留、索引是否已建、连接是否已建；生产 WSL/文件系统与本次 scratch 不可混报。记录每个请求的 trace，但不给普通用户答案附上冗长工具流水账。

token 对照固定答案任务与必要证据范围；只缩短输出不能算检索省 token。还要确认 compact 卡片、重复工具 schema、多层 prompt 注入和跨 agent handoff 是否反复携带同一内容。若问题答案没有证据，零 token 的错误结果不会优于正确检索。

长上下文研究说明需要评估模型如何使用多段材料；它并不证明所有新模型在相同位置都会失败。本项目减少无关上下文主要是明确的成本目标与可测工程决策。[Lost in the Middle][lost-middle]

### 7.1 可选的 prompt 语言对照

默认使用便于维护的中文语义/写作规则，保留英文 schema、工具名和技术术语，不重复整套双语指令。需要判断质量或成本时，再做 Q40 的 18 次初次执行。当前没有直接对应 Codex/gpt-6.1-sol、这些任务和这套工具的中英对照，不能先认定英文更好。

NAACL 2025 的翻译研究说明收益依模型和任务而变；它比较的是任务/查询翻译等策略，不等价于单独替换本应用 system 指令语言。tokenizer 研究说明等义文本在不同编码下长度不同，不能据此给当前中英 prompt 设固定倍率。[翻译原始论文][translation-paper]、[tokenizer 原始论文][tokenizer-paper]

比较版本应保持规则意义、例子数量、任务范围、实际模型与语料 revision 相同，随机顺序、新会话；固定中文目标输出和原文。确定性规则由程序查，主体与条件由盲评 rubric 查。记录 usage 中的输入/缓存/输出与失败重试；只有估算时注明编码和省略的消息/schema 开销。先减少重复注入，再比较语言；没有明确收益就保留可维护版本。[官方 token 说明][openai-tokens]、[prompt 文档][openai-prompts]、[评估实践][openai-evals]

## 8. 分阶段验收门槛

### P0：可观察契约与正确性

- 精确定位 gold 全部通过；重名不误选；Q01/Q02/Q19/Q21 的主体和证据边界全部通过。
- 每次实际引用都能打开当前文件的实际范围；删除、移动、冲突和不可访问状态不冒充正常空库。
- 同一文档与同源副本不计为多份独立证据；旧 full 客户端保持可用。
- 日志能分辨 scope、intent、索引状态、候选与读取成本。以上是明确契约，不能以平均检索分数掩盖失败。

### P1：现有词法后端与热路径优化

- B/C 相对 A 不降低已存在的中文、混合术语、跨章节覆盖与精确查找能力。
- 未变化库的热 lookup/read 不再全库遍历；读取量随返回文档和片段规模变化。
- 核心维护接口保存一篇文章后，只更新受影响文档；外部文件编辑由增量观察和补偿扫描发现。索引可短暂落后，但最终证据通过当前文件读取纠正。Sapphire 的同等保存链路在 V2-05 后续验收，不阻塞核心放行。
- **Proposed，需在指定用户硬件上确认：** 热 lookup 工具路径 p95 可先以 100 ms 内为目标；1,000 文档的普通词法候选查询 p95 先以 250 ms 内为目标。不得以静默漏结果换取达标。实际硬件记录后再决定是否调整预算。
- **Proposed：** 在相同问题与证据质量下，compact 相对现有 full 的候选工具返回 token 中位数降低至少 30%；证据支持率和 Recall 不下降。它是待测目标，不是本次已经达到的收益。

### P2：宽泛覆盖与摘要膨胀

- Q13/Q14/Q18/Q23/Q24 通过；增加 20 份同源摘要后，原稿和其他相关方向仍进入预定候选范围。
- 1,000 份无关摘要作为后续规模探针，单独报告质量、延迟与 token，不作为首批六篇整理的前置条件；如失败，先定位是否元数据角色、范围、词法 query 分组或选择器问题。
- 不强制新建主题页；已有导航可用，过期导航不排除正文相关的其他资料。回答的“全部”必须有完整枚举或明确覆盖依据。

### P3：条件触发的语义/重排试验

只有在本地确有目标证据、正确 scope 与角色过滤已生效、可靠名称/别名仍不能解决，并出现可复现的同义表达漏召回时，才进入小规模语义适配器试验。库达到某个文件数并不是单独的升级理由。

至少收集数个真实失败问法及保留的改写问法；比较词法、词法+语义、再加重排。候选方案应补回实际漏例，并保持精确定位、来源归并与当前证据不退化。重排只作用于有实际收益的 question/compare，不默认加到每个 lookup。任何“提升百分比”均待实测。

### P4：V2-06 核心试点与 V2-08 分批迁移

P0–P2 的相关核心行为结合约 6 篇试点材料验收；无需为启动迁移先跑完 10,000 文档扩容、可选语义、语言或应用实验。试点清单为 Me、三篇真实文章、Vidu 和 models runtime 报告，详见[迁移方案](local-shared-wiki-migration-v2.md)。文件是否可搜索、是否按模板整理、是否有成熟综合分别记录。

- 当前模板化正文措辞、后续定点维护的思想与表达保全、出处不造假、Me 边界、当前 revision 和恢复合同通过；明确纠正的字句准确变化，未涉及内容保持。这里只指试点明确用例，不宣称任意未来文章已有 100% 可靠性。
- Q34/Q39 验证读写触发、冲突、继续与单篇恢复；实际维护由已实现的工具完成，不能靠修改 prompt 宣称新能力已生效。
- 现有 MD 的 Key note 提取与 `/wiki` 维护由实际绑定的 Weber worker 完成：记录真实 agent/session、读取覆盖、job、写入与索引回执，核对其使用本轮配置和指南。至少一篇旧 MD 通过此链路原位模板化并可在后续问题中使用；通用 Codex CLI 成功、脚本摘要或开发 agent 代写不计为 Weber 协同通过。批量开始条件见[迁移放行](local-shared-wiki-migration-v2.md#31-真实-weber-链路与模板化放行)。
- 新能力按[定点维护](local-shared-wiki-maintenance-v2.md)验收：新页、旧文与人工编辑过的页面均可从最新版本局部纠错/补充；未涉及字句和来源保持，原字句不匹配、越范围或读后再变化准确拒绝，不按作者或 ownership 拒绝。Q56 的实际复核与已符合任务的 no-change 均有真实阅读和持久回执。
- 多次维护同一文章，验证核心思想、带风格的观点、理由、反例和关键条件仍存在，局部纠错未扩成整段润色。模板化保持当前 pika_vault 正文措辞；明确被纠正的位置允许实际变化，不能把整篇字节不变当未来维护的通过条件。原始/提取坐标、BOM/CRLF/emoji/重复句和锚点影响单独验证。
- Q58 的真实知识价值门槛：至少围绕一个真实、值得复用的研究问题形成知识页，用后续不同问法验证复用，并完成一次明确纠正。实际工具调用、当前产物和回答须有证据；合成 Concept 或只断言接口字段存在不替代该闭环，不要求六篇原文逐篇派生 Concept。
- 记录每篇的处理成本和人工改正量，长短材料分组；发生实质性归属、原文或作用范围错误时停下剩余项修正。单纯风格差异记录为后续优化，不要求先统一全部 persona。
- V2-08 第一批建议 5–10 篇并按输入长度分组，以试点观察决定后续批量；复用现有任务/history 记录完成项，不重跑全部成功文件。Concept/Topic 只在有用途时创建，Synthesis 不自动核验。
- V2-08 最终覆盖当前 Library 下所有 Markdown，以全量文件清单与任务/检索结果对账；每篇有整理或真实 no_change 回执、当前索引、精确定位及当前内容读取证据，领域内容有内容检索结果。pika_vault 优先不缩小最终范围，Me/Research 等按真实类型整理；未处理、冲突、失败或无法检索项未解决时不能宣称全量完成。
- 核心通过后可以迁移；18 次语言对照、V2-05 和 V2-09 均不是其放行条件。

### P5：V2-05 / V2-09 后续应用验收

标签场景 Q35/Q36 在共享标签 API 和 Sapphire 过滤实际实现后运行，核对当前 scope、any/all、文档计数、分页和变更结果。SmartReader 场景 Q37/Q38 在对应后续功能实现后运行，核对稳定文档引用、原文/批注归属、重复 capture 和当前版本。应用失败不能静默切到另一套不等价知识索引；但尚未开展应用开发不阻碍核心试点和首批资料整理。

完整来源根闭包、深层传播和自动独立证据计数按总纲 §10 留作实际缺口触发项，不因未实施这些功能判定核心失败。

## 9. QMD 的可选采用边界与已核实接口

当前 Octopus 没有 QMD 依赖或调用。本轮默认增强现有 SQLite/jieba/bigram。QMD 是后续可选后端，不是当前系统已接入的能力。

本次固定读了 QMD `v2.8.3` 的 README 与源码，并核对 2026-10-12 的 main changelog。main 的 metadata/filter/discovery 仍列在 `Unreleased`；不能以 main README 宣称任意安装版本都支持。[QMD 固定版本][qmd-release]、[变更记录][qmd-changelog]

| 需求 | 已核实的接口/行为 | 适配注意 |
| --- | --- | --- |
| 无模型关键词检索 | CLI `qmd search`；SDK `searchLex` | 当前中文方案仍须用本库评估；不是天然比现有 jieba 更好 |
| 控制检索分支 | MCP `query` 的 `searches`；REST `POST /query` 的 `searches` | 结构为 `{type: lex/vec/hyde, query: ...}`；过滤 collection 用复数 `collections` |
| 禁止自动扩写 | typed `searches`；或 SDK 直接 `searchVector` | v2.8.3 CLI `vsearch` 源码会调用 expandQuery，不能把它当作一次 embedding 的最便宜路径 |
| 重排开关 | `rerank: false`；`candidateLimit` 限候选 | QMD 的 relevance score 不是事实正确率；lookup 不应绕到模型分支 |
| 常驻模型 | `qmd mcp --http`；SDK 常驻 store | 避免每次命令重新装载模型；启动/设备失败时保留词法降级 |
| 取正文 | `get` / `multi_get` 支持限量、行号 | v2.8.3 从索引内容表读取，不代替 WikiService 的当前文件证据读取 |
| OKF 元数据 | main 新增过滤只识别 `qmd.metadata` | OKF `uid/type/status/tags` 不能假设自动成为该后端 filter；元数据与身份权威仍在 WikiService |

v2.8.3 的 MCP `query` 源码还支持与 `searches` 互斥的纯文本 `query`，但其 REST 接口要求 `searches`；README 参数表存在滞后。适配器选 typed `searches` 这个明确公约数，并对所固定版本做契约测试，不能把 CLI、MCP、REST、SDK 参数混用。[MCP/HTTP 源码][qmd-mcp]、[检索源码][qmd-store]

QMD 已发布源码含 CJK 字符间隔规范化与短语匹配，不能继续引用早期 issue 断言它完全不能搜中文。也不能据此保证自然中文问句的召回质量。嵌入模型、维度、文本格式与 chunk 版本进入 fingerprint；换模型或改变语义输入时重建受影响向量。[QMD 固定源码][qmd-store]

若接入语义检索，优先只给正文片段附上文档标题、章节路径和确有依据的短范围说明。需要验证“失去上下文”造成的漏召回后，才尝试为片段生成额外 contextual text；不要给每个 chunk 先制造一份长期 AI 小总结。[Contextual Retrieval][contextual]

融合职责二选一：要么 WikiService 融合现有 lexical 和语义候选；要么 QMD 完整负责它自己的 hybrid。避免先双重扩写、再重复融合、再两次重排。来源归并、业务 scope、当前文件读取与引用定位始终归 WikiService。

## 10. 执行顺序、交付与暂缓项

先固定真实语料与原 30 条 rubric，补入口 trace；新增 Q31–Q40 随阶段落实。实际任务顺序为 **V2-01 → V2-02 → V2-03 → V2-04 → V2-06 → V2-08**，V2-06 只依赖 01–04 的核心链路；V2-05 Sapphire、V2-09 SmartReader 后续实施，V2-07 由真实缺口触发。P0/P1/P2 是质量与性能维度，P3 是可选实验，P4/P5 是试点和应用放行说明，编号不表示必须先完成语义后端才能迁移。

每阶段输出相同格式的结果表：已通过、失败样例、具体原因、输入/缓存/输出 token、冷热时间、IO、复用与人工改正量、实际版本。标明接口已实现还是 proposed、资料来自实际库还是注入 fixture、使用真实工具还是固定回放。无需把私人正文或完整 agent 对话上传到公开仓库。

本轮不宣称已跑完 30 条，不宣称线上答案质量或 QMD 性能已验证，不因引用过某篇论文就预设其技术适合当前小库。无必要的多 agent 逐题复核、固定庞大主题树、每段 QA 生成、独立图数据库、全库全文注入与无条件向量重排均暂缓。真实缺口触发后再评估成本和收益。
