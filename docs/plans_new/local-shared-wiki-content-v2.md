## 1. 目标与当前基线

目标是让日常入库后的文章既便于阅读，也能被准确定位、按需展开和追溯。小库先解决内容角色、文档身份、来源和当前版本；规模扩大后沿用同一契约，不依赖全库总结。

设计附件的真实主副本是 `applications/sapphire.data/vaults/obv/repo`。当时 Library 有 133 个文件，其中 37 份 Markdown、9 份 HTML、3 份 PDF、43 份 TXT；按当时默认候选排除规则保留 42 份 Library 文本，即 35 MD + 7 HTML。整个 Vault 另有 421 份 Codex Skills 文件。这些是静态附件盘点，不是当前生产数量或最终整理范围；当前用户要求 Library 全部 Markdown，含已有资产 Markdown，见[当前 spec](local-shared-wiki-spec-v2.md)。

附件内只看到文章模板已填写完整 OKF 字段；三篇示例原文仍主要只有 tags，Vidu 报告和 Me 资料没有 frontmatter。附件没有 Wiki 的 config/index 数据，不能据此确认在线绑定、ownership 或索引状态。本方案从 **旧内容仍可搜、新整理内容符合模板** 的兼容状态开始。

### 成功后的典型行为

| 用户问题 | 应发生的内容选择 |
| --- | --- |
| “我的专业是什么？” | 定位 Library/Me 的当前相关字段；短资料一次读全 |
| “我的职业是什么？” | 当前资料未记载时明确说明，不能用学籍替代职业 |
| “Vidu S2 的 SRF 是完整长程反向传播吗？” | 定位 Vidu 技术报告第 4.3 节，读取具体条件与理由 |
| “我有哪些数字人研究资料？” | 先覆盖视频蒸馏、单目 Rig 等已有方向，再选择代表材料 |
| “给我文章入库模板” | 返回 Template 文档；它不参与普通数字人事实的优先召回 |

## 2. OKF 是交换底座，article-v1 是本地文章约定

采用此前核对的 [OKF v0.2 固定版本规范](https://github.com/GoogleCloudPlatform/open-knowledge-format/blob/ad30107c31c06aec8a7d5636e0d1058118604e6f/SPEC.md)。OKF 的 type 可由生产者自定；title、description、sources、generated 等使用原生格式。uid、aliases、x_wiki 以及下述正文小节是本地扩展与约定。

### article-v1 保持原有形态

```yaml
type: Reference
title: 文章显示标题
description: 一句话说明文章的问题、讨论范围与观点属性。
tags:
  - 具体主题
sources: []
generated:
  by: Weber/实际运行版本
  at: "实际整理时间，完整 ISO 8601 datetime"
status: stable
uid: "首次分配的 urn:uuid；后续更新保留"
aliases: []
x_wiki:
  profile: article-v1
  body_dialect: obsidian
```

以上是字段示意，写入时必须替换示例值；没有事实依据的作者、日期、verified 等不填。sources 是选填出处，当前文章可以省略或为空，不为凑字段保存副本或寻找未知作者。以后总结外部文章可记录实际题名/URL，综合库内材料可链接实际使用的文章。generated 记录整理生成行为，不能由它推断整篇正文都是 AI 创作，也不能把它当作原文发表时间。stable 表示可使用，与是否记录过内容核验分开。

### 正文分区

```markdown
# 文章标题

## Key note
保留或生成的阅读要点；有必要且实际有来源时再加入脚注。

## 正文
保留来源正文、条件、反例、公式、表格、代码与资源。

## 相关笔记
少量有具体关系的链接和解释；没有则省略。

## 整理说明
记录实际发生的整理动作；没有必要则省略。

```

description 负责一句话选文，Key note 负责快速理解，正文承担详细论据。同一篇的这三层不成为三份独立证据。

有实际来源且需要脚注时，`sources[].id` 与正文脚注使用相同标签；没有出处的现有文章不保留空脚注或占位路径。历史模板中 `references/*.md.txt` 是旧三篇资料交付包的保存方式，按 Q54 不作为当前模板的必要部分。模板文件自身的旧字段、固定要点数量和小节安排同样只作参考，按文章用途和最新合同调整。

article-v1 是来源文章的整理约定，适用于这次讨论的三篇参考文章。PersonalRecord、Concept、Topic 与 Synthesis 继续共用 OKF 身份/来源机制，但正文围绕自身用途组织，不强行套成“外部原文+Key note”，也不发明尚未定义的新 profile 名称来假装已经兼容。

已有正文的 H1/H2、Obsidian block ID、标题锚点与媒体相对路径需要保持可解析。旧文章只补元数据时不强制重排；明确做 article-v1 格式迁移时，再选择包裹或调整标题的可追踪操作。不能一边声称逐字保留，一边无记录地改变标题文字或相对路径。

## 3. 统一 doc_role，避免 AI 摘要淹没检索

doc_role 是服务端对公开 type 的归一化投影，便于索引、prompt 及后续 App 客户端一致理解文档用途。它不应成为另一份与 YAML type 竞争的人工字段。OKF 没有以下强制枚举；这是本项目的本地类型表。

| 公开 type 示例 | doc_role | 默认用途 |
| --- | --- | --- |
| Reference | reference | 保留来源正文的参考文章 |
| Source | source | 可直接回查的原始资料/记录 |
| Synthesis | synthesis | 多源研究综合、解释或对比 |
| Concept | concept | 有独立说明价值的概念页 |
| Topic / Navigation | navigation | 主题入口与阅读地图 |
| PersonalRecord | personal | 明确主体的个人资料 |
| Template | template | 格式与操作示例 |
| 无 type / 未映射值 | unknown | 保持可检索，不能凭标题猜作者或证据地位 |

实现应保留原始 type 和未知扩展字段。历史 `kind=original/source/concept/topic` 是兼容输入，不是新的权威分类；无法无损映射时返回 unknown 和兼容来源。

几个必要区别：

- **generated ≠ synthesis。** 原文加 AI Key note 仍可为 Reference；正文主要是综合解释时才选择 Synthesis。
- **doc_role ≠ 真伪评分。** Source 也可能错误，Synthesis 也可能准确。引用依据仍是当前实际读到的内容。
- **目录 ≠ 主体认证。** Library/Me 是个人查询优先范围；外部文章第一人称不能因相关或被收藏而变成个人事实。
- **模板 ≠ 领域知识。** 模板中的 Vidu 示例路径帮助说明格式，默认不应挤占真实 Vidu 报告的领域召回。
- **导航 ≠ 已读来源。** 导航写“已读某论文”不能让这次回答省略原文读取。

新字段投影先以可重建的 registry 形式建立；迁移时只更新本次明确范围。当前没有 type 的文章继续可查，不能要求先人工标完所有旧文才开放搜索。

### 标签是检索维度，进度是另一回事

tags 描述文章实际覆盖的问题、对象或方法。保留少量能区分内容的标签，必要时保留准确英文术语；不为每篇补齐一套庞大标签树，不自动把“数字人”与所有视频生成方法视为同义词。Sapphire 的后续筛选使用共同 tags/tag_match 契约，而非每个 app 再解析和猜一遍。

“已索引”“已整理”“已形成长期知识”是不同工作进度，不是 doc_role 或 OKF status 的替代枚举。一份 Reference 不需要另生 Concept 才算整理完成。SmartReader 的浏览器材料、app 草稿也不能仅因能阅读就被计为已入 Wiki；真实入库回执才建立主库身份。

## 4. 区分五种身份，UID 不产生权限

| 身份 | 定义 | 用途与边界 |
| --- | --- | --- |
| OKF Concept ID | 包内相对路径去掉 .md | 标准交换身份，随路径变化 |
| uid | 文档中的本地稳定身份声明 | 改名/移动时保留，需与 registry 映射 |
| document.id | 当前 WikiStore 的内部身份 | 维持已有接口、历史和运行态引用 |
| sources[].id | 文档内来源脚注标签 | 连接 `[^source-id]`，不是全局资源身份 |
| revision | 当前内容版本 | 校验读取坐标、写入前提与缓存有效性 |

uid 不授予读写权限。新文件复制同一个 uid、旧路径被替换、手工构造来源字段，都不能继承原文的 task grant、read receipt 或 ownership。重复 uid 应返回身份冲突或歧义，不自动合并成同一受管文档。

推荐兼容顺序：

1. 保留现有 document.id，不重置运行态历史。
2. 解析已存在的 uid，并建立冲突检测。
3. 对明确整理或迁移的文档分配/补齐 uid。
4. 经已确认的移动/改名维护 uid ↔ 当前路径映射。
5. 内容哈希用于版本和重复线索，不单独决定两个文件的作者身份、授权或是否应覆盖。

最终回答引用当前读取结果的文档与位置。旧索引坐标失效时重新定位；不能用 uid 相同为理由，把旧段落坐标直接套到新版本。

## 5. 文章来源、直接依据与重复内容

按 Q57，本期来源服务三个实际用途：记录文章或总结依据的出处，回查相关材料，以及在已知依据变化时提示直接依赖内容。sources 选填；当前文章未记录出处可以正常整理和使用，不要求逐篇回溯补齐。

| 记录或关系 | 本期含义 | 使用边界 |
| --- | --- | --- |
| 文章来源 | 实际题名、URL 或库内文章位置 | 是出处，不自动证明每条观点正确或本轮已读 |
| 直接总结依据 | 本次确实用于形成总结、解释的材料 | 便于回查与变更提醒，不把所有引用都当重复内容 |
| 已确认重复表示 | 同一材料的展示版、导出或纯重复摘要 | 归并重复候选，保留必要资源与不同版本 |
| 普通相关链接 | 问题、方法或观点之间的具体关联 | 用于导航，不触发证据依赖失效 |

程序可登记自身入库和维护中确知的直接关系；其他来源声明保留原意，不猜深层谱系。同标题、同 URL、同网站或共享参考文献只提供线索，不自动合并不同文章。

同一正文、Key note 和展示副本不成为多份独立支持；明确来自同一材料的重复总结不占满候选。综合 A、B 的报告不会把 A、B 合成同一作品，也不自动成为第三份独立实证；有独立分析价值的综合继续可检索。本文不要求自动计算全文 root_source_ids 或每句结论的独立证据数。

有明确资源标识但正文未读、资源不可用和版本未知分别如实表示，不把它们都写成无出处。回答仍引用实际读到的位置、区分转述与原始资料；程序索引和公开来源声明都不产生事实核验状态。

完整来源根闭包、深层传播与自动证据计数属于 §10 的条件项。可移植 Markdown 只保留实际出处和必要链接，索引及历史保存运行态版本和直接依赖记录。

## 6. 原稿快照、摘要与 AI 综合的更新规则

### 原稿快照

按 Q54，原位模板化后的文件就是正式入库文章，不默认另存 `.source.md.txt`，旧输入无需作为第二份永久原稿维护。实际改动仍沿用有限文本历史，恢复记录不作为默认知识候选。

旧 article-v1 三篇资料包里的 `references/*.md.txt` 原为保留输入字节、避免被 OKF 当作普通 .md 概念的附件。若确实导入了此类已有副本，按实际关系登记并退出重复候选，需要追溯时仍可读取；本轮未在当前主库找到此类文件。不能把用户所有 TXT 或名为 references 的目录整体排除，普通独立参考资料仍应可查。

### 摘要更新

- 生成 Key note 时读取原文正文及明确来源，不以旧摘要、相关区和整理日志再生成摘要。
- 已有准确摘要复用；任何作者写下的有价值要点、观点和风格表达均保留，确有错误或缺口时定点修正、补充，不因归属重新生成整份摘要。
- 原文小修改后更新词法索引、正文坐标和 revision；不自动调用 LLM 重做 Key note。
- 原文实质变化可使摘要标记需要检查，但检查队列与实际改写分别管理。
- 只传播失效/待检查状态到依赖综合，不递归重写整张关系图。
- 普通问答默认不入库；明确要求沉淀且既有专题属于本次可写范围时，优先更新该专题。否则只在本次范围内创建有新用途的记录，既有专题仍作为只读来源。

### 研究综合

Vidu 报告这类综合有独立价值：能解释方法差异与测量边界。它可以参与召回并被引用为“这份报告的判断”，但不能用它替代所有被链接论文的原文证据。阅读或比较要区分作者报告、整理者推导、用户实验与本次推断。

当前、适用且来源范围清楚的 Concept/Topic/Synthesis 可以直接复用其概念说明或已有综合。精确数字、原话、争议、条件缺口及影响结论的依赖变化，再展开对应 Reference。不要要求每问从头读完所有原文，也不要为了减少阅读而把过期综合自动当当前事实。

### 选择值得长期留下的内容

日常阅读先允许讨论和草稿停留在会话/SmartReader；用户明确选择保存后，再按目的形成 Reference、用户笔记或综合。问题、分歧和研究假设可以先放在已有专题内部；有独立用途时才拆页。引用链、更新理由和未解决条件应随真实内容保留，而不是机械增加新文件数。详见[知识积累方案](local-shared-wiki-knowledge-v2.md)。

## 7. Parser、Registry、检索与 UI 的共同消费契约

| 组件 | 应读取/产出 | 不能自行另立的语义 |
| --- | --- | --- |
| Parser | YAML + Markdown/Obsidian AST；真实标题、分区、脚注与链接 | 不把代码块中的示例标题当正文层级 |
| Registry | uid/内部 id/路径映射、doc_role、来源与展示关系 | 不凭目录或 generated 推断作者身份 |
| 索引器 | 文档级预览 + 正文段落；内容角色/直接来源关系 | 不把摘要、原文、HTML 三份都计为独立证据 |
| 查询服务 | 按 intent 选择粒度；返回当前可定位的候选 | 不用排名认证事实正确 |
| Weber | 阅读与综合；按模板整理指定内容 | 不在 prompt 中重做全库身份和来源推断 |
| SmartReader（后续 App） | 阅读材料、选区讨论、草稿与明确入库，后续映射主库 id/revision | 浏览器 UUID、DOM range 与草稿不得冒充 Wiki 身份、坐标和当前正文 |
| Sapphire（后续 App） | 库浏览、标签/搜索、来源与版本展示、普通编辑 | 不维护与 /wiki 不同的标题/别名/链接解析规则 |

设计基线仅消费 YAML tags/aliases 和旧 octopus-wiki/octopus-section 注释；v2 已实现统一 OKF 解析和兼容适配供核心组件消费。读写 revision、任务范围与历史继续保留；旧 owned-region 记录作兼容和恢复信息，不决定正文编辑资格。应用新功能仍按对应 feature plan 接入。

### 当前和拟议接口

现有 search/read/info/list_documents/graph/maintain/organize/publish 保留。以下查询增强已实现：

- `search(intent="lookup"|"question"|"overview"|"compare", view="compact")`。
- 旧调用省略 view 时保持兼容 full。
- `read_many(items=[{doc,start,length,expected_revision}], budget_chars=...)`，在总响应预算内批量读明确位置。

内容格式与这些接口协同：compact 返回 title、description、doc_role、命中位置和必要来源状态；实际出处与已知直接依赖按需提供详情，不能把综合使用的多份资料压成单一作品。read/read_many 返回当前正文与准确 revision。新增能力必须通过任务卡 capabilities 和真实 tool schema 声明，未上线时继续使用既有工具。

### 写入端的统一适配

v2 写入接口已提供可选 `frontmatter_patch`，允许 `title`、`description`、`type` 及明确支持的 `x_wiki.profile` / `x_wiki.body_dialect`；原有 tags、aliases 参数继续作为唯一输入，不在 patch 中双写。服务端校验 profile 与实际正文结构一致，再原子更新获准元数据与内容。新版 organize 显式传该参数选择保全路径，能力以运行时 capabilities 和真实 schema 为准。

uid 由服务端分配或保持，generated 由实际执行身份和整理时刻生成；模型不能通过 patch 设置 verified、改写 uid 或提升核验状态。既有未知字段与真实核验记录按保全规则保留。提供文章来源时，服务端适配实际资源及来源标签与脚注；运行态输入身份、revision 和阅读记录用于机械一致性，不强制全部写成公开 sources，也不因既有文章未填出处拒绝模板化。这里的校验不等于事实核验。

保留两种来源对象的区别：当前工具 `sources` 使用 `{doc, revision, location}` 表达运行态来源定位；OKF 文件使用 `{id, resource, ...}` 表达可移植来源与脚注标签。不能把 `sources.resource` 直接传给当前工具，相关链接也不自动编译成支持来源。该适配不扩大可写范围，不将 publish 改为已有页面整页替换；已有内容按下述定点维护合同处理，旧工具保留兼容。

既有工具还包括 `blocks/restructure`。获准旧页的纯追加先完整读取当前目标并满足 read ledger，再保留全部原块及原顺序，插入新的研究问题、解释或更正段；publish 只建新页。旧生成区和私有来源注释保持兼容，新版受控写入共用元数据/来源适配与持久回执；正常维护不是删除旧生成区后整篇重建。

### 正文的定点维护

Q60 最终取消以 AI／人类作者、人工编辑历史或可信生成区作为正文编辑门槛。v2 已提供独立的局部纠错与补充协议，不靠原 organize 生成区重建、人类全文保存或 publish 整页覆盖替代。

V2-02 已实现 revise，绑定真实任务、文档身份、当前 revision 和已读取的原始位置，接受具体纠错或插入补丁；服务端保留未选中字节，核对实际原字句、范围及读取覆盖。read/search 的提取坐标不直接用于原文件写入，BOM、CRLF、HTML 和 Unicode 映射需按实际用例验证。历史人工编辑不是冲突，读取之后再次改变才是并发冲突。

旧 ownership 记录保留必要历史信息，涉及本次修改时更新或撤销过期定位，不作为拒绝维护的理由。现有 organize 的 original_text 生成区清理不能进入新修订路线，也不能顺带删改未请求处理的正文、Key note、标签、关联或来源。正文作者类别不影响规则；思想、观点、反例、判断条件和风格表达的保全由实际差异、自检、冷读和内容验收共同验证。

来源重读后原解释仍适用时，只更新实际检查过的直接依赖复核记录，不为解除提示改字，也不认证未检查部分。内容已经符合本次任务时允许真实 no-change 回执。新建、追加、纠错、复核和无变化结果均进入持久任务产物记录及恢复；索引故障不导致重复正文生成。

完整参数、原始位置、历史兼容与验收见[定点维护合同](local-shared-wiki-maintenance-v2.md)。它替代未实现的 region_updates 方案。正常维护不重新生成既有正文；明确事实错误定点纠正，既有观点与引文遇新证据时保留语境、补充说明，不擅自换立场。

## 8. 旧库渐进迁移

执行顺序以[迁移计划](local-shared-wiki-migration-v2.md)为准：V2-01～04 核心→V2-06 约 6 份试点→V2-08 可恢复批次。后续 SmartReader/Sapphire UI 和英文 prompt 对照不是迁移前置要求。先区分 Vault 中可搜但未规范的旧文、库外待采集原材料、重复展示/草稿；不要都视为“还没入库”而重新创建一遍。

### 第一阶段：只修消费端

实现原生字段解析、doc_role 投影、脚注/来源与快照识别，保留 legacy 原文。检查重复 uid、已知展示副本、模板和导航角色。已有文章无需全部重新生成摘要。

### 第二阶段：用少量真实文章走通

先选择已给出的三篇文章，以及 Vidu 技术报告、Me 的小文件进行独立明确任务验证。前三篇采用既定模板；Vidu 不需要为了格式把所有论据压成几条 Key note；Me 不需要被强塞进外部文章 Reference 模板。

可加入 MetaHuman runtime 报告形成约 6 份代表试点，覆盖不同长度、文体和中英术语。先稳定实际工具、来源、原文和有限写入行为；persona 的风格措辞可以在试点中继续调整，不等待“最终完美 prompt”。结构或内容错误只重做受影响项目，风格变化不自动触发全库重新生成。

### 第三阶段：当前 Library 全量迁移

新入库的来源文章默认 article-v1，其他类型按自身用途组织；用户已明确选定当前 Library 全部 Markdown，pika_vault 优先，包含已有 assets Markdown。Octo 落成具体批次清单，Weber 经受控任务整理或真实 no_change，逐篇验证当前检索；资产角色保持并用显式范围/include_assets 检查。人工普通编辑不自动触发再次入库，原始正文与媒体继续由当前库持有。

根 `知识库导航.md` 当前有失效链接与历史 generated_by 字段，应作为导航维护任务单独处理，不能在一次文章入库中顺手改全库。对缺失目标保留状态，不能生成虚构页面来让链接检查变绿。

### 后续规模扩大

先按重复率、实际主题覆盖、长文局部命中和 token 指标判断瓶颈，再引入向量/重排能力。无需每收一篇就生成 concept/topic 多份派生页。若采用语义层，仍保留精确标题、别名、路径及正文证据通道。

## 9. 验收要求

验收以实际内容结果为准，包含以下最小场景：

1. article-v1 的 description、type、sources 与 uid 被 API 正确消费；两个 app 启用对应功能后使用相同语义，UI 尚未实现不阻塞核心试点。
2. 未迁移的 Me / Vidu 文件仍可正常定位，无需人工先补 YAML。
3. 已确认同文 MD/HTML、来源副本、Key note 不放大重复支持；不同文章不因共同被引用而合并，不要求自动完整来源根。
4. Template 在领域事实查询中不压过真实报告；显式模板查询仍命中。
5. 原文更新后旧坐标不可直接用于当前引用；普通编辑不自动生成新摘要。
6. 整篇总结可分批读完整文档；局部问题只读足够的章节。
7. 外部参考文章第一人称不写入 Me；缺失个人字段不被其他身份替代。
8. 原生字段、未知 YAML、既有公式、代码、块锚点、媒体与链接按实际整理范围保留。
9. 重复 uid 或替换路径不会继承写权限与读票据。
10. 格式检查不产生 verified；来源可追踪不等于事实已经独立核验。

预算是起步/分批建议，不是“只准读三篇”或“整篇最多几千字”的硬上限。
