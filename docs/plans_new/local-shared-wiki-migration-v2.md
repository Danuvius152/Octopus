## 1. 决策：先让小样本闭环工作，再逐批整理

**现有库的批量模板化从 V2-06 的真实 Weber 试点通过后开始。** V2-01～03 完成内容解析、范围、当前版本读写、恢复及检索工具；V2-04 接通既有 Weber 的配置、维护/写作指南和真实工具，再在 V2-06 的约 6 份代表材料上验证，Vera 检查内容保全和检索结果；通过后 V2-08 分批整理剩余获准文章。Sapphire/SmartReader 新功能、可选语义后端与 prompt 语言对照不成为前置条件。

**当前用户确认的完整范围：** 主库 `Library/` 下所有 Markdown（递归枚举 `.md`，兼容大小写后缀）均纳入整理、入库和检索验证，pika_vault 优先，随后覆盖 Me、Research、课程笔记、导航、模板和其余目录。Octo 建立全量清单并将每批明确到文件；既有 Weber 判断实际类型与整理动作，现有 Vera 参与试点前验收讨论、试点放行、批次抽查和最终全量覆盖核对。已符合要求的文件完整复核后记录 no_change，也验证当前索引与检索。没有新文本产出不构成遗漏；未处理、冲突、失败或尚不可检索的文件不计为完成。

这一顺序同时解决两个问题：只有 prompt 草稿而没有真实产物，很难知道它是否有效；在读写和来源约定尚未确定时批量生成摘要，又会留下大量需要返工的内容。试点要验证一条真实链路：当前材料 → 正确分类 → 有限整理 → 发布回执 → 当前索引 → 日常问题读到依据。索引接入和整理产物分别验收，不用一次“任务成功”代替全部状态。

Q54/Q59 确认当前 pika_vault 以旧模板为参考、按最新需求原位规范化，保持正文措辞，不另存永久原稿或强制补齐出处。Q60 未来维护保护思想、论证和风格表达，允许局部纠错与补充，不按作者类别或过去人工编辑限制资格，不重新生成正文；合同见[定点维护](local-shared-wiki-maintenance-v2.md)。Q58 要求试点至少一个真实问题的知识建立→不同问法复用→明确纠正，隔离 fixture 只补机械验证。

任务编号保持既有约定，实际顺序为 **V2-01 → V2-02 → V2-03 → V2-04 → V2-06 → V2-08**。V2-06 是核心端到端与约 6 篇试点，只依赖 01–04；V2-08 是已有和库外材料的分批迁移。V2-05 Sapphire、V2-09 SmartReader 留在后续；V2-07 语义后端只由真实词法检索缺口触发。

## 2. “未入库”先分成三类

普通 Markdown 无新模板也可索引。设计附件没有生产绑定/索引，不能由当时文件存在推断可查；本次当前核对已有 Library 42/42 索引，但实际整理及逐篇检索仍需独立验收。[历史索引入口][repo-store]、[历史检索实现][repo-search]；当前状态与执行顺序见进度页。

| 材料现状 | 首要动作 | 何时需要模型 |
| --- | --- | --- |
| **Vault 内旧文章，已可搜但未规范** | 保留已有身份与路径；先确认范围、角色和题名，再按需要补 description、Key note、来源与可靠别名 | 只有确实需要理解后整理、概括或建立有用联系时；可确定提取的字段由程序处理 |
| **库外原材料，待 capture** | 确认来源和目标位置，检查是否已有同一资源，保存可追溯的原始材料或引用，再接入索引 | 抽取内容后按实际类型整理；不要求 capture 时就生成完整知识综合 |
| **重复展示、导出副本、草稿，待分类** | 分清主文、来源快照、展示副本与未完成笔记；保留必要的来源/恢复关系 | 只有语义关系无法确定时辅助比较；不按文件名或内容相似就自动合并、删除 |

同一文章在 app 中有展示页、在 Vault 中有正文、在导入目录有原稿快照时，先确定它们的角色与关系。确认为来源快照的文件可以退出默认知识候选，但仍能从来源读取；未知文件先保留可解释的状态，不把整个 TXT 或 references 目录统一排除。

对于单份材料，还要分别记录三个事实：**已保存并可检索、已按模板整理、已经形成有用途的综合知识**。它们不是三个必须连续完成的关卡。一个只有清晰题名和正文的旧笔记可以很好地回答问题；一份格式完整的 AI 总结也可能没有足够证据。`generated` 表示处理事件，结构通过不自动产生 `verified`。

## 3. 首次整理前需要稳定的最小约定

V2-01 至 V2-04 应提供以下可用行为；这比统一所有 prompt 的措辞更关键。

1. **解析与类型兼容。** 新 OKF/article-v1、旧 managed 格式和无 YAML 笔记可以共存。Reference、个人记录、Synthesis、Concept、导航、模板和未知类型有正确投影；读取旧文不要求先全库重写。Me 是个人记录，不套外部文章的 Reference 模板。
2. **真实能力与 prompt 一致。** worker 只被要求调用已经实现并声明的工具、字段和写动作；`read_many`、`intent`、`frontmatter_patch` 等能力未上线时，使用明确的旧能力，不把草案接口写进正在运行的任务要求。
3. **有范围的、按当前版本的写入。** 对已确认的目标执行维护，检查当前 revision，保护原文和人工内容；版本冲突留给重读与差异处理，不把旧摘要覆盖到人刚改过的文件上。
4. **可检查的结果。** 每篇输出稳定身份、当前路径、发布 revision、修改概况和实际索引状态。排队、写入成功、索引待更新各自如实报告。
5. **能恢复一篇真实改动。** 用现有 history/journal 验证一次恢复，不另建完整备份系统。恢复同样校验当前版本，不能回滚掉后来的人工作品。[现有历史机制][repo-history]

约定须贯穿 parser、服务端工具 schema、worker briefing 和输出校验。语义与表达交给 prompt，范围、身份、revision、原文保全和发布事实由程序负责。将保护写成更多自然语言段落，不能替代这些已有或待补的确定性边界。

试点须验证 V2-02 的 revise 与原始位置、读取覆盖、版本、实际差异和任务回执：旧文章、生成页及人工编辑后的页面都可在本次范围局部维护，保留未涉及内容。多次维护后原思想、理由、反例与风格仍在，不要求整库补 ownership 或鉴别作者。

来源实际重读后解释仍适用时，仅更新已检查直接依赖记录；已有内容符合任务时可有真实 no-change 回执。恢复与索引重试不重复正文生成，详细合同见[定点维护](local-shared-wiki-maintenance-v2.md)。

### 3.1 真实 Weber 链路与模板化放行

现有 MD 的 Key note 提取、已有摘要复用判断、必要关联和 `/wiki` 维护均由既有 Weber agent 执行。维护入口提交持久任务，服务端将指定目标分配给当前绑定的 Weber worker；程序负责格式、范围、当前版本、原子写入、回执、历史与索引。不能把摘要提取换成脚本规则，也不能由开发 agent 代写后宣称 Weber 已通过验收。

**开始 V2-06 少量真实文章试点：** V2-01～04 核心代码与配置已上线，所需本地检查通过；确认当前账户、Vault 与 `curator_agent_id` 指向既有 Weber，真实 worker 获得正确规则和工具；试点文件、输入 revision 与处理动作明确。新版模板和 prompt 草稿可提前准备，生产文章写入在此节点开始。

**放行 V2-08 批量模板化：** 少量真实文章试点满足以下条件并留下结果记录。

1. Weber 实际完整读取当前文章；已有准确 Key note 复用，缺失时理解后生成，保留主张、条件、反例与作者归属，不靠题名或首段猜摘要。
2. 真实维护 job 经受控工具原位写回；当前 pika_vault 正文论述与措辞、公式、代码、图片引用保持。新增 Key note 与原正文分开，无需新增永久原稿或补造来源。
3. 返回真实 job、worker session、产物 revision、差异、history 与索引状态；后续查询实际读到新版本与要点，任务成功不依赖 agent 的口头报告。
4. 定点纠错、人工编辑后的维护、读后并发冲突、no-change、恢复及索引失败均符合合同；重试不重复生成摘要或覆盖后来的用户编辑。
5. 至少一个真实问题完成知识建立→不同问法复用→明确纠正，并证明原核心思想和有风格的观点仍在。

既有普通 Markdown 在兼容索引中可先检索；“可查询”“已模板化”和“形成可复用知识”分别记录。试点及批次范围内沿同一链路推进，正文措辞保持适用于当前 pika_vault 模板化，未来明确纠错另按定点维护规则执行。

## 4. Prompt 语言：先选能维护的默认，再比较实际结果

默认采用**中文的写作、领域语义与观点归属规则，保留英文 schema、工具名、枚举和技术术语**。不把整段规则中英重复一遍，不翻译 `uid`、`expected_revision`、`read_many` 等机器标识，不翻译原文题名和引用来凑统一语言。这是适合本项目维护者的工程选择，尚不是模型效果优越性的实验结论。

现有 Octopus 将 persona、工具说明和任务指南组合为 `system_prompt`，Codex harness 再通过 `developer_instructions` 传入。因此本项目可调整的是应用层的 persona/开发者指令和任务上下文，不能据此声称可以重写模型供应方的隐藏系统规则。[装配代码][repo-assembly]、[Codex 参数][repo-codex]

| 证据 | 可以得出的结论 | 本项目不能据此断言的内容 |
| --- | --- | --- |
| NAACL 2025《Is Translation All You Need?》比较不同任务、语言与模型中的英语翻译策略 | 翻译收益依模型和任务而变，语言/文化细节可能在翻译中损失 | 论文不是当前 Codex/gpt-6.1-sol 的 system prompt 中英对照；不能推成“英文总是更准” |
| NeurIPS 2023《Language Model Tokenizers Introduce Unfairness Between Languages》 | 等义文本的 token 长度受语言与 tokenizer 影响 | 不能把论文中的某个语言倍率当作当前中英 prompt 的倍率 |
| OpenAI 官方 token 与 prompt 文档 | 应记录实际 usage；版本化任务指令并用任务样例比较；公共静态前缀有利于复用缓存 | 英文示例不证明英文最优；字符数、字节数或其他模型编码的估计不等于当前完整请求费用 |

来源：[NAACL 原文][translation-paper]、[tokenizer 原始论文][tokenizer-paper]、[官方 token 说明][openai-tokens]、[prompt 文档][openai-prompts]。这些研究为试验设计提供边界，没有给出本项目语言版本的实测排名。

先删除重复工作流、冗余工具解释和无关历史，再考虑语言压缩。比较时分开输入、缓存输入、输出、工具返回和调用次数；有实际 usage 时以它为准。若只能估算，记录编码器与估算范围，不能给出确定现金节省。Codex 的订阅额度也不能直接按某个 API 价表换算。

## 5. V2-06：约 6 篇代表材料的试点

六篇来自已审阅的实际 Markdown，全部纳入整理复核与读/检索检查。当前授权覆盖 Library 下所有 Markdown；先按代表样本明确处理动作，确有必要才改字，已经符合要求的文件记录真实 no_change，不为了“六篇都改过”而改写个人事实或长报告。Me 与 Research 属于最终整理范围，不再仅作只读验收对象。

| 材料 | 试点动作 | 主要检查 |
| --- | --- | --- |
| `Library/Me/information.md` | 当前个人记录完整复核；必要元数据或真实 no_change | 个人 gold 按当前版本重建；不猜缺失职业、课题或偏好，不套 Reference；旧回执不能覆盖后来编辑 |
| `Library/pika_vault/思考随笔/对笔记写作的理解.md` | 按外部文章来源和实际已有结构整理 | Key note 帮人读文；作者的“我”不进入用户画像，原有人工内容保留 |
| `Library/pika_vault/思考随笔/AI越擅长，我们就必须要撤退？.md` | 整理题名、description、来源和必要要点 | 保留“可能”、条件与讨论对象，不把作者判断变成已证实事实 |
| `Library/pika_vault/编程与开发/AI agent skill的一些开发经验.md` | 整理外部文章，同时保留当前代码/链接/条件与反例 | 核对当前否定流程、风险、程序验收边界和双版本同步；实际反例按当前revision，不能恢复不存在的旧LaTeX案例或把反例转为推荐 |
| `Library/Research/vidu_realtime_report/技术报告.md` | 正确识别本地分析报告；检验长文段落定位，按需补元数据 | 精确 Vidu、TTFF、SRF 等问法读到当前论述，摘要不代替长文；Synthesis 不自动核验 |
| `Library/Research/models_runtime_deep_dive.md` | 与 Vidu 一起检验宽泛选材和跨文档比较 | “数字人研究”可覆盖两种真实方向；有处理历史不能推成 RNN，来源/推断边界保留 |

先用这六篇跑日常问题和整理回读，直接观察哪些规则导致遗漏或返工。优先修正文保全、作者归属、来源造假、当前 revision 与检索定位；同一标点或 Key note 句式的个人偏好，不阻止已经正确的文件进入可检索状态。

如果试点需要检查库外 capture、HTML 抽取或长课程笔记，可增加 1–4 个真实材料，使总数保持在 5–10 篇的量级；它们是针对具体缺口的补充，不要求穷举全部格式。未确认支持的格式保持原始材料和待处理状态，不虚报已抽取全文。

## 6. 最小迁移清单与可恢复批次

复用现有任务、发布和历史记录。先建立当前 Library 全量清单，包含各级目录中的文章、个人记录、报告、课程笔记、导航和模板；清单可以是一个 JSON/JSONL 或表格导出，不新增队列框架。批次头记录 `batch_id`、任务范围、代码/parser/prompt 版本、运行模型与开始时间；单篇行只保留执行和恢复需要的信息。

| 最小字段 | 用途 |
| --- | --- |
| `input_ref` | 库内优先现有 server doc ID，加当前路径；库外为实际资源位置。已有 OKF `uid` 可记录映射，不要求旧文先造 UID |
| `expected_revision` | 当前服务端 revision；尚未入库的原材料记录输入 hash。它表示此次处理读到的版本 |
| `action` | 本次动作及材料角色，例如仅索引、仅元数据、文章整理、建立一篇明确有用的综合；不让 worker 自行扩大成全库维护 |
| `status` | 待处理、完成、跳过、冲突或失败；实际实现沿用已有任务状态，不新造平行状态机 |
| `output_ref` | 成功后的 doc ID、路径和 revision，附实际索引状态；完成不等于全部来源已经核验 |
| `restore_ref` | 对应已有 change/history 记录；无文本改动则明确无需恢复 |
| `note` | 简短修改概况或阻塞原因，例如来源未知、重复资源、人工编辑冲突；不复制私人正文和完整模型对话 |

第一批建议 5–10 篇，约 6 篇试点可以构成首批。同时按实际输入长度限制单次 worker 负载，长报告单独处理，不能把十篇长文连同全库导航塞进一次上下文。试点会给出每篇/每批的 token、耗时、失败和人工修正量，再据此决定后续批量；不事先编造硬件无关的速度或价格承诺。

开始一篇前核对当前文件；未变化的已完成项直接复用回执。源版本、任务内容或目标发生变化时生成明确的新处理记录，不用“同路径”跳过更新。发布按篇完成并记录恢复引用；中途失败可继续剩余项，不重新整理已成功全文。清单记录自动改动对应的恢复引用；用户之后的编辑不属于该批次回滚范围。

每篇清单另记录检索验证结果：当前索引状态、路径/身份精确定位、实际当前内容读取，以及领域内容的题名或正文问法命中；模板和导航按相应角色或明确范围验证，不要求进入所有默认领域候选。Vera 对语义质量按类型抽查，Octo 对清单覆盖、版本、回执及逐篇检索执行全量核对。最终交付报告以当前 Library 枚举与处理清单对账，列出总数、已改动、no_change、检索通过及所有未完成项；仍有未处理、冲突或失败时不能宣称全量完成。

## 7. 放行与停批规则

这些是拟议验收门槛，不是已完成成绩。初期以少量关键合同和真实产物检查为主，不要求搭建庞大评测平台。

| 项目 | 首批放行条件 | 失败后的动作 |
| --- | --- | --- |
| 内容保全 | 原文、公式、链接、媒体引用和人工 Key note 没有未授权变化；新增要点保留关键条件 | 停止尚未执行项，定位受影响规则/文件；不能靠降低抽查比例继续 |
| 主体与来源 | 不新增无依据的个人事实、作者/日期/来源，也不把 Synthesis 标成自动验证 | 修正 prompt 或解析归属，复核受同一规则影响的产物 |
| 日常检索 | Me、Vidu 精确对象正确；实际问题读到正文；宽泛题发现真实独立方向 | 区分身份、元数据、词法、选材和阅读失败，修复对应层 |
| 写入与恢复 | 当前 revision 检查、单篇发布回执和一次恢复通过；冲突不会静默覆盖 | 保留已完成结果，处理冲突目标，不重做整库 |
| 开销可解释 | 逐篇记录工具轮次、实际 token/估算口径、耗时与人工改正量；不存在无目的的重复全文传输 | 优先缩小任务上下文、去掉重复步骤；需要的正文仍继续读 |

这里的“全部通过”针对试点中上述明确合同，不代表对未来所有文章的可靠性已有统计保证。对内容和范围造成实质错误时停批；纯文风问题可记入下一版，不要求当前批次所有文章语言风格完全一致。

进入后续小批前，至少能解释试点失败原因及修正影响；更换 prompt 后对受影响样例复跑，再继续排队项。若某批发现坏规则，恢复已确认受影响的自动修改时仍检查当前 revision；人工后来改过的文件先生成差异，不能强制套用旧备份。

## 8. V2-08：已有与库外材料逐批迁移

当前 Library 内的执行顺序为 pika_vault 优先，再分批覆盖 Me、Research、课程笔记、导航、模板及其余目录；高频资料优先只影响批次顺序，所有 Markdown 最终都要完成整理复核、入库和检索验证。先让已有文档在正确范围里可检索，再按真实类型补对人和检索都有效的题名、description、Key note 和实际出处。课程笔记、研究报告、私人记录按其实际类型处理，不统一伪装成外部 Reference。

库外材料先确认是否已有同一资源。可以用明确来源标识和精确内容 hash 辅助匹配，近似文本只提供可能重复的候选。保留新的版本与原有记录之间的关系；重复导入不自动生成第二份主文，也不能因 URL 相同就覆盖用户已有批注。来源暂缺可以记录未知，不要求模型补齐作者和发布日期。

**Concept 与 Topic 是按用途选择的产物。** 只有某个概念已经反复用到、同一问题需要跨文复用，或导航能帮助现有资料发现时，才安排一两篇明确有用的页面。优先复用已有页面和链接；用户问过一次概念，不自动给所有 Reference 蒸馏一页。综合可支持“本地报告如何分析”的回答，其涉及原始实验或外部事实时仍按实际读到的依据归属，不能用文档类型代替核验。

普通查询、读后讨论和写作建议不会自动发布新知识。用户明确要求保存、整理或更新时，才按当前授权范围写入；用户的观点与外部作者的观点分别表达。一次成功的复用可以是找到已有正文并给出准确引用，不以新增页面数评价知识库成熟度。

## 9. 可选语言对照与近期开销记录

语言对照用于解决观察到的质量或 token 问题，**不是 V2-06/V2-08 的硬门槛**。有必要时做一轮轻量 A/B/C：6 个短任务 × 3 个等义版本，共 18 次初次执行；只对失败、接近或不稳定项目追加重复。

- A：中文语义/写作规则，保留英文机器标识；B：等义英文规则，输出和资料仍按原任务保持中文；C：中文领域/写作规则加简短英文协议规则。
- 固定实际 Codex 模型、推理配置、工具能力、语料 revision、示例数量、输出要求和任务范围；使用新会话并打乱顺序。不能把精简版英文和冗长旧版中文比较后，把收益都归因于语言。
- 六个任务覆盖：Me 已知/未知字段；Vidu 的条件与否定；数字人的跨文覆盖；外部文章的作者归属与整理；反例/代码/链接保全；人工内容与 revision 冲突。以真实必要上下文构造小任务，避免为了试语言复制整库。
- 程序检查身份、参数和内容差异；Vera 按不显示语言版本的 rubric 检查主体归属、条件、可读性与引用支持。记录实际 usage 和任务完成成本，不要求模型输出隐藏推理过程。

最先可以用固定材料与固定工具返回比较表达和保全能力，节省变量；但回放不证明真实工具调用已经正确。候选版本若值得采用，仍在一条真实查询和一条整理链路验证。有限样本没有明显收益时保留当前可维护版本，不为了“国际通用”全量翻译。

近期开销表至少按材料分别记录：读取/写入工具轮次、输入/缓存/输出 token 或明确标注的估计、处理耗时、重复尝试、人工修正分钟或修改项数。长报告与短 Me 分组观察，不用它们的混合均值掩盖问题；token 下降的同时需要检查证据质量和改正成本。[官方评估实践][openai-evals]

## 10. 后续应用与交付边界

V2-05 的 Sapphire 标签过滤和 V2-09 的 SmartReader 功能属于后续应用计划，不阻塞首批资料整理。应用复用同一文档身份、内容角色、来源和当前读写合同；标签筛选消费共同索引，SmartReader 的保存/复用入口不形成另一套权威正文和强制摘要流程。

拟议标签接口采用 `tags: string[]`、`tag_match: 'any' | 'all'`，默认 `all`；标签目录为 `GET /api/wiki/tags` 与 app `wiki/tags`。这些是待实现合同。统计按当前范围内去重后的 doc ID 计算，多个章节不多计，同源多文档的标签计数也不等于独立来源数。SmartReader 的交互范围与具体功能见后续应用方案，不借迁移之名提前执行。

原设计阶段完成迁移决策和代表样本；后续已有真实 persona/上线/首批及当前修复检查，具体范围见[当前进度](local-shared-wiki-progress-v2.md)。每批留下完成/无变化/冲突项、当前结果、原因和恢复引用；已索引不计为已整理，旧版本回执不直接计新版本通过。先收口当前两项实机失败和修复部署、完整试点/Q58，再覆盖全部 Library；不等待后续 App、语言或可选语义实验。
