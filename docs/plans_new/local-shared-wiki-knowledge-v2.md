# 本地共享 Wiki v2：知识积累、阅读与长期综合

> **Status:** in-progress — 核心读写、角色/来源及真实首批已推进，Q58 的真实知识复用与纠正闭环未完成；应用入口仍是后续计划，见[当前进度](local-shared-wiki-progress-v2.md)。
>
> 修订：v2.1，2026-10-13（Asia/Shanghai）；文件名保留 v2。本文补充前版的知识层设计：速度、token 与扩展性是持续使用的条件，长期可复用的理解与综合是知识库的目的。沿用现有 Octopus、独立 /wiki、Weber 与 OKF v0.2 + article-v1，不要求再建立一个独立知识系统；Sapphire/SmartReader 接入只属后续 App feature plan。

## 1. 这轮设计需要修正什么

前版重点解决“怎样找到正确文章、少读无关内容”，但对知识层的价值描述还不够完整。若 Topic、Concept 和 Synthesis 永远只能用于导航，每次回答仍要求重新阅读全部 Reference，系统虽然更擅长搜索，却没有充分利用已经形成的理解。

本轮增加一条明确原则：

**当前、适用且来源范围清楚的知识页，可以直接支持概念解释与已有综合。是否追原文，由本次问题的证据要求决定。**

这里的“可以复用”不表示知识页自动正确。Weber 仍需读取当前知识页，理解它解决什么问题、适用什么范围、哪些内容是推断，并保留来源与更新时间的实际含义。需要原文时应展开相关段落，而不是为任何问题重读全部来源。

你的库应同时积累三类价值：

| 价值 | 具体结果 | 对你的用途 |
| --- | --- | --- |
| 材料可找到 | 精确标题、别名、章节和来源定位 | 找到 Vidu 报告、Me 当前记录 |
| 理解可复用 | 概念解释、方法关系、条件与反例 | 不必反复重新理解实时性指标与因果蒸馏 |
| 思考可继续 | 未解决问题、证据分歧、选择理由与研究假设 | 下一轮研究能接着已有问题推进 |

其中“你的想法”必须有真实归属：你明确表达的判断可以标为用户观点；Weber 的建议、外部作者的观点和模型综合分别标明，不能因为被保存进个人库就混成同一种立场。

## 2. 再次核对 LLM-Wiki 与 my-wiki

### Karpathy 的原始思想

本次核对的是 Karpathy 的 [LLM Wiki 原始 gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)，不是评论区、同名仓库或他人扩展版。作者提出将原始资料、持续维护的 Wiki 和操作约定分开，让综合、交叉关系及新旧观点的变化长期积累；他也明确表示这是可按个人需要取舍的模式，目录和工具并非固定实现。[原始说明](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f#the-core-idea)

这对本项目的启发是：**把已经做过、以后仍有用的理解保存下来**。检索与知识积累可以配合，不能把作者对“每次从零拼接资料”的批评理解成所有 RAG 都无法积累知识。

### my-wiki 的实际策略

当前 [my-wiki README](https://github.com/NimaChu/my-wiki) 以 Reference、original 和长期 Concept 组织知识，并让聊天与网页共享同一库。当前入口是 [AGENTS.md](https://github.com/NimaChu/my-wiki/blob/main/AGENTS.md)，具体流程集中在轻量 playbook，不能继续按旧版 CLAUDE.md 假定其结构。

其 [Query 工作流](https://github.com/NimaChu/my-wiki/blob/main/my-wiki-skill/references/workflows.md#query) 明确优先读 Concept，只有核验、出处、时效或细节需要时才展开 Reference；[维护工作流](https://github.com/NimaChu/my-wiki/blob/main/my-wiki-skill/references/workflows.md#maintain) 强调独立可复用的知识单元与已有页面复用。网页捕获和后续蒸馏也分开，不因保存来源就默认允许维护。

下面各节是基于这些思想、现有代码与用户习惯作出的**本项目设计推导**。不移植 my-wiki 的目录体系、星系应用或全部完成门槛，也不把作者关于维护成本的乐观描述当作性能测量。

## 3. 理解、综合、检索是三个相互连接的动作

### 理解：把当前材料读明白

用户在 Octopus 原生会话与 Weber 阅读讨论一篇文章时，可能只想问某句话是什么意思、论证有没有跳步、与自己的研究有什么关系。此时 Weber 应围绕当前材料讨论，保留作者的前提与判断强度。后续 SmartReader 可以提供另一种阅读入口。

结果可以停留在对话中。没有保存意图，就不为了“知识闭环”自动写一篇总结。讨论需要旧库知识时使用本次明确的 Wiki 查询范围；只讨论已提供的当前文章不必先搜索整个库。

### 综合：形成跨材料、可继续使用的解释

综合应围绕一个真正的问题，而不是把几篇摘要拼成更长摘要。例如：

- 不同视频生成报告中的“实时”分别指吞吐、首帧还是交互响应？
- 关键点、3D rig 与直接视频生成分别适用于什么约束？
- 同一个 forcing 术语在不同论文中是否对应相同训练条件？

这类产物需要表达材料之间的关系、比较条件与未解决之处。它可以成为一篇 Synthesis，也可以只更新已有专题的一节。没有独立价值的术语和零散片段不必各自生成 Markdown。

### 检索：复用已知，再填补当前缺口

检索既能找 Reference，也能找已有 Concept、Topic 和 Synthesis。命名对象问题优先精确定位；宽泛研究问题优先覆盖现有方向；已形成稳定解释的问题可以从知识页回答。

三种动作应形成循环：理解产生候选洞见，用户选择值得保存的部分，综合进入受控维护，后续检索复用它。循环不要求每次问答都写回，也不要求每篇文章都立即晋升为 Concept。

## 4. 只维护少量有独立用途的长期页面

继续使用现有 Library 大分类。以下是页面职责，不是必须新增的四套目录或数据库。

| 对象 | 什么时候值得有 | 最小内容 |
| --- | --- | --- |
| Topic / Navigation | 一个领域有多条路线，用户需要知道从哪里继续 | 问题范围、方向地图、代表材料、阅读顺序 |
| Concept | 某个概念或方法会反复被问，解释能脱离单篇来源独立成立 | 定义、适用条件、关键区别、例子、来源 |
| Synthesis | 一个比较或判断依赖多个来源，重复推导成本明显 | 当前结论、比较维度、理由、条件、来源与不确定处 |
| 研究问题/分歧记录 | 现有材料暴露出值得继续追查的问题 | 问题、已有证据、缺口、下一步怎样区分不同解释 |

**问题和分歧先放在相关专题内部。** 只有它们已经有独立讨论价值、需要单独引用或持续积累证据时，再拆成单独页面。一个“待研究的问题”列表不需要新建任务系统。

以现有数字人资料为例，可以先形成一个“实时数字人研究”专题入口，再按真实反复出现的需求决定是否沉淀“实时性指标”概念或“实时生成路线比较”综合。这里是拟议主题，不表示附件中已有这些 Markdown 成品，也不要求立刻创建它们。

### 页面应有自己的问题边界

一个长期页面应说清楚：

- 它回答什么问题，讨论到什么范围。
- 哪些是已有资料支持的内容，哪些是整理者的综合或用户的判断。
- 影响结论的重要条件和仍未解决的问题。
- 从哪里进入相关原文或进一步解释。

这不是每页必须照抄的四个标题。短概念可以短，复杂综合可以长；正文组织服从内容。article-v1 继续服务来源文章，知识页可以选择本地约定的 Concept / Topic / Synthesis 类型，不能把所有页面都套成一篇外部文章。

## 5. 从阅读讨论到受控沉淀

当前在 Octopus 原生会话与 Weber 讨论；明确保存或维护时沿独立 `/wiki` 的核心 API/MCP、durable job 与受控工具沉淀，不经 App。后续 SmartReader 可以复用这套含义和服务合同：

| 用户意图 | 默认行为 | 是否进入长期知识 |
| --- | --- | --- |
| “解释这段” | 读选段及必要上下文，直接讨论 | 否 |
| “和我库里的 Vidu 报告比较” | 使用本次 Wiki 查询，读取相关现有材料 | 默认不写入 |
| “帮我把这个想法表达清楚” | 对明确内容写作，区分用户想法与 Weber 补充 | 先形成草稿 |
| “把这篇整理入库” | 原材料与来源提交 maintain；来源文章按 article-v1，其他材料按实际类型 | 是，限本次目标 |
| “把刚才的讨论补到这个专题” | 使用该专题的明确可写范围，保留旧内容与来源 | 是，限指定专题 |
| “保存这段为我的观点” | 保存用户实际表达和明确选中的内容，保留相关参考 | 是，不把整段 AI 发散都记成用户立场 |

writing 规则是**实际写作时按需使用的共享能力**：SmartReader 中形成草稿、Weber 撰写综合、文章入库产生 Key note，都可以使用。单纯检索、解释已有概念、显示任务状态，不需要加载全部写作指南；它也不应被限定为某个 app 私有能力。

当前文章的原文、选段与既有讨论要避免反复整篇重传。重新进入同一材料时应复用文档身份与版本信息，按问题补充必要位置。核心当前能力以 task/guide/schema 为准；SmartReader 的材料绑定、草稿与请求装配按后续对接文档实施，不表示 App 已接入或为本轮知识积累的前置条件。

用户已经明确要求保存或修改具体对象时，按该范围执行，无需逐段再次询问。若只是讨论，则保留对话的探索空间。

## 6. 已有未整理材料什么时候处理

首先区分三种进度，它们不是强制串行流水线，也不能占用 OKF 的 status 字段：

| 进度 | 含义 | 是否要求 LLM |
| --- | --- | --- |
| 已索引 indexed | 有可读内容、当前路径与检索入口 | 通常是确定性处理 |
| 已整理 organized | 文章的身份、范围、正文边界、摘要与来源已按适用模板整理 | 需要理解时才调用 |
| 已形成可复用知识 curated | 有值得长期复用的解释、综合或关系 | 通常需要有目标的理解与综合 |

一篇普通原文可以只处于 indexed，仍能正常检索；一篇已整理文章不必另外创建 Concept 才算完成入库；一个专题也可以先有少量高质量综合，再逐步完善。这些是工作进度描述，运行态可按实际记录投影，不要求每篇文档再增加一组强制字段。

### 对当前小库的顺序

1. 先让当前 Library 全量材料建立统一身份和索引；默认领域候选按实际角色控制模板、快照和资产噪声，明确 lookup/read 仍按对应范围可达，不能以候选过滤代替全量验收。
2. 用已讨论的三篇样例验证 article-v1；用 Vidu 报告与小型个人资料验证查询和归属。
3. 用户当前正在读、准备引用或反复询问的材料，优先整理。
4. 用户后续已指定当前 Library 全部 Markdown，pika_vault 优先，其余按实际类型明确批次并完成整理/复核和检索；普通查询或手动保存不自动扩展为新的全库维护。
5. 只有反复出现、能节省理解成本的主题，再沉淀长期 Concept / Topic / Synthesis。

用户可以一次指定一个目录或一批文章的整理范围，队列在范围内持续完成。无需把每一篇都变成额外确认；也不能将“整理这篇”解释成修改所有相关旧文。

### 两种维护范围

**文章入库**默认只写本次新文或指定文章，相关旧文只读。关系可以写入新文，反链由系统推导。

**专题维护**在用户明确选定专题和来源范围后，允许更新该专题及本次指定知识页。新文章发现值得更新的旧主题，但旧主题不在可写范围时，可以记录维护建议；不能借“长期积累”扩大写范围。

原文变化先更新索引并使相关依赖标记需要检查。语义重整只在本次维护中发生，不能让一次小修改递归触发全库重写。

持续积累使用[定点维护](local-shared-wiki-maintenance-v2.md)：不按 AI／人类作者或过去人工编辑决定能否修订，在明确目标和当前版本上纠正具体错误、补充解释与条件。保留既有思想、论证和风格表达，当前 pika_vault 先保持正文措辞做模板化，正常维护不重新生成正文。

来源重读确认原解释仍适用时，仅更新实际检查过的直接依赖记录，不为解除提示改字。已有观点遇相反证据时保留主体与语境，补充证据或说明；无法确认的问题不替换为模型的断言。新页、旧页和人工修改后的知识都走同一维护合同，不要求认领生成区。

## 7. 查询时复用知识页，按证据需求追原文

### 什么时候可以直接使用知识页

当本次问题落在当前 Concept / Topic / Synthesis 的范围内，页面表达清楚，来源范围可识别，也没有已知依赖漂移或冲突时，读取这个当前页面即可用于解释或已有综合。引用知识页本身，并准确说明这是页面中的解释或整理判断。

例如，已有“实时性指标”页清楚区分几个指标的含义，用户再问这些概念有什么区别，不应每次重新读取全部视频生成论文。来源仍然可追溯，但追溯能力不等于每轮必须走完整条链。

### 什么时候定点展开原始证据

| 触发条件 | 应补充什么 |
| --- | --- |
| 用户问论文的精确数字、配置、实验条件或原话 | 对应 Reference 的表格、段落或原始资源位置 |
| 页面只给结论，缺少回答所需条件和理由 | 最相关的来源片段 |
| 两份知识页冲突，或有来源更新提示 | 冲突双方与发生变化的来源 |
| 当前问题超出知识页范围，提出新的跨文比较 | 缺失方向的来源与必要知识页 |
| 用户要求事实核验、复查或最新情况 | 在本次任务能力与范围内重新查证，并区分未完成部分 |
| 个人事实需要准确回答 | Library/Me 的当前相关记录 |

展开的是**所需证据**，不是所有 Reference。整篇评价仍须读完整目标；局部问题按段落读取；完整阅读允许分批继续，不能被“初始三篇”或固定工具轮次变成硬上限。

### 缓存与证据归属

复用已有综合不等于用模型参数中的印象替代当前知识页。旧聊天的摘要、没有读取的链接、派生页的自我声明，都不能自动成为本次证据。

对外部资料没有进行本轮读取时，可以引用“库内报告记录的结果”，不能宣称“本轮核验了原论文”。未知或过期状态要反映在答案范围里；不用额外警告淹没正常解释。

## 8. 防止知识库被 AI 总结反向污染

### 控制明确重复，保留综合价值

源文章、其 Key note、明确展示版和重复摘要，不当作多份独立支持。综合引用 A、B 不合并两个作品，普通相关链接也不表示重复。本期按 Q57 记录实际出处和已知直接关系，不要求完整来源根或自动证据计数；有独立解释价值的综合保留其用途。

同时，不因为一篇页面由 AI 整理就一律降成“只能导航”。正文用途由 doc_role 与实际内容判断，generated 只是生成/整理信息。好的综合有独立复用价值，其价值与独立证据数量是不同维度。

### 不用输出给输出作无限循环背书

- Key note 从原文和明确来源生成，不从上一次 Key note 再摘要。
- 新综合可参考已有知识页的结构和解释，但必须保留可追溯来源，不因引用了三份同源综合就声称三方支持。
- 用户只是在探索的假设，保存时仍是问题或假设，不自动升级为确认结论。
- 冲突先判断是否来自测量条件、版本、主体或语境差异；不要为了制造“洞见”把不同定义硬写成矛盾。
- 尚未查清的分歧写入相关页的“待核实”部分，保留双方位置和所缺证据；不让 LLM 仅凭语气选胜方。
- stable、organized、curated 与 verified 分开。可检索、已整理和引用闭合均不自动等于事实核验。

### 哪些检查交给程序

程序负责身份/路径、版本、重复表示、来源位置、已读覆盖与写入范围。它可以指出缺链、漂移和重复，但不应把关键词相反直接认证成语义矛盾。

Weber 在实际入库、专题维护或问答时，针对相关材料判断条件与观点。这种局部检查适合当前小库，不需要定期让 LLM 比较全库所有句子，也不需要先建立庞大的事实图谱。

## 9. 速度、token 与扩展性仍是核心约束

长期知识页和检索优化应共同降低重复工作：

| 场景 | 主要节省来自哪里 |
| --- | --- |
| 明确查某篇文章 | 精确路径/标题/别名定位，减少多轮搜索 |
| 问某个局部细节 | 章节命中与批量读取，减少整篇传输 |
| 反复解释同一概念 | 读取已有高质量 Concept，减少重复跨文综合 |
| 宽泛研究概览 | 少量 Topic / Synthesis 覆盖方向，同源去重 |
| 普通保存与小修改 | 确定性增量索引，不反复调用 LLM 整理 |
| 来源变化后的维护 | 只检查相关依赖与本次范围，不全库重写 |

但长期整理也有成本。对一个很少再用的材料，提前生成多篇概念、问题和综合可能比按需阅读更贵。实施应比较：

**首次整理成本 + 后续维护成本 + 多次查询成本 + 人工改正成本。**

因此优先维护反复使用、跨文连接明显、对研究决策有影响的主题，而不是追求“所有材料都已蒸馏”的比例。不要用知识页数量、关系边数量或整理覆盖率代替价值。

### 需要观察的结果

Q58 已确认核心至少验证一个真实、值得复用的研究问题：建立知识页，以后续不同问法复用，并完成一次明确纠正。隔离 fixture 用于机械边界，不能替代真实理解价值验收；不为每篇 Reference 强制造 Concept。

除了定位准确率、延迟、工具调用数和输入 token，还应验证：

- 第二次同类问题能否复用已有综合，减少重复原文阅读。
- 复用时是否保留关键条件与来源归属。
- 知识页过期后，是否能正确展开受影响的证据。
- 广泛主题是否覆盖不同方向，而不是返回一串同源摘要。
- 用户是否能从上次的未解问题继续研究，而不必重新说明全部背景。
- 新增一份资料是否改变了已有理解；没有实质增量时是否避免新增重复页。

省 token 不等于强制英文 prompt。中文阅读与写作规则可继续用清楚、简短的中文，API 字段保留英文。若需要比较中英版本，应在相同内容和模型设置下测实际行为与 token；不把翻译本身当成可靠提速措施。

## 10. 采用、调整与不采用，以及实施顺序

以下为本项目取舍，原项目行为依据见第二节和文末来源。

| 思想或做法 | 本项目决定 | 原因 |
| --- | --- | --- |
| 把有用综合长期保存 | 采用 | 减少重复理解，让研究能连续推进 |
| 原始材料与新增解释区分 | 采用 | 便于回查、保留作者与用户归属 |
| 查询优先复用适用的知识页 | 采用并保留精确查询通道 | 兼顾知识积累与原文细节定位 |
| 页面和网页界面共享同一库 | 采用 | 避免 app、agent 各维护一份内容 |
| 只按任务加载具体工作流 | 采用 | 保持 persona 简短，避免常驻整本手册 |
| 自动更新大量相关旧页 | 调整为明确专题范围内维护 | 保留新文入库时旧文只读的用户习惯 |
| processed 依赖 Concept 与证据闭环 | 不作为 article-v1 入库完成门槛 | 文章可完成整理，无须为指标额外造概念页 |
| 每问先读全局 index.md | 不设为固定步骤 | 精确问题可直达，小目录与主题入口按需使用 |
| 自动保存所有问答 | 不采用 | 保留探索空间，避免重复与未经选择的观点堆积 |
| 全库周期性语义扫描 | 当前不默认采用 | 先做局部依赖检查与选定范围维护 |
| 固定三篇/固定工具轮次即停止 | 不作为通用规则 | 可作起步预算，不能截断整篇或必要比较 |
| 搬迁为对方完整目录与应用 | 不采用 | 继续使用 Library、OKF、/wiki、Sapphire 和现有队列 |

### 实施顺序

身份、内容角色、来源、紧凑检索与读取核心及对应指南已实现，实际首批已有定位、理解和保存验收。接下来收口当前修复版本，再补齐真实完整试点和一个有用途研究问题的知识建立、不同问法复用及明确纠正，随后覆盖 Library 全量。通用写作自动装配和 App 功能按其范围接续。

SmartReader 的阅读讨论和写作入口随后接入相同任务与内容契约，可以与核心能力并行设计；其完整 UI 功能不阻塞底层检索与内容契约落地。Weber 只调整必要的知识与归属段，继续保留智者、读书伙伴和独立判断的风格。
