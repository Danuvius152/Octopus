## 3. 领域边界

已确认术语见 [GLOSSARY.md](../../GLOSSARY.md)。会话保存持续的对话上下文；逻辑轮次是一条请求及其恢复；CLI 调用是轮次内部的一次尝试。手动中断后提交新提示开始新轮次，而自动恢复仍属于原轮次。

委派的子会话可以被再次使用，因此“取消旧委派”不能等同于“停止这个子会话现在正在做的任何事”。请求身份决定哪条执行被停止；委派工作归属决定取消范围；派发状态决定何时处理返回。这三者必须分开。

一次轮次结束或普通 Stop 不封闭全部工作分支。已启动的 bg 和子委派仍可完成，结果进入待处理队列。显式取消委派才封闭对应工作分支，并终止它所属的 bg/后代。

## 4. 修复前基线事实（f6d859e）

本节记录审计与设计时核对的原实现；其中的缺陷和接口限制不代表修复后的行为。修复后的契约见 §6，最终验收记录见 §9。

- [turns.py](../../server/sessions/turns.py) 的 `_Attempt.failed` 把曾见过中间错误等同于失败，成功终态不能解除它；成功 result 又在恢复判定之前广播，触发 F1/F2。
- 同文件的 `_handle_stream_event` 在恢复判定前已经写入 result。修复必须同时调整写入和广播时机，保证历史与实时语义一致。
- [events.py](../../server/sessions/events.py) 丢失 result 的历史错误标志和原因；实时 result 没带原因。[useWebSocket.ts](../../web/src/hooks/useWebSocket.ts) 又丢掉错误标志，[MessageBubble.tsx](../../web/src/components/MessageBubble.tsx) 固定显示 Done。现有消息表已有 `content/is_error`，保存这两个字段本身无需迁移。
- [codex.py](../../server/harness/codex.py) 的容量提示文字缺少匹配。恢复代码会把原始事件追加到分类文本，不能断言结构化错误码必然被当前源码丢弃；现场完整 CLI JSON 未保存。
- Codex profile 使用 `CLOSE_AFTER_SPAWN`，[run.py](../../server/harness/run.py) 启动后关闭 stdin。当前忙时输入新提示会排队，无法通过这个通道向正在执行的同一进程追加探活提示。
- [questions.py](../../server/sessions/questions.py) 处理模型调用 Octopus 的 `mcp__ask__user`：模型给问题和选项，框架展示表单并回传答案。当前没有转译 Codex 原生 `request_user_input` 的适配。
- [bg_tasks.py](../../server/bg_tasks.py) 的输出后六十秒规则独立于总时限。MCP/API 目前只有 command/description；manager 内部虽然有总时限参数，模型无法通过公开工具设置静默例外。
- bg 执行后台 shell 命令，完成状态与 stdout/stderr 注入原会话并触发后续轮次。它让原轮次可以先结束；独立模型上下文由子 agent 提供。
- Agent 创建和更新都需要校验保存后的 backend/credential 组合。表单发送 null 清除绑定，Session API 也把空字符串规范为 null；绑定校验应复用账号范围内查询。
- 现有队列把人工消息和自动回流混在一个 FIFO，取消当前 inner task 后立即取下一条，人工纠偏可能落在队尾。队列项只在内存，内容到消费时才写入会话历史；需要实现 Q10 的派发控制，继续保留用户已选择的内存存储边界。
- 队列快照目前是字符串列表，WS 入队/出队让客户端 append/slice。优先派发需要稳定请求 ID、结构化来源和带 revision 的权威队列快照，保证重连或多标签页状态不倒退。

## 6. 已收束的设计树与落地方案

### 6.1 请求、尝试与唯一终态

在请求被接受时建立稳定身份和来源，使排队、初始化、全部尝试、用户中断和终态共用它。自动恢复不会创建新的用户请求或重置原轮次恢复预算。

`_Attempt` 明确记录成功、失败或缺少终态；中间 error 单独作为诊断，后到的明确成功终态解除已恢复的中间错误。正常结果、初始化/stream 异常和中断使用同一个一次性结算入口，在恢复判定结束后才保存和广播唯一最终 result。

真正 transient 最多两次额外恢复，沿用一秒、两秒退避。没有文本/工具活动时使用原始请求及轮次起点恢复状态；已有活动时只续接捕获的原会话，缺少可用恢复身份则明确失败。idle 使用现有独立预算；不得把所有恢复类别的独立预算误写成整轮最多三次调用。认证、额度不走 transient，不自动换模型。续接不是工具副作用恰好一次的保证，提示应要求检查既有工具结果并避免重复工作。

最终状态、原因、provider 错误码、关联请求和恢复类别/次数采用有类型的结果/恢复载荷，复用现有 `content` JSON 存储和 `is_error` 字段；在历史/WS 适配边界统一规范化，普通文本消息保持既有形状。这项诊断修复不建立持久请求队列。中间诊断/恢复使用非终态消息，委派、应用对话和构建不能因它结束。历史、分页、WS 和重连使用同一形状与 seq。旧 NULL 结果显示“已结束，结果未记录”，不回填成功。

### 6.2 Stop、优先纠偏与明确恢复

Stop 在第一次等待之前关闭自动派发门并捕获当前请求，再取消该请求及恢复。所有入口都经过同一个调度门，包括初始请求、FIFO 领取、空闲时新回流、未送达的 steer 转入队列。一个短时调度锁保护派发门、当前领取身份与优先选择；贯穿整轮的会话锁不承担这项职责。

原先排队的人工消息与自动返回都保留并暂停；Stop 后新提交的人工指令获得优先资格，旧积压不会抢先启动。纠偏运行中后续人工消息继续遵守后端原有 steering/排队能力，自动返回始终只入待处理队列。纠偏完成不恢复积压；用户明确点击“继续处理”才打开派发门，剩余条目按保存的顺序处理。

队列暂停与执行状态独立：纠偏可以 running，同时积压仍 paused。暂停期间继续接收 bg、agent、research 等返回，执行空闲也不能绕过派发门。Stop 必须覆盖“已经取出、广播等待中、尚未建立 inner task”的窗口，未开始执行的领取项返回待处理状态。

客户端展示“已暂停 · N 条待处理”和明确恢复入口；发送提示说明新指令优先、积压仍暂停。结构化队列条目含请求身份、来源与摘要，快照含 revision；HTTP/WS/多标签页只接受较新状态，不能继续用 slice(1) 推测出队项。执行历史继续保留现有自动注入 marker，但来源另行结构化保存。

暂停不占模型运行配额。存在未处理项时不得误发“全部完成”通知或自动归档；延后执行的 fork 等操作也不能绕过派发门。暂停父会话不冻结 child 的问题期限，消费旧 agent-question 前必须检查它是否仍有效，过期问题只保留说明、不再触发回答轮次。

### 6.3 内存接收与浏览器重连

扩展现有内存队列项，保存稳定请求/交付身份、来源、关联工作、载荷及顺序；Session 内存对象保存派发暂停和队列 revision。继续使用现有 bg/委派/research 投递入口，在当前服务生命周期内区分已接收、领取和实际开始，避免同一返回被重复领取。

仅排队项目在界面显示待处理，不伪装成模型已经读过的执行历史；实际开始后沿用会话消息持久化。Stop 与领取竞态保留尚未开始的项目，已经执行后被中断的请求不隐式重新入队。读取快照和处理均保持账户与会话范围校验。

浏览器重连/切换会话/多标签页从同一个运行中的服务读取队列及暂停快照。服务重启后内存队列和暂停状态不恢复，保留现有历史与后台任务记录的处理，不自动重放旧工作。revision 必须同时带服务实例或队列代次，避免重启后的新快照因旧客户端 revision 较大而被拒收。

### 6.4 委派取消、bg 归属与迟到调用

委派每轮有不可变工作归属，子委派回流延续所属工作；follow-up 新轮建立新归属。取消先封闭目标工作，再停止匹配执行、匹配待处理项、所属后代和该轮 bg，保护独立新请求。向仍有效的上层调用者交付一次取消结论，取消后代的说明可以留历史，但不能再唤醒已取消分支。

取消请求在第一次等待前固定目标轮次；前端取消携带它所见的轮次身份，避免旧按钮请求跨 follow-up 误杀新轮。已完成轮次仍可拥有未结束的 bg 或后代；取消它只清理该轮所属工作，保留原终态，不重复向父会话交付结论。后台停止一直使用捕获的进程引用，并覆盖 spawn 尚未完成的启动预约，启动返回后若归属已关闭则立即清理。

MCP 工具身份绑定实际 HarnessRun 的 lease 与不可变工作归属；可信上下文从 HTTP 入口到线程、loopback REST 和 manager 始终透传，不允许模型任意填写 work ID。Stop/取消先撤销旧运行 lease；工作归属改变时重新建立运行。同一工作内的多轮和 relay 继续允许 Claude held process 复用，随机 lease 不参与每次候选 spawn signature 比较。原生异步子 agent 的精确旧 turn 归属在缺少 CLI correlation 时不能靠当前 session 猜测，但稳定委派工作归属仍可可靠限定 Q9 取消范围。

首次建立账户并接管既有会话时，旧无主运行的权限也随之退役；账户存在后，旧无主 MCP 身份不能通过 REST、WebSocket 或直接 MCP 请求访问账户数据。后续轮次使用接管后的会话所有者。建立账户前的单用户身份政策保持有效。

### 6.5 两种静默时限与问题生命周期

模型继续采用五分钟静默停止；明确等待当前尝试的有效问题时暂停 idle，最后一个问题关闭后重新给完整五分钟。问题默认三十分钟自动答复保持现有政策；人答、自动答复、取消和尝试结束使用一次性解决路径，关闭表单、取消定时器并唤醒 long-poll。整体时限默认关闭，显式启用则先检查且包含等待及恢复。

问题 deadline 由服务端权威管理。MCP 不再用固定三十五分钟覆盖自定义或禁用的答复期限；正常 408 仍表示等待，持续通信失败返回明确错误，不合成用户授权。旧问题、旧尝试和迟到回答不能为新轮次提供豁免或复活任务。

Codex 原生 MCP 每次工具调用默认六十秒超时，因此只为 `ask` 覆盖 `tool_timeout_sec`：正数答复期限加六十秒传输余量；服务端禁用自动答复时使用 `2**31-1` 秒的有限传输哨兵（约六十八年）。原生配置没有已确认的无限开关，不能把零解释为禁用原生超时；这项覆盖不改变 `exec --json` 或其它 MCP 工具。配置语义见 [OpenAI MCP 文档](https://learn.chatgpt.com/docs/extend/mcp) 与 [配置参考](https://learn.chatgpt.com/docs/config-file/config-reference)，本机 Codex 0.162.1 已在独立临时配置中验证正数解析。

后台参数统一开放给 MCP/API/manager：`idle_timeout_seconds` 省略=60、整数且非负，0 关闭该任务静默；`timeout_seconds` 省略=1800、整数且为正，始终保留总时限。两项均不接受布尔值或浮点数，最大值为 SQLite INTEGER 可保存的 `2**63-1`。进程启动前校验；实际限制作为任务快照持久保存并用于回执、详情、广播与回传。保留首字节后双流静默的默认判据，长测试由调用方显式声明例外，不按命令名猜测。

静默/总超时明确报告失败原因与对应限制；人工取消标 cancelled；外部信号、关闭和重启标 interrupted 并说明原因。历史未保存的限制/原因保持未知。服务启动不自动重跑旧后台任务。

### 6.6 凭据绑定与失败显示

Agent 创建、更新及仅切换 backend 都校验最终绑定组合。省略字段保留，null 清除，空字符串按现有 Session/form 约定规范为 null；非空无效或其他账号 ID 使用相同反馈，后端不兼容拒绝保存。采用共享 scoped validator，并在最终写入保证校验条件仍成立，精确处理绑定删除竞态；不能仅先 SELECT 后 UPDATE，也不能吞掉所有数据库异常。

用户界面分别表达成功、失败、已中断、正在恢复；恢复默认显示简短进度，细节可展开，最终结论保留恢复次数。失败原因经有限长度和敏感信息处理后进入实时与历史链路，避免仅靠全量原始 stderr 排障。

委派子会话手动中断后直接继续 → 当前新聊天不会自动重开已结束的旧委派；`follow_up_delegation` 是正式重新开启委派的路径。沿用 Q1/Q5 的请求归属边界；若用户进一步要求手动继续仍回传旧父代理，需要另行确定该行为。

用户追问六十秒限制是否已中断测试、模型随后如何处理 → 只读数据库和已有日志核对确认报告中的四项任务均为 interrupted/exit code -15；两项真实验收输出停在 Codex deep research 端到端测试，此前六条 Codex 实机测试已通过。另一次全套验证在浏览器阶段将输出重定向到文件，外层静默被停止。四项结果均以 `[bg-task-result]` 回到父会话。模型实际补跑过程见 §7。最新 Wiki 实机验收是自然退出的 exit code 1，两个测试失败，与这四次 SIGTERM 终止区分。

全量测试的运行时长不会自动豁免静默规则。经过 bg 启动的后端、前端或浏览器验收都适用；`pytest -v` 的持续输出只能降低触发概率，单条实机测试或重定向输出仍可能静默超过六十秒。直接在普通终端执行、不经过 Octopus BgTaskManager 的命令不受该看门狗控制。

## 7. 手动中断与故障因果

当前 `interrupt` 取消当前 inner task、放掉旧 backend 并清理其进程。下一条消息重新创建 `_Turn/_Attempt`，恢复预算和中间错误状态重新开始；保留原 thread ID 只为继续对话上下文。

因此“模型跑偏 → Stop → 纠偏提示继续”是支持的路径，本身不造成 F1。F1 要求某一次 CLI 调用在中间 error 后已经成功，外层却继续恢复。F2 是委派终态与该恢复执行错位。并发 Stop 与结果清理仍应纳入行为测试，正常路径说明不替代竞态验证。

用户补充的“Stop 后立即处理下一条积压返回”来自现有 FIFO 契约，是新轮次开始而非旧进程没有停止。Q10 已明确改变该行为：Stop 暂停派发并保留结果，人工纠偏先执行，明确恢复之后才处理积压。
