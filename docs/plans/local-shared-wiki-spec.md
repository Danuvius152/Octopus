## 1. 问题与目标

沿用 Octopus 和 Sapphire 现有主库，让同账户各 agent 在用户明确点名知识库时准确查证，让 Weber 在明确范围内整理知识，同时保留人的作者身份、观点与编辑权。

共享 memory 和统一总摘要曾污染无关任务。本方案以显式任务、索引定位、按需读取和受控发布解决这个问题。库规模较小，采用本地索引和现有框架能力；复杂度由实际检索质量与恢复需要决定。

## 2. 用户入口与职责

| 入口或动作 | 行为与写入范围 |
| --- | --- |
| `/wiki <问题>` 或本次消息查询开关 | 当前 agent 查库、读证据、回答；查询只读 |
| `/wiki maintain <新材料>` | 原样接收新材料，去重，保存新文件并交 Weber 整理 |
| `/wiki maintain <本次新建文件清单>` | 校验真实创建记录，只整理本次新增文件 |
| `/wiki maintain <明确指定的旧文件>` | 独立维护任务，只整理指定文件 |
| Sapphire 普通保存或直接编辑/新增 MD | 更新检索索引，不启动整理、总结或再次入库 |
| 后台定期维护 | 清理过期备份、冲突候选与无引用对象，不改知识正文 |

`/wiki` 是 Octopus 聊天命令，与现有 `/research`、`/model` 同类；不是 shell 程序，也不依赖在每个 CLI 中安装原生 Codex skill。没有材料或明确范围的 maintain 请求不能默认变成全库整理。不另设 `/wiki submit` 用户入口。

框架负责共享接口、索引、任务授权、持久队列、范围检查、版本与文本恢复；MCP 是执行接口；按任务加载的指南负责查证与写作。Sapphire 负责人的阅读、编辑、附件与 Git 功能。Weber 保留智者、读书和思考伙伴身份，不承担所有查询流量；其他 agent 直接查询，正式整理与发布绑定实际 curator 身份。

## 3. 主库、组织与访问边界

### 3.1 一份权威内容

主库沿用 Sapphire `.data` 的现有 repo。Markdown 的原文和 Weber 补充共处同一文件，不新建另一份需要同步摘要的权威库；普通 TXT/HTML 原件保留，需要整理时建立有明确来源的阅读页。

框架 `wiki/` 保存三类数据：

- 可重建的文档、章节、词法检索和链接索引；允许必要的派生文本或倒排数据。
- 必须保留的稳定文档身份、生成区 ownership、任务、创建凭证和恢复状态。
- 仅实际修改文本的有限历史与冲突候选。

当前 SQLite 同时有派生和持久表，不能把整个 `index.sqlite3` 删除后声称只是重建缓存。新的索引版本迁移只重建派生部分。主库与索引、少量历史都会占空间；要去掉的是附件和全库正文的冗余快照，不承诺派生数据零存储。

### 3.2 文件与内容边界

旧文件名、目录、附件路径和既有链接保持。目录承担大类；新笔记优先复用 `Library` 的合适分类，无匹配放 `Library/Inbox`。标签表达细粒度概念；补少量可靠的中英文名称、缩写或别名，保留已有元数据，不制造译名和同义词清单。

普通笔记、文章、报告参与默认检索。工具技能、tmp、临时提取、配套静态文件保留为资产，明确需要时可读其文本或关联图片，不自动套模板。PDF 本轮仅保留原件、路径与既有引用，不提取、OCR、总结或以模型推测内容。视频、源码、配置和字体不蒸馏。

### 3.3 显式任务

意图逐消息保存，沿用现有队列、重试、恢复、可信委托和 app 结构化调用。普通下一条消息关闭新访问授权；先前已读内容仍可能在会话历史中，不能称为清除记忆。正文、引用、app context 和资料中的命令字样不产生授权。

常驻上下文只放简短能力说明及 Weber 的简短表达原则，不放主库目录、全文、全库摘要或共享 memory。账户、会话、有效任务、curator 身份和写入清单由服务端检查。保留同账户可信协作边界：知识接口的限制不等于 OS 强制禁止原生 shell 读写文件。

## 4. 查询契约

### 4.1 检索实现

采用可增量维护的**本地中英文章节索引**。标题、路径、可靠别名、标签、Key note 和原文章节共同帮助定位；检索基于已整理文章，但尚未整理的普通笔记也能搜索，整理状态不取代相关性排序。

建议沿用 SQLite，加入 FTS5 章节索引与轻量中文预分词/字符二元组兜底，采用字段权重与 BM25；精确路径、标题和别名优先。分词器具体选择由开发者用验收语料证明，不需要再向用户确认。要求：

- 连续中文、两个汉字的概念、自然问句、学术英文、缩写、连字符术语及中英混合可检索。
- 索引与查询规范化一致，保留词序和频次；命名对象优先原词与可靠别名。
- 不靠每次 Python 逐行读取全部已缓存正文来评分；不只索引 Key note，也不以任意中文碎片的 OR 命中冒充语义检索。
- 章节片段返回稳定文档身份、当前路径、revision、标题/章节、位置和分页；索引片段是导航，引用证据读当前文件。
- 当前文件新建、修改、删除、改名及整理发布更新受影响索引和链接关系。直接文件变更可用轻量 stat 差异检查发现，只重新解析变化文件。
- 索引失败或版本落后明确报告，不把失败当“库中没有”；索引损坏可重建派生表，持久任务、身份与 ownership 保持。
- 接口尽量兼容现有搜索和阅读返回字段；必要新增章节定位字段应同步 OpenAPI、MCP、app 文档与测试。
- 不预先安装向量服务、独立图数据库或全文重排模型。只在真实评估发现必要缺口时考虑额外引擎。

默认 unicode61 不能直接切开连续中文，FTS5 trigram 的 MATCH 不能匹配少于三个 Unicode 字符的查询，需实际验证中文处理。[SQLite FTS5](https://www.sqlite.org/fts5.html)

### 4.2 agent 的查证流程

`问题定位 → 索引检索 → 读取必要原文 → 按具体证据缺口扩展 → 回答并引用`。

1. 保留用户原措辞与命名对象，先查文章名、术语或研究问题；必要时补有限、可靠的中英名称、缩写和别名。
2. 候选元数据、Key note 和概念/导航页帮助选读；通常从 1–3 个最相关候选开始，这是起步建议，不是总篇数或轮数上限。
3. 局部问答读取命中章节及必要上下文；整篇总结、评价或整体论证讨论完整读目标文章；多篇比较读各方理由、条件和反例。
4. 只有缺少定义、证据、适用条件、出处或另一方观点时才扩展搜索/沿链读取。证据足够就回答；上下文不足时准确说明阅读覆盖。
5. 没有相关知识前完成合理原词、别名检索与必要目录定位。未命中不自动开启外部研究；一般背景与库内观点区分。
6. 自然回答并附实际已读位置的可用引用。普通回答不输出内部工具流水账；过程与排名细节按用户需求或诊断显示。

Key note 是有用的整理层，不是替代当前正文的证据。人工小修改后，既有要点可能不覆盖新内容，回答以最新正文为准。禁止将 AI 摘要再摘要的链条当独立来源；多个派生页来自同一来源不变成多份独立证据。查询结果不自动写回主库。

这借鉴 my-wiki 的原词/别名查找、概念导航与来源查证，以及 Pika 的章节索引与分批读取；不复制固定三篇/三轮限制。参考核查见[研究补充](../research/local-knowledge-agent-practices.md#9-q37q53-后的参考核查与采用边界)。

## 5. 维护契约

### 5.1 范围与去重

`明确请求 → 去重与固定范围 → 完整读取最新版 → 整理和必要关联 → 意义自检与冷读 → 发布并更新索引`。

- 日常入库只修改本次新增笔记。旧文、旧概念页、导航和旧反链保持只读；派生索引展示反向关系。
- “本次新增文件”使用框架已验证的创建凭证；幂等键、当前 revision 与创建记录校验继续保留。
- 同键同请求复用原任务；同键不同请求返回冲突。**不同幂等键的完全相同材料也复用已有文档**，返回其位置，不重复建文件或重新整理旧文。
- 内容去重比较完整接收的原材料，已有整理笔记应排除可信的 Weber 生成区后比较原文；不把摘要相似当原文相同。最低保证逐字相同的材料去重，不擅自语义合并。
- 相似但不同的材料可新建且只补必要关联；同名不同内容不覆盖、不自动合并。明确用户指定重新总结时才安排已有笔记的再次维护。
- 批次新增的必要概念/主题入口须有独立阅读价值并属于获准的新建范围；不逐篇复制来源卡，不为模板齐全造空页面。

### 5.2 内容、模板与写作

已有段落、标题、数字、公式、代码、引文、frontmatter、用户总结、立场与核心观点逐字保留。需要逻辑组织时补标题、元数据和关联；重排只能保留全部原始片段，保持既有锚点与链接。文件搬迁不是正文整理的一部分。

开头使用 `Key note`。已有**实际可用**的开头要点则沿用；存在“摘要/总结”标题并不足以证明内容可用。原总结始终保留，必要补充明确归属 Weber。新增要点保留判断强度、适用条件、理由与反例，篇幅由内容决定。

标签、别名、解释与关系只在有用时补。新增解释、推断和跨文档综合允许，注明性质和依据，不虚构作者、时间、引文、经历或可靠程度。自检自身新增内容的含义，再冷读新增内容及必要上下文；不强制逐篇独立模型复核，不把结构 lint 当语义证明。对用户已有 AI 总结不默认逐句重新考证。

维护时加载适配自 Pika 的写作改写与作者风格校准规则；这些规则只改本次可新增的内容，不给改写旧正文的授权。风格依据可靠、同文体的作者文字；没有依据用自然中文，不把转载、引文、AI 扩展或参考项目作者档案当本用户文风。

### 5.3 特别相关的 wikilinks

入库时可以自动检索并补 `[[关联]]`，但只有**特别相关**的笔记：

- 同一具体研究问题、对象、论点或方法，且从两篇已读正文找到可说明的关系依据。
- 同文件夹、同大标签、泛泛同属“AI/学习/数学”只帮助发现候选，不足以添加关系。
- 搜索少量最相关候选，读取必要章节，写一句具体关系；没有可靠候选就不加，不设链接数量下限。
- 新增链接采用 `[[笔记]]`，目标重名时使用能唯一定位的库内路径；章节/块锚点实际存在。保留原有 Markdown 链接及原有坏链，不借维护批量改写。
- 新链接只写获准的新文或明确指定的维护文件；关联到旧文不授权修改旧文。链接本身不是已阅读证明。

### 5.4 并发冲突、人工编辑与完成

维护开始完整读取目标最新版。排队后或发布前正文变化时，在**同一已经授权的维护任务**内重读最新版、重新整理后再尝试发布，范围保持不变。重读后覆盖检查基于新 revision，旧阅读覆盖不能继续用于发布。

自动重试必须有上限；建议最多两次重读重试，由实现固定并测试。持续变化、失去可靠 ownership 或无法安全保护人工内容时，保留候选和原因并报告需处理，不能无限循环或以旧版覆盖。

维护重试与普通编辑是两回事：已整理笔记的小修小改只更新文件和检索索引，保留已有整理与状态，不自动再次入库或总结。直接新增 MD 同样先可检索，只有明确 maintain 才整理。人工修改过的生成区视为需保护的人工内容；重读最新文件不意味着恢复旧 AI 文字或覆盖用户改动。来源漂移可作信息提示，不应强制重新维护、阻断检索或把普通编辑误报为未入库。

一项完成必须同时具备：完整目标阅读、原文保全、必要的要点/元数据/特别相关链接、自检与冷读、实际发布、索引更新。没有必要新增的字段或链接不强填。最终列实际文件、补充内容、重复复用和未完成原因；模型一句“已整理”不构成完成。格式、链接和版本检查只能证明对应机械保证。

## 6. 有限文本历史与清理

### 6.1 保护什么

框架仅为**实际修改的普通文本笔记/阅读页**保存必要的恢复内容、版本、caller、原因和 ownership。save/upload/rename/delete/restore 根据具体文本路径处理，改名兼顾前后路径及稳定身份；不在每次操作前后遍历、读取和保存全库附件。

图片、PDF、视频等附件的备份、删除、回收站与版本管理由 Sapphire 决定。框架不增加附件 blob，也不替 Sapphire 自动 commit/pull/push。Git 相关操作只按实际工作副本变化更新文本身份与索引；频繁 Git 提交不是框架数据库的备份机制。

直接绕过接口的文件编辑可被索引发现，但框架锁不能约束外部编辑器，也无法保证取得每次外部编辑前的字节。不以这项限制禁用用户正常编辑。

### 6.2 保留规则

- 普通文本备份保留 30 天，每篇最多 10 个不同历史文本版本；重复 hash 不额外占版本名额。当前主库正文不是待删除的历史版本。
- 仅尚未解决的冲突候选保留 90 天；已解决候选及时退出保护集合。过期后接口准确表示无法恢复，不留可用恢复按钮或悬空引用。
- 执行中任务、prepared 写入、崩溃 journal、恢复所需数据，以及仍使用中的创建凭证受保护，不能被时间/数量清理误删。
- 复用现有内部 scheduler，每日运行清理，启动时补执行；这是确定性后台工作，不调用模型，不增加默认 Weber 文章整理日程。
- 清理持有相同库锁；记录回收对象数、字节与异常，任务可重复、可中断恢复。先判断引用根与保留规则，再删除无引用对象。
- 清理只针对 Wiki 文本历史及候选，不删除主库正文、附件、持久身份/ownership、任务凭证或验收交接目录。

### 6.3 退役已有全库快照

用户已同意在新机制验收后退役现有冗余全库快照，取消其整库恢复能力，再回收无引用对象。约 542 MiB 只是本次核查估计，不能作为固定回收量。

执行前核对当前原件、保留文本恢复与所有有效引用根；在隔离库完成文本恢复和 GC 验证，再在真实库记录迁移前后清单、容量和保留项。不能直接删整个 `wiki/`、整份 SQLite 或全部 blobs。旧库批量整理改用实际修改文本的逐文件恢复记录，不再创建覆盖全部二进制的快照。

## 7. 兼容 Sapphire 与定制 Weber

现有满意的 `/wiki` 前端保持。沿用框架 app 网关与现有认证，不新建索引或模型运行器。普通保存与显式入库的入口保持分离；入库并整理是统一 maintain 流程，原有保存接口与知识接口不能对同一次操作重复写。

Sapphire 现有 Git、附件、回收站功能保持 app 所有权；必要代理调整只为准确识别文本修改、同步索引和避免扩大备份。历史保留期、冲突重试及旧快照退役的能力变化须同步接口文档，已过期恢复入口不能假装可用。

Weber 已配置实际 persona。开发先验收框架，再对照当前 persona 做必要小幅合并更新，保留其模型、reasoning、backend、凭据、私有记忆、会话及用户新增定制。常驻保留智者、文章理解、独立思考、跨领域联系及简短表达原则；完整管理、检索和写作步骤随任务加载。提交入口不应加载只在 curator 发布时使用的全部写作规则。

Sapphire 新增 UI 在 app Iterate 内开发；本轮文档不要求接手框架 agent 重做其界面。

## 8. 验收

使用可外部观察的保证，至少覆盖以下场景：

| 场景 | 通过条件 |
| --- | --- |
| 普通聊天与下一条普通消息 | 无新 Wiki 调用、无知识摘要注入，旧 token 失效 |
| 中文/英文与章节细节 | 原词、两个汉字、同义提问、可靠别名、缩写、中英混合及正文后半部分可定位；同目录噪声不挤掉相关结果 |
