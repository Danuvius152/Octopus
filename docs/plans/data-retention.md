# 数据保留、依赖与清理预览

> **Status:** proposed — 先明确数据分类、引用和保留责任，提供干运行预览，再单独选择清理政策。

默认继续保留现有历史。写下本计划不授权删除聊天、文件、账户数据或生产资料。
上游消息保留目标在本分支还涉及输入 receipt、原生历史、附件、spill、来源结果
与 Wiki 恢复责任，不能只按 message 时间批量删除。

## 第一段：分类、依赖与预览

按实际持久根列出用户内容、结果/恢复证据、可重建缓存和日志。每类写明 owner、
引用者、保留默认值及可删除条件；使用[当前存储合同](../implemented/current-storage-format.md)
和[账户搬迁](../backup-and-migrate.md#account-export-and-import)的真实收集/排除规则，
不另造一份凭目录名猜测的资源清单。

预览针对一个明确范围列出预计删除对象、体积、仍被保留的原因及依赖链。活跃
工作、原结果读取、原生历史、来源引用、备份/恢复材料未退出前不能进入可删集合。
预览与真正执行之间的并发变化须在使用点重检，不能把昨天的清单当成今天的许可。

当前 Monitor 自己的保留窗口不代表主库与文件已经具有统一清理政策。
[会话文件生命周期](../../server/sessions/lifecycle.py)已有删除责任是盘点依据，
不能从某条删除路径推导其余根都可独立清理。

## 调度历史

auto-archive 只隐藏会话，不缩减历史。选择保留范围时按账户和时间/数量预览，
跳过未决输入、活跃工作、退休未确认、当前 last-run 及被其他业务引用的会话。
真正删除复用现有 owner，分别说明 DB 历史、附件、spill 和原生/fork 工作副本。
session 行存在或已归档不证明副本可再生：未提交改动、原生恢复与唯一文件仍
可能只在那里。备份以实际引用/内容/身份清单为准，不盲目排除副本。

## 之后才选择的清理政策

自动清理需明确用户选择、时间/体积范围、例外、执行 owner、失败后的可见结果，
以及如何保护正在变化的引用。历史删除、日志轮转与缓存重建分别交付；预览页
不隐藏实际删除动作。可重建不等于重建成本为零，报告收益与恢复成本。

账户删除与 crypto-shred 单列政策子项。当前 disable 不等于删除数据；若提供
删除，须分别说明活跃工作、密钥/秘密、外部授权、文件和既有备份。删除一个
DEK 不能概括为所有副本和外部 provider 数据均已消失。

## 完成条件

对一个选定范围，预览能准确解释删除候选与保留原因，活跃工作和保留结果引用
的文件不被误列。导出/备份与恢复边界完整，跨账户无可见或可删旁路。只有后续
已选择的实际清理范围才验证执行、中断和并发重检；本阶段不改变保留默认值。
验证遵循[测试政策](../testing.md)，不以生产删除验证计划。
