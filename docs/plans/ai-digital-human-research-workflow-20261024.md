# AI 与数字人研究工作流改进计划

> **Status:** proposed — 对照 Pika 的行为流程与 prompt，改进研究证据、PDF 转 Markdown、阅读写作与 Wiki 续接；面向 AI 与数字人。

日期：2026-10-24。本文是后续设计建议，未实施功能变更。Wiki 当前合同仍以[开发总结](wiki-development-summary.md)和实时操作卡为准，应用整合仍由[Wiki 未来计划](wiki-future-plan.md)管理；本文只补充研究工作流的改进，不另建一套 Wiki 规则。

## 1. 建议先做什么

**优先让一次研究留下可核查、能接着使用的依据，再扩展检索渠道或增加 agent 数量。** 你现有的 Wiki 已经有当前版本读取、来源关系、范围受控的维护、历史保全和终稿冷读；research 已有问题拆解、并行检索和主动反证。最值得补的是两者之间的研究语义：一个结论在什么条件下成立，哪些证据支持或反对它，已经试过什么，以及下一步要解决哪个缺口。

Pika 最值得迁移的做法有四项：

1. 需要信息时先复用适用的研究资产，缺哪部分再查哪部分。
2. 保存有用的失败、限制和重启条件，让后续研究能够接着做。
3. 区分“材料已保存”“来源支持该表述”“实际复现成功”和“可以推广到其他场景”。
4. 按任务选择行为和交付物，写作时保护含义，再校准体裁与表达。

这些原则主要来自 MRS 的研究与保留流程，以及 Obsidian 的写作与交接约定。[参考研究流程](/home/jack/ref/pika_math_learning_toolkit-2.1.6/payload/math-research-solve/references/core-workflow.md)、[写回交接](/home/jack/ref/pika_math_learning_toolkit-2.1.6/payload/manage-personal-knowledge/references/writeback-handoff.md)

落到你的方向，优先服务三类实际任务：**比较论文和方法、把研究想法转成可区分假设的实验、根据新结果更新已有认识。** 数字人可以涉及形象生成、驱动与动画、语音、交互和系统整合，不能把这些都压进同一套指标。具体分支由当前问题决定。

**PDF 转 Markdown、原页核读和基于材料写作，应作为第一批材料准备能力。** Wiki 继续负责 Markdown 维护；上游负责将论文处理成保留来源、结构和必要图表的 Markdown，并说明转换与阅读的实际覆盖。两者可以分开实现，不必先把 Wiki 改成 PDF 解析系统。

## 2. 对照后的判断

| 方面 | Pika 的可迁移做法 | 你的现状与改进判断 |
| --- | --- | --- |
| 任务入口 | 不同请求进入查询、研究、续接、审阅、归档等不同流程；默认 prompt 直接说明该做什么 | Wiki 已区分查询与维护；research 的 scope 主要把问题拆成搜索词。补上交付目标与任务类型，简单查证继续走短路径。 |
| 既有知识复用 | 使用旧结果前重读必要材料，核对条件与状态；不足再补外部信息 | Wiki 查询已支持这种原则。research web leaf 不继承 Wiki、memory 或 MCP，需要主会话向研究任务传递有界的已读上下文。 |
| 证据表达 | 结论、条件、材料、历史和适用范围关联保存 | research 的 `Finding` 当前只有 claim、url、angle、verification。应增加定位、来源版本、适用条件和证据关系。 |
| 反证与失败 | 有价值的失败、撤回和修正留在历史中 | 已有主动反证，不能再把它写成缺失能力。真正的缺口是 refuted finding 被排除后，其证据与理由没有进入最终结构化结果。 |
| 独立性 | 外部评阅、自查、独立评阅分开；不同名称不证明独立 | 当前 research 用多次核验的显式正向多数决定 verified；不同搜索角度也参与排名。应保留该机制的真实含义，不能把调用次数或角度数解释成独立来源数。 |
| 研究续接 | 记录尝试、反馈、限制和何时值得重开；复用未变材料 | research 已保存报告并回传会话，但尚未在所读实现中形成项目问题、实验记录与历次结论的结构化续接。 |
| 来源更新 | 只检查受影响关系，不把所有历史重做一遍 | Wiki 已有直接来源版本和 changed/missing 等观察。应在其上增加具体结论的影响说明，而非另建来源身份系统。 |
| 写作校准 | 先保护含义，再按体裁与可靠作者样本调整；第二遍连续冷读 | 你已有原思想保留、归属区分和冷读。增量价值在研究笔记、论文相关工作、实验记录的不同写法，以及可检查的语义保留项。 |
| 检索评估 | 区分定位正确、证据充分、覆盖缺口、速度和模型成本 | 你的 Wiki 计划已包含类似评估。补 AI 与数字人研究案例，不重复建设一个通用评测平台。 |
| PDF 材料准备 | 文本层优先、逐页定位、明确 OCR 与索引边界、命中后核读原页 | 值得作为 Wiki 前面的输入流程。参考包的文本提取不等于完整 PDF→MD；转换质量、结构恢复与原页映射需要补足，详见 §5.4–5.7。 |

现状依据：[research schema 与 prompt](../../server/research/schemas.py)、[研究编排](../../server/research/orchestrator.py)、[leaf 上下文](../../server/research/leaf.py)、[报告保存](../../server/research/manager.py)、[Wiki 直接依赖观察](../../server/wiki/maintenance_dependencies.py)。

有两个细节决定了优先级：

- `verify_prompt` 要求核验者输出 `note`，但当前编排仅消费 verdict 和 positive verification，核验理由没有继续传给综合阶段；被否定的条目也不在 `ResearchReport.findings` 中。对研究选题而言，“为什么这条路线不成立”有时比又一条正向结论更有用。
- 当前测试允许所有搜索 leaf 失败后仍生成一份报告。保留有缺口的交付是合理的，但需要让用户区分流程结束和问题已有充分依据；不能只靠最后一段 prose 自觉说明。[现有测试](../../tests/test_research_orchestrator.py)

## 3. AI 与数字人需要怎样的证据

### 3.1 先判断能不能比较

建议方法比较先生成“比较条件”，再组织优劣结论。字段按问题选择，不要求每篇论文填写所有项。

| 问题类型 | 需要核对的条件示例 |
| --- | --- |
| 生成、重建与渲染 | 输入模态、训练与测试划分、身份是否见过、分辨率、单帧或时序、预处理与后处理。 |
| 驱动、动作与口型 | 驱动信号、个体适配、跨身份设置、时序窗口、同步指标的实现、测试素材范围。 |
| 语音与对话 | 语言与说话人范围、流式或离线、首包与完整响应、打断条件、评测协议。 |
| 系统性能 | 硬件、精度、batch、输入长度、缓存和预热、测量起止点、端到端或单模块。 |
| 用户体验 | 参与者与任务、对照方式、评分或观察协议、是否仅有精选展示。 |

以上是待采用的研究检查项，不是对某个现有模型的性能结论。对不可比的实验分组展示，缺失条件写明缺失。例如，单模块吞吐量和包含输入处理、生成、渲染的交互延迟，回答的是不同问题，不能根据这两个数字直接宣布谁更快。

### 3.2 不把所有核验压成一个标签

建议分别记录以下信息，避免将它们误排成一个单调升级的等级：

- **谁提出结论：** 论文作者、代码文档、第三方报告、用户观察或本次分析。
- **来源是否支持这句话：** 支持、反对、存在争议、尚不足以判断，并保留证据位置。
- **是否执行过实验：** 未运行、运行失败、部分完成、完成；关联真实运行记录。
- **在哪些条件下观察到结果：** 数据、版本、配置、指标和局限。

“论文确实写了这个结果”只验证了转述；本地复现验证的是指定条件下的行为。同行评审、公开代码、demo 和独立复现各自提供不同信息，都不能自动替代另一项。

### 3.3 让实验记录帮助下一次选择

保留能解释结论的代码版本、配置、数据划分、指标实现、随机性控制、实际输出和必要失败材料。模型或数据太大时保存稳定位置及可取得性说明，不默认复制权重、完整数据集或所有日志。

每个值得保留的失败应回答：尝试了什么，实际发生了什么，失败可能属于方法、实现、环境、资源还是评测问题，目前还不能排除什么，以及什么变化会使重试有价值。一次运行失败不能自动推翻方法假设。

## 4. 建议补上的行为流程

### 4.1 先确定交付目标，避免所有问题都启动深研究

| 用户意图 | 默认行为 | 足够完成的标志 |
| --- | --- | --- |
| 查一个事实或出处 | 定点查当前一手材料，已有适用依据可复用 | 直接回答、位置准确、必要限制清楚。 |
| 理解一篇论文 | 根据所问范围解释问题、方法、证据和局限 | 读过支撑解释的范围；整篇总结或评价时覆盖全文。 |
| 比较方法或调研方向 | 分解比较轴，查多个必要来源，核对比较条件 | 各关键问点有依据或明确缺口，能说明选择理由。 |
| 讨论研究想法 | 分开假设、已知依据、竞争解释和可判别实验 | 给出值得做的下一步及不同结果的含义。 |
| 复现实验 | 按已授权目标核对代码、数据、环境、执行及结果 | 留下真实执行记录；未执行部分明确标注。 |
| 继续旧项目 | 重开问题入口、相关结论、失败和未决项 | 只补当前缺口，说明新证据改变了什么。 |
| 更新 Wiki | 将具体材料、来源、目标和保留项交给现有维护入口 | 以实际维护回执和最终结果为准。 |

这些是可组合的任务行为，不要求先问用户七选一。能从上下文判断就直接推进；只有目标存在实质冲突、会改变研究方向时才澄清。

### 4.2 先接上已有研究，再补缺口

主会话需要本地上下文时，先用现有 Wiki 查询取得相关问题页、综合或实验记录。已读摘要覆盖当前问题就复用；精确数字、冲突或适用条件不足，再读相应原文。随后把研究任务写成“已知什么、缺什么、要回答哪个决定”。

不要规定每次都必须查 Wiki，也不要每次从空白重新做全网调查。指定新论文的局部问题可以直接读论文；明确要求最新进展时则核对当前来源。保留当前来源范围规则，不能以“旧材料够用”为由跳过任务明确要求的联网部分。

### 4.3 让反证留下来

综合阶段接收支持、反对、争议和缺口四类材料。被否定的结论不进入正向推荐，但保留“原主张—反证位置—适用范围—当前处理”。同一论文的官网、博客解读和 Wiki 摘要先标明共同来源；只有确实确认来源独立时才称为独立佐证。

模型投票可以提示哪里需要进一步核对，不能替代证据。两个核验调用看到同一份材料，不会因此产生两份独立实验。

### 4.4 结束时留下下一步，而非再写一遍摘要

研究报告按任务需要留下：当前判断、最关键依据、仍未解决的分歧、最有价值的下一步，以及什么观察会改变判断。已有实验时补充结果与尝试历史。短问题可以只用几句话表达，不固定生成庞大栏目。

进入 Wiki 的内容按后续用途决定：能复用的解释、稳定的方法比较、有信息量的实验结论或待继续的问题。普通查阅不自动创建知识页；已明确要求记录或更新时，在同一授权范围内完成，不再重复征询。

## 5. 实现边界与资料归属

### 5.1 在现有结构中补足证据

建议扩展 research 的结果合同，使每项关键结论能够关联以下信息。这里列的是概念字段，实施时先核现有术语与 schema，避免建立同义对象。

| 信息 | 最小内容 |
| --- | --- |
| 研究任务 | 问题、预期交付、范围、约束、截至时间、相关项目或既有资料引用。 |
| 来源 | URL 或真实本地身份、版本/日期、实际读取位置、短证据摘录、提取或访问限制。 |
| 结论 | 表述、归属、适用条件、支持/反对来源、尚缺什么。 |
| 核验 | 核验对象、实际方法、证据位置、理由和局限；不只有布尔值。 |
| 覆盖 | 哪些问点已回答，哪些因找不到、未读取、访问失败或不适用而留下缺口。 |
| 实验引用 | 实验位置、代码与配置版本、执行状态、结果位置；没有执行就不生成成功记录。 |

保留 `report.md` 一类可读报告，并在任务目录保存与其绑定的结构化证据文件；报告可以包含简短续接段，不再另建一份重复摘要。检索失败、反证及不可比条件要进入证据文件和适当的报告位置。只有确有内容时才保留原始附件，避免把所有中间输出变成永久档案。

模型填写了来源字段并不证明已经读到来源。能取得工具读取记录时，将证据定位与实际返回内容关联；否则保留核验限制，并对关键结论回到原文检查。来源独立性无法判断时保留未知，不按域名或 URL 数量自动认证。

现有完成、通知和进程退出状态继续由原模块负责；研究证据充分性另行表达，不挪用已有生命周期状态。进程成功退出并不等于证据充分。

### 5.2 Wiki 与 research 之间的交接

当前 web leaf 的无 Wiki/MCP/memory 设计应保留。由有权限的主会话先读取，再向研究任务传递小范围上下文：原问题、资料身份与版本、实际读过的摘录、适用结论、待核问题。内部路径和私人笔记内容不直接拼成外部搜索词；只派生完成研究所需的公开概念。

实施需要真正扩展 research 入口及数据流，不能只在 prompt 中写“查询 Wiki”并假设 leaf 已有工具。没有传入本地上下文时，结果应如实体现本次只调查了外部资料。

研究完成后，需要写库的交接包含准确目标、原始材料与来源、结论状态、改动范围、必须保留的内容。继续使用现有 `maintain` 与 worker；research 不新增 Markdown 写入通道，也不把一个 job ID 当作已维护完成。

### 5.3 一份内容只有一个主要存放位置

- **Wiki：** 长期可复用的解释、综合、问题入口和实验结论，继续使用当前主库身份与来源系统。
- **研究任务目录：** 本次报告和证据包，供核验、交付与再次引用；不是另一份自动同步的主库。
- **实验项目目录：** 代码、配置、数据引用和输出，保持原始执行证据；Wiki 保存解释与定位。
- **私人 memory：** 工作约定与位置，不存整份研究知识或重复论文摘要。

先用现有 Topic/Synthesis 或明确选定的项目页承载“当前问题—已知结果—实验—未决项—下一步”。只有真实查询证明需要时再增加专用类型或索引。修正首先检查明确相关的结论；来源版本变化可以触发复核，不能直接把所有下游结论判为错误。

### 5.4 PDF 相关 skill 的可取之处

这套工具的价值主要在读取流程与证据管理。`pdf-problem-search` 负责定位和核读；`manage-personal-knowledge` 提供通用分页文本索引与单文档 OCR；`obsidian-vault-notes` 负责把取得的依据写成可维护笔记。三者职责可以迁移到 AI 论文阅读，无需迁移数学题的公式指纹、定理角色或求解流程。

| 已读材料中的做法 | 对你的用途 | 迁移时的调整 |
| --- | --- | --- |
| 已知文件或资料范围时先缩小范围，索引不足再直接读指定 PDF | 精确查论文方法、实验条件、附录，减少无关检索 | 不照搬固定 top-3、八份 PDF 等配额；按问题所需证据确定范围。 |
| 保留换页信息和从 1 开始的 PDF 物理页码；印刷页码需另行核实 | 读书笔记中的段落、表格和图能回到原件 | 页码从转换阶段保留；缺印刷页码就留空，不按偏移猜测。 |
| 命中后查看局部原文和必要相邻页，不只信排名 | 避免把论文摘要、相关工作或他人结果当作本文实验 | 将“页面角色”迁移为方法、实验设置、结果、消融、局限和附录等角色。 |
| `pending`、`indexed`、`no_text`、`error` 分开，错误不当作未命中 | 清楚知道材料没写、没找到，还是没读出来 | 进一步记录逐页状态；该包的 `indexed` 只要求至少一页有用文本，不能当作全篇转换完成。 |
| OCR 生成新的可搜索 PDF 与 sidecar 文本，保留原文件，不自动更新索引 | 扫描稿恢复与笔记入库可以分别验收 | OCR 成功只表示产物存在；还要核正文顺序、表格、图注和识别质量。 |
| 写回包包含来源、截至时间、结论状态、保护项和文章要求 | 让阅读到写作之间少丢条件与归属 | PDF 来源、转换稿和研究者解释要分别标明，写作不能顺手修补未核实的原文。 |

### 5.5 建议的 PDF→Markdown 流程

这一节是基于参考流程提出的新设计，不是参考包已经具备的能力。完整路径为：**原始 PDF → 按页提取与质量检查 → 必要 OCR/页面核读 → 可追溯 Markdown → 阅读或写作 → 现有 Wiki 维护入口。** 单次问答可以只读需要的页；明确要求整篇转换时，所有页都必须有处理结果与覆盖说明。

1. **确定来源和用途。** 记录原件位置、文件版本或 hash、总页数与要求的页范围，区分全文转换、指定页提取、精读和综述写作。论文题名、作者、年份从可核对材料取得，不从文件名补齐。原始 PDF 保持不变。
2. **按页判断读取方式。** 先利用有效文本层，检查空白、乱码、阅读顺序和遗漏；扫描页或提取失真的页再采用合适的 OCR 或视觉核读。混合文档逐页处理。`-layout` 保留版面空格并不保证语义阅读顺序；OCR sidecar 也不直接等于全篇正文，要与原页覆盖对账。
3. **恢复可读结构。** 识别标题、段落、列表、脚注与参考文献，处理双栏、跨页续段及页眉页脚。只删除已确认的重复版式噪声，不因一句话像标题或重复出现就擅自删改正文。不把全文压成摘要冒充转换，也不为让文字通顺而补写缺失内容。
4. **按研究用途保留图表。** 表格必须保留行列对应、单位、指标方向、脚注和实验条件；简单表可转换成 Markdown 表格，复杂表保留清晰图像并提供已核实的结构化摘录。架构图、消融图、定性展示保留图像或可重开的原页区域、图注和来源。读不清的数字不推测。
5. **保留必要公式。** AI 论文中的损失函数、变量定义和关键符号属于内容保真要求，并不等于引入数学求解体系。能可靠转写时保留公式；不能可靠转写时保留原图及待核标记，不能删除或改成貌似正确的公式。
6. **建立来源映射并核验。** 将 Markdown 段落、表、图与 PDF 的实际页、必要区域或原文片段关联，记录提取方式、已核范围与缺口。每页都记录处理状态；对支撑研究结论的数字、表格、图和条件回到原页核对，其他部分采用与风险相称的检查并披露覆盖。转换完成、视觉核对和语义阅读分别记录。
7. **交付并接入主库。** 产物先落到指定任务目录，报告完整/部分范围、不可读页、图片与引用情况。用户已要求转换并入库时，继续通过现有入口提交 Markdown 及真实来源；仅要求转换或阅读时，交付对应结果。文件生成成功、入库提交、实际维护完成是三个不同事实。

工具选择应以代表性论文上的实际结果决定：正文顺序、关键表格和图像是否保真、定位是否可用、失败能否暴露，以及成本是否合理。当前不指定某个转换器为默认，也不把“换一个更强的模型”当作质量检查的替代。

### 5.6 转换稿、阅读笔记和综合写作分别承担什么

| 产物 | 应保留的内容 | 不能发生的混淆 |
| --- | --- | --- |
| 转换稿 | 来源正文、结构、必要图表、页码映射与识别缺口 | AI 补充解释不能混进作者原文；摘要不能冒充全文。 |
| 阅读笔记 | 作者的问题、方法、证据、条件、局限，以及明确标出的个人分析 | “作者声称”“原文支持”“我的推断”不能混成同一层；引用存在不等于引用对象已核实。 |
| 专题综合或写作 | 围绕当前问题组织跨来源比较、理由、冲突和判断 | 不把多篇摘要拼接当论证，不用同源转述制造共识，不把新解释归给原作者。 |

三种用途不要求每份 PDF 都生成三篇笔记。只读当前问题时直接定位证据即可；需要长期精读时保留可追溯转换稿；明确写作或已有综合页需要更新时，才生成或修订对应内容。

阅读流程可分两层：先取得真实目录、摘要与章节概况帮助定位，再为当前问题读方法、实验、结果和必要附录。局部问题到证据充分就结束；整篇总结或整体评价须覆盖全文，并将未能读取的图表、补充材料或页面作为具体限制。不要固定每次都追完所有参考文献；某条关键结论依赖被引论文时，再读其原始出处。

写作时先确定段落的作用：解释概念、说明方法、支持比较、指出限制，还是提出下一步。阅读取得的材料按这个作用组织，新段落脱离聊天也应能读懂。引用贴近它支持的句子，数字、比较条件和来源版本随结论一起保留。笔记可以使用直接链接和页码；正式论文按目标文体使用所需引用格式，不照搬参考 skill 对某种文献标签或“资料来源”标题的偏好。

写后先核对含义、来源和图表，再连续复读语言。重点查“may→必然”“在该数据集上→普遍”“作者报告→已经独立证实”等强度变化，也检查双栏错序或 OCR 误字是否被润色成了看似合理的内容。转换疑点交回原页核验，不能只靠行文流畅掩盖。

这些写作做法依据参考中的[文章修订要求](/home/jack/ref/pika_math_learning_toolkit-2.1.6/payload/obsidian-vault-notes/references/article-revision-style.md)与[来源标注要求](/home/jack/ref/pika_math_learning_toolkit-2.1.6/payload/obsidian-vault-notes/references/source-citation-style.md)，体裁适配与 AI 论文场景是本计划的迁移建议。

### 5.7 接入 Markdown Wiki 的最小交付

一个转换任务至少交付可读 Markdown，以及能重开原件的来源与覆盖信息；存在必须保留的图表时再附相应资源。映射较少可放在文内，较多则保存在任务目录的配套文件中，避免把大段工具日志放入正文。

建议来源信息覆盖：原始 PDF 身份与版本、PDF 物理页码、必要章节/图表号、转换稿版本、局部定位、提取/OCR 方式、已处理与已核对范围、缺失与待核项。字段应接入现有来源机制；这些是设计需求，不是当前 Wiki 已支持的新参数。文字、图片、转换稿和笔记来自同一论文时，保持同源关系。

每份原件与版本的转换应可识别重复请求。再次转换不覆盖已经人工整理的 Wiki 正文；原件更新时生成新的转换结果，核对来源映射与变化，再按指定范围维护。原始 PDF 继续作为只读原件或附件，Wiki worker 消费可读的 Markdown 与真实来源交接，不需要获得 PDF 改写职责。

来源转换服务负责 PDF→MD、图表资源和映射；阅读行为负责证据理解与已读范围；写作行为负责成文与引用；Wiki 负责现有 Markdown 发布和维护。初期可共用一个入口并按需加载行为，无需为了这四项职责立刻建立四套独立服务或四份重复 prompt。

## 6. 可迁移的 prompt 设计

Pika 的默认 prompt 有一个值得学的特点：直接说明任务行为及边界。例如 MRS 强调从证据图继续研究、保留有用结果与失败、区分历史与当前可用结论；知识管理入口强调覆盖范围和必要回退。这比单纯要求“专业、全面、深入”更容易检验。[MRS 默认 prompt](/home/jack/ref/pika_math_learning_toolkit-2.1.6/payload/math-research-solve/agents/openai.yaml)、[知识管理默认 prompt](/home/jack/ref/pika_math_learning_toolkit-2.1.6/payload/manage-personal-knowledge/agents/openai.yaml)

以下是面向你的场景的候选行为文本，不是已经安装的 skill。实施时由一个位置维护通用规则，按任务加载所需部分；入口只表达用途，不复制整套流程。带条件比较、证据保留和跨任务续接，需要第 5 节的数据支持，不能只靠 prompt 承诺。

### 6.1 通用研究入口

> 围绕用户要理解、比较或决定的具体问题推进。需要背景时，复用已读且仍适用的 Wiki 和项目资料；缺失或可能变化的部分再查一手来源。保留命名对象、范围、版本及限制。区分作者主张、来源能够支持的事实、本次推断和用户尚待验证的假设。简单问题直接完成，只有多来源调查确有价值时启动深研究。按当前任务交付答案、比较、实验方案或续接说明。

### 6.2 论文精读与方法比较

> 先说明论文回答什么问题，方法为何可能有效，关键结论由哪些实验支持。对影响判断的结果，读到相应方法、实验设置、表格或附录；没有读到的位置不作已核验依据。整篇总结或评价须覆盖同一版本的全文，材料不可得时保留缺口。比较方法时先核数据划分、输入条件、版本和指标协议；性能比较再核硬件及测量边界。分开直接可比、条件不同和信息不足的结果。结论应能帮助当前研究选择，并指出最可能改变选择的证据。

### 6.3 研究想法与实验设计

> 把想法写成一个可以被观察结果支持或削弱的假设，说明已有依据和最强的竞争解释。提出一个投入与问题价值相称、能区分这些解释的实验，明确基线、变化因素、保持不变的条件、评测方式和结果解释。根据问题决定是否需要多次运行、消融或人工评价。区分计划、执行和分析；没有运行过就写成实验方案。不要为每个想法强制套同一组实验。

### 6.4 项目续接与新证据

> 先读当前问题和相关结论，核对已有失败、未决项及其适用条件。复用未变且仍适用的材料。新证据到来时，说明它支持、限制、反对或尚不能改变哪项判断，并给出具体依据。保留旧结论的历史和失败原因；不要因新结果较晚就自动覆盖旧结果。结束时说明本次增加了什么、剩余什么，以及下一次最值得做的动作。

### 6.5 Wiki 写作与修订

> 先保护事实、数字、比较方向、否定、因果、来源归属和判断强度，再按笔记用途组织文字。论文笔记解释问题与证据；实验记录保留条件、输出和异常；综合文章说明关系与分歧。沿用当前文本中的可靠表达，不从参考工具的作者画像推断本用户的文风。完成后连续读一遍改动及必要上下文，检查条件是否丢失、表述是否变强、具体内容是否被空泛语言替换。按已有维护范围提交，不扩成整篇重写。

Pika 的作者画像来自其自身语料，其具体人格和文风不能迁移为你的画像。可迁移的是“可靠样本—体裁—含义保护—第二遍检查”的方法。你已有冷读要求，因此此项应补充针对研究体裁的样例和验收，避免增加重复口号。[作者画像方法](/home/jack/ref/pika_math_learning_toolkit-2.1.6/payload/obsidian-vault-notes/references/author-voice-profile.md)、[改写规则](/home/jack/ref/pika_math_learning_toolkit-2.1.6/payload/obsidian-vault-notes/references/ai-style-rewrite.md)

### 6.6 PDF 转 Markdown

> 将指定 PDF 的约定范围转换为可追溯的 Markdown。保留原文件，先检查逐页文本质量与阅读顺序，再对需要的页采用 OCR 或视觉核读。保留章节、正文、脚注、引用和必要图表，不将摘要或补充解释混入转换正文。关键表格保留行列、单位、脚注与比较条件；不能可靠识别的文字、数字或公式保留原页定位和待核标记。记录每页处理结果，建立 Markdown 到原页的映射。交付时分别说明已转换、已核对和未能读取的范围；生成文件不等于已经理解论文或完成 Wiki 维护。

### 6.7 带原页证据的阅读

> 围绕当前问题定位论文的相关章节、表格、图和附录。Markdown 用于阅读和导航；出现关键数字、排版歧义、图表解释或提取疑点时回到对应 PDF 原页。确认材料是在报告本文结果、介绍前人工作，还是提出尚未验证的解释。引用保留论文版本、页码和必要局部位置。局部任务读到足够依据，整篇总结或评价覆盖全文；不足时说明具体缺口，不将检索摘要或转换成功描述为完整阅读。

### 6.8 从材料写成研究笔记或综述

> 按指定用途把已核读的材料写成独立可读的 Markdown。先确定读者、问题和每段的作用，再组织作者主张、支撑证据、适用条件、分歧与本次分析。将引用放在它支持的结论旁，保留必要数字、单位、图表和来源定位；正文中的直接引语、译文和自己的解释明确区分。没有读到的来源不冒充已核实，提取疑点不靠润色补齐。写后对照材料检查含义与判断强度，再连续复读语言与衔接。任务已包含入库时，通过现有 Markdown 维护入口完成对应范围。

## 7. 分阶段实施顺序

每一项被选中实施后，都应完成入口、结果、异常处理和相应验证。这里的阶段是功能依赖，不是先交付半条流程再补质量，也不预设必须完成所有后续扩展。

| 阶段 | 完整交付 | 主要落点 | 依赖与验收 |
| --- | --- | --- | --- |
| P，第一批，可与 A 并行 | PDF→Markdown、原页核读、图表保留及写作交接 | Wiki 外的材料准备入口、任务目录、来源映射与候选阅读/写作行为 | 不依赖重做 Wiki。用代表性 PDF 完成“转换—核读—成文—按任务交接”；双栏、扫描、表格和部分失败可见，人工笔记不被重转覆盖。 |
| A，最高优先 | 研究证据与缺口可追溯：保留核验理由、反证、来源定位和条件；区分流程完成与证据充分 | `server/research/schemas.py`、`orchestrator.py`、`manager.py`；相关 API 与报告展示 | 先定义证据合同。反证不再消失；同源核验不显示为独立佐证；搜索全失败仍可交付缺口说明，但不显示为充分回答。 |
| B，最高优先 | AI 研究行为与 Wiki 上下文衔接：任务路由、按需本地材料、可比性检查、研究结果交接 | 主会话调用规则、research 入口、候选 prompt 的单一维护位置、现有 Wiki 提交入口 | 依赖 A。用一个真实研究问题完成“旧知识＋新证据＋明确结论”；简单查证不被迫启动完整深研究；如任务包含入库，最终回执与来源一致。 |
| C，次优先 | 项目续接与实验记录：复用已有页面类型，保存有信息量的失败和下一步 | 指定研究项目、报告证据包、Wiki 问题或综合页 | 依赖 A/B。在三次连续任务中，第二次识别并利用第一次的失败，第三次能说明新证据改变的具体判断；保持原始实验输出可定位。 |
| D，次优先 | 研究写作质量与真实任务评估：体裁示例、语义保留检查、质量与成本对照 | 现有 Wiki 写作流程及可选 `knowledge_eval` 评估 | 不要求先改写整个库。用保留材料验收数字、条件、归属和判断强度；评估发现的新问题进入回归案例。 |
| E，条件性 | 视频时间段证据、批量资料库索引及更复杂的多模态理解 | 已有材料准备能力的增量扩展 | 基于 P 的真实使用缺口启动；视频时间段和解释依据可重开，不以静态预览冒充完整时序理解。 |

建议第一批推进 **P＋A，再完成 B 的连接**：P 解决论文如何成为可信的 Markdown 材料，A 解决研究结论如何保留依据，B 将二者接到已有 Wiki 和研究任务。P 的转换与阅读可以先独立使用；其结构化证据与 A 的结果合同对齐后再完成研究交接。C 应围绕一个正在做的 AI 或数字人课题验证价值；D 的验收案例从第一批开工时就准备，专门的作者表达校准可以随后单独交付。

职责上，Weber 负责研究行为、内容样例和语义验收；Octo 承担获选实现的接口、数据与产品接入；需要独立技术审查时再明确交给 Vera。本计划没有发起这些委托。

## 8. 怎么判断确实有改进

### 8.1 先冻结一组有代表性的研究任务

建议先准备 12 个任务作为小规模验收集，覆盖下列行为；这个规模用于找问题，不用于宣称普遍最优。开发样例与保留验收材料分开，gold、私有来源路径和期望答案不进入公共 prompt。

| 类别 | 数量 | 必须观察的行为 |
| --- | --- | --- |

### 8.2 质量与成本分别记录

1. **关键结论可追溯：** 每条会改变研究选择的结论都有实际读过的依据、位置和条件；不足的条目明确留下缺口。
2. **结论不越界：** 来源支持转述不冒充本地复现，投票不冒充来源独立，不可比配置不产生无条件排名。
3. **续接有效：** 相关旧结果被正确使用；未变材料是否复用，以实际读取和判断为准，不只统计“少读了几次”。
4. **失败信息保全：** 所选反证、运行失败和访问缺口仍能找回，不因综合成文而消失。
5. **表达保真：** 数字、限制、比较方向、归属和不确定性未被改写改变。
6. **成本可解释：** 记录总耗时、模型调用、实际 token（可取得时）、重复来源读取和失败重试；对同一任务比较，不将并行任务各自耗时相加冒充墙钟时间。

发布验收应要求所选案例中没有伪造来源、虚假复现、越权写库和无条件错误排名；覆盖或来源不足可以作为诚实的部分结果。速度改进只有在证据质量不下降时才成立。

功能正确性用小而确定的测试验证 schema、反证保留、版本变化、失败传播及交接；真实模型内容质量继续使用已有 opt-in `knowledge_eval`，不混入默认单元测试或常规提交门禁。本次计划编写没有运行模型实验或生产库维护。

### 8.3 PDF→Markdown、阅读与写作的六类验收

在原有 12 个研究任务之外，增加下列六类材料案例。冻结原始文件与版本，明确抽查范围；转换器应在同一批材料上比较。无需为验收先处理整份 PDF 库。

| 案例 | 核查重点 |
| --- | --- |
| 双栏文字论文，含页眉、脚注和跨页段落 | 正文顺序正确，脚注归属可辨，页眉去除不误删正文，逐页覆盖可核对。 |
| 扫描论文或质量较差的页面 | 触发适当 OCR/核读，识别疑点保留原页位置；工具退出成功不冒充内容正确。 |
| 有效文本页与扫描页混合 | 不因部分页面可读就宣称全篇完成；转换输出与逐页状态一致。 |
| 实验结果表，含多级表头、单位、脚注或跨页续表 | 指标与方法行对应正确，数值、单位和条件可核；无法可靠转表时保留图像与明确缺口。 |
| 架构图、消融曲线或数字人定性展示 | 图片/原页区域、图注和解释匹配；仅看到图注时不宣称已分析图中内容，不从精选图推断整体效果。 |
| 部分失败、重复转换及原件更新 | 交付真实缺口；相同输入不制造重复主库内容；新版本映射重新核对，不覆盖人工整理稿或沿用失效坐标。 |

每类材料还应完成一个基于其证据的小问题；选其中适合的材料完成一篇阅读笔记或一段综述。这样同时检查文件转换和后续使用，避免只验 Markdown 能打开。转换验收看内容与定位，阅读验收看证据是否支持回答，写作验收看条件、归属和判断强度是否保留。

## 10. What this defers

- **不纳入数学特化：** 定理/证明状态、量词与公式指纹检索、题库、CAS/Lean、数学教练及其专用归档协议。通用研究问题可以发展和分支，不照搬 MRS 的不可变数学目标模型。
- **不复制完整 MRS 基础设施：** 不新建内容寻址研究库、独立版本系统、复杂交换包或每次研究必经的归档审批链。出现真实跨机器交付或多人接力需求时，再依据现有项目存储设计。
- **不照搬“三次失败评审后仍接受”的回退：** 参考工具对此有明确状态区分，但对研究可靠性应继续展示未解决问题，不能用评审次数宣布结论通过；也不为小修改固定增加多 agent 审阅。
- **Wiki 继续以 Markdown 为维护对象：** PDF 转换、图表保留和原页核读已纳入 P 阶段，在 Wiki 前完成材料准备。暂缓的是 Wiki 内直接维护 PDF、无差别整库转换、复杂视频理解和大规模自动索引，不是 PDF→MD 或论文阅读本身。
- **不先上全库语义图和向量重排：** 已有 Wiki 计划的触发条件继续有效，先用真实漏检或续接失败证明需求。
- **不自动全库润色或提取作者人格：** 对可靠样本的风格校准应有具体写作用途，不从收藏、转载或历史 AI 文本推断用户立场。
- **不启动自动定期研究、全量实验归档或生产维护：** 这些需明确的任务范围；本文交付的是后续计划，没有创建日程、修改运行 prompt 或改变现有主库。
