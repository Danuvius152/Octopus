## 2. W01 — 本地中英文章节检索

**依赖：** 已有 store/read 接口。可以先独立在临时库开发。

**实施前已有：** stat 差异刷新、文档身份、文本提取、标题/路径/正文子串评分、分页与当前文件读取。

**需要：**

- 在现有 SQLite 加入可重建的章节与字段索引，保留 durable identities、managed_notes、jobs 和历史状态；不要删整份 DB。
- 索引标题、路径、可靠别名、标签、Key note、全文自然章节；长篇后半部分同样可检索。
- 实现中英规范化和中文切分/二元组兜底，以词法索引和字段权重排序；明确路径/标题/别名优先。分词器、权重等例行技术选择自行验证。
- 搜索查询不再遍历全部正文评分；正文读取仍从当前主库进行，索引片段可定位并标明 revision。
- 保存、发布、改名、删除同步变化文档及派生关系；直接新加/改 MD 下次轻量刷新发现，未变化文件不重解析。
- 未整理笔记可搜索；正文小修改后的已整理笔记保持身份、整理内容和可用状态，不自动排队。来源漂移是提示，读当前正文查证。
- 尽量兼容现有 API，章节字段的必要新增同步 schemas/MCP/前端 contracts。

**完成证据：** 中文短词/问句、英文术语/缩写、中英混合、精确标题/路径/别名、正文细节、比较与无结果等实际查询集；记录预期文档、top-k、无关候选及耗时，并对比当前基线。证明更新/改名/删除及派生表重建不丢持久状态，普通编辑没有 Weber 任务。

**2026-10-12 审查补充验收：**

- 合成反例：长 Key note 与短附录的命中范围必须含真实证据；未知中文名称的字符分别出现或只出现一字不能命中；中英文术语跨长段落分片边界仍可读到完整词；比较文章的不同章节共同覆盖查询词组，不因单章节 AND 被排除，文档去重在分页前。
- 目录列表在 SQL 中过滤、计数和分页；只对本页补当前元数据，保留 source/kind/quality/资产语义。旧、新检索计时使用相同完整操作边界，不能用纯评分与整个 search 相比。
- 私有真实查询：“数字人研究有哪些结论”先原词，再扩展有依据的名称，目标 `Library/Research/vidu_realtime_report/技术报告.md` 应进入约定 Top-3；“那篇 Vidu 论文／实时报告”以对象名/真实题名/可靠别名检索，通过所在目录消歧，完整路径直接读取。记录真实路径、章节证据、revision、读取文件数和耗时，不将合成 smoke 提升为真实验收。
- W06 Codex 实机：“介绍我的背景”“我的职业是什么”先分页定位 `Library/Me` 并读当前材料，缺失事实不猜补；“我的笔记里某术语怎么解释”继续知识检索。实际验证路由、分页和缺失事实，合成 HTTP 测试不能证明模型行为。

**主要接缝：** `server/wiki/store.py`、`extract.py`、`links.py`、`sections.py`，`server/routers/wiki.py`、`server/mcp_servers/wiki.py`，`tests/test_wiki_api.py`。

## 3. W02 — 定向文本历史与 Sapphire 写入桥

**依赖：** 已有共享锁与 history。与 W01 共享更新 hook，集成时协调同一接缝。

**实施前已有：** CAS、原子写入、prepared journal、恢复与 ownership；Sapphire mutation 前后 inventory 会读取全库并保存 blob。

**需要：**

- 框架只备份实际改动的普通 MD/Markdown/TXT/HTML 和阅读页；附件仍由 Sapphire 管理。允许必要的轻量文件清单检查，不保存未改附件。
- 在代理发送 mutation 前解析并复用请求体，以具体 path 确定 save/upload/delete、rename 前后路径与 restore 的原位置。body 只读取一次，不破坏转发、认证或 multipart。
- 当前 restore 接口原路径需从 app 回收站记录核查；实际 app 合约由接手 agent 读代码确认，不凭文档猜。
- Git commit/push 不做框架备份。Git pull/sync 可能异步改变工作副本，要识别实际文本变化并刷新索引；框架不修改 Sapphire 的 Git 策略。
- 保留锁等待不阻塞事件循环、线程取消 join、请求断开后的 journal 完成、异步 app job 监督和 uncertain writer 恢复。
- 新文件保留真实创建凭证；改名延续稳定身份与 ownership。普通编辑不启动 summarize/maintain。
- 历史只保留实际版本；restore 创建新 revision，结构化操作候选不能当正文直接恢复。

**完成证据：** 修改一篇 MD 不读取/复制无关 PDF/视频；附件请求不新增框架二进制 blob；rename/delete/restore、异步 Git 文本变化、冲突与取消/崩溃恢复均有行为测试。证明人工生成区编辑及范围/身份保护继续成立。

**主要接缝：** `server/wiki/history.py`、`app_bridge.py`、`server/routers/applications.py`、Wiki 写入/恢复路由，现有 Sapphire 私有后端合约只读核查。

## 4. W03 — 保留期、每日清理与快照退役

**依赖：** W02。真实库迁移还依赖 W06 新版本验收。

**实施前已有：** 内容 hash 对象、changes/management/proposals、全库 snapshot；没有保留期和 GC。

**需要：**

- 普通历史 30 天/每篇最多 10 个不同历史版本，未解决冲突候选 90 天；相同 hash 复用。时间与计数针对备份，不删除主库内容。
- 明确 GC 引用根：保留历史 before/after、仍有效 snapshot、prepared 写入、external journal、活跃/可恢复任务、未消费创建凭证等；ownership 必须保留，但比较 hash 不一定要求同名 blob 常驻。
- 过期候选、历史及管理快照的清理保持事务一致；保留任务的最小审计/创建信息，防止清理破坏重试和入库幂等。API 明示已过期恢复能力。
- 用现有内部 scheduler 每日清理并启动补跑；库锁、线程 I/O、中断恢复、重复执行和可核查计数完整。无需模型或 Weber 自动文章维护日程。
- 调整现有全库 curate 的 snapshot 依赖，旧库批量整理采用实际文本逐文件保护。
- 新机制验收后，按真实引用关系退役 snapshot `d02ee2b85ffc4cb89f3a1b07b149d15c`，再 GC 无引用对象；保留身份、ownership、任务和实际文本恢复。用户已同意取消这份全库快照的恢复能力。
- 更新 snapshots/history/restore 返回和文档，客户端不能保留失效恢复入口。无需发明未确认的新 endpoint。

**完成证据：** 控制时钟测试 30 天、10 个不同版本、90 天边界及活跃保护；两轮 GC 和中断恢复安全；文本可按保留版本恢复；从旧 DB/快照状态迁移不丢持久数据。真实迁移前后原件清单/哈希不变，记录容量与保护根，不以预计 542 MiB 作为固定成功量。

**主要接缝：** `server/wiki/history.py`、`jobs.py`、`registry.py`、`server/scheduler.py`、启动生命周期、历史接口。

## 5. W04 — 材料去重与维护冲突重读

**依赖：** W01/W02 接口完成；与 W03 一起检验状态保留。

**实施前已有：** 同幂等键复用、真实新文件清单、curator 身份、完整阅读 gate、持久队列和 revision 冲突候选。

**需要：**

- 不同幂等键、不同目标名的完全相同材料复用已有文档，返回其位置且不再次整理旧文。比较原材料或可信剥离生成区后的原文；相似内容不自动合并。
- 同名不同内容保留冲突/明确失败，不覆盖；原有幂等键语义和 creation receipt 校验继续成立。
- 排队后正文变化或发布 CAS 冲突时，在同一任务、同一写入范围内重读最新版并重新整理。刷新当前 item revision 与完整阅读覆盖，不能沿用旧版已读状态。
- 固定有界重试策略，建议两次重读重试；持续变化留下候选/原因，任务真实标 attention/失败，不无限循环。
- 人工已改生成区继续保护。自动重读不能把人工修改抹掉；ownership 不可靠时保留候选并报告。
- 普通编辑不重新入库、不触发新任务；只有明确请求重新总结才更新已整理页。
- actual publish 后索引更新完成才记 done；模型文字、标题存在和纯结构 lint 不足以宣称完成。取消终态与已完成项保持。

**完成证据：** 换幂等键的同材料、已整理同原文、相似不同/同名不同；队列后变化、read 到 publish 间变化、重读后成功、持续变化、取消；人工 Key note 修改不被覆盖；活跃创建凭证/恢复数据未被 GC 删除。

**主要接缝：** `server/wiki/jobs.py`、`curation.py`、`tasks.py`、`sections.py`、历史 API 与任务状态。

## 6. W05 — 查询指南、维护分层与特别相关的 wikilinks

**依赖：** W01/W04 提供真实检索、重试与发布语义。

**实施前已有：** `entry/query/maintenance/writing/curator` 指南，Weber 智者 persona，新增链接校验。当前所有 maintain 调用者仍加载完整写作指南；relations 输出普通 Markdown 链接。

**需要：**

- 按[prompt 设计](local-shared-wiki-prompt-proposal.md)区分查询、提交入口和真正 curator worker。入口只加载范围/去重/排队所需规则，worker 才加载完整维护和写作。
- 查询采用索引定位、按需查证、具体缺口扩展与证据足够停止；1–3 个候选为起步建议，整篇任务完整分页，用户回答不堆工具日志。
- 新 metadata 支持少量可靠 aliases，旧字段/正文不被标准化重写。
- 新增关系输出 `[[...]]`；重名目标用唯一库内路径，章节/块锚点校验。保留既有链接和旧坏链，不批量重写。
- 仅同一具体研究问题/对象/论点/方法且两篇正文有依据才添加；目录/大标签一致不足够。无特别相关候选就不添加，不设最少链接数。
- 检索、读相关正文、加入说明、链接校验、索引反向关系形成完整路径；新文维护不写关联旧文。
- 开头已有要点的“可用”由内容判断；去掉仅凭标题通过的假质量结论。保留原文与作者观点，新增解释/推断标注，自检加冷读；不加入逐篇独立模型审查。

**完成证据：** 同目录弱关系不加、强研究关系正确加、无候选无链接、重名/不存在锚点拒绝、正文实际读取；未指派旧文哈希不变。工具和 prompt 加载按角色/模式验证；整篇阅读与普通查询终止策略通过 Codex 场景检验。

**主要接缝：** `server/wiki/workflow.py`、`prompts/*.md`、`curation.py`、`links.py`、MCP schema、harness assembly。本票不重做满意的前端。
