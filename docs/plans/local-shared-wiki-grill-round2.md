## 已确认的 Q32–Q35 及维护入口补充

用户明确答复 Q32、Q33、Q34、Q35 均为是。

- **Q32 — 资产边界**：普通笔记、文章和报告进入默认知识检索与整理；`Codex Skills/`、临时提取目录和配套静态资产原样保留，默认不作为普通笔记搜索结果，也不插入 Key note。用户明确指定或文章需要关联资产时，可按任务范围读取文本/图片；PDF 仍不处理。
- **Q33 — 新笔记落点**：优先使用 Library 内合适的现有分类；没有合适分类时放 `Library/Inbox`，后续明确维护时再归类。旧文件不迁移，不自动扩建一整套大分类。
- **Q34 — 普通保存**：Sapphire 普通保存更新索引；正文变化时标记受影响的 Weber 整理区待刷新，不自动重写。明确入库与维护动作才更新 Weber 生成的 Key note/关联说明；用户原文与自写要点保留。
- **Q35 — 首轮样稿**：首次整理先展示 2–3 篇代表性样稿与新增部分，用户确认风格后执行已确认范围的批量整理。以后明确入库沿用同一规则，不逐篇人工审批，也不增加独立模型语义复核。该样稿关卡来自用户明确接受的方案，不是 skill 强制要求。
- **日常入库范围**：用户补充“入库并整理”只整理新建笔记，已有笔记不修改。可读取旧文查找关联；新链接写入新文，不能自动向旧文补反链、改标签、Key note 或导航。框架记录本次新增文件清单并校验写入范围；首次旧库整理仍是先前确认的独立批次。
- **入口简化**：用户要求 `/wiki maintain` 足够，提交本来就要整理。用户命令因此收敛为 `/wiki <问题>` 与 `/wiki maintain <材料、文件或范围>`；新材料原样接收、持久排队和整理作为同一维护工作流的内部步骤，不再要求用户额外调用 `/wiki submit`。

## 已查明的事实

### 模板和写作规则

- 2026-10-12 只读清单修正：143 个 MD 中，102 个在 `Codex Skills/` 工具资产树内（6 个技能定义、90 个参考说明、1 个运行环境说明、5 个测试 fixture），工具目录外只有 41 个 MD；71 个 TXT 和 16 个 HTML 在目录外，另 2 个 HTML 属于工具资产。Q27 已接受普通内容与工具资产区分，但 TXT/HTML 的具体用途及默认检索边界需要按下面的新路径事实进一步澄清。
- 目录外 41 个 MD 中，30 个已有合法 YAML `tags` 列表，11 个没有 frontmatter；20 个有 wikilinks，21 个有 Markdown 链接，包含别名、章节/块锚点和嵌入。只有 3 个含摘要/要点/总结/结论标题，1 个在开头 60 行内；没有全库统一 keypoints 结构。已有 `description` 属于 Skill 功能说明，不是普通笔记摘要。
- 只有根目录一个 Library，其中有 35 个 MD、71 个 TXT、16 个 HTML 和 96 个 PDF。目录外六个 MD 为 EndleX.md、Links.md、Notions.md、Recent Plan.md、Year Goals.md、知识库导航.md，均留在原位置。
- 71 个 TXT 中 70 个在课程资料的 tmp/os-research 或 tmp/review_extract 下，另一个在论文配套 static/css；16 个 HTML 中 5 个也在 tmp 下。不能将它们当作 71 篇独立文本笔记和 16 篇普通文章自动套模板。
- my-wiki 的来源、概念、主题模板分别服务证据登记、可复用知识和逻辑导航。模板中 `status: stable`、作者、日期、来源数量等示例不能直接当作真实值。
- Pika 要求辨别原作者、引文、复制来源和 AI 新增段落；保护事实、条件、因果、否定、时间线和判断强度；依据篇章用途和可靠的作者文本校准新 prose；改后连续冷读，并记录范围、依据和不确定内容。
- 这些写作规则适用于本任务允许新增的段落和派生页；参考项目删除或重写旧原文的许可不适用于此库。
- Pika 附带的 `author-voice-profile.md` 称来自 85 篇 `思考随笔`。当前尚未确认该样本集与本用户的作者身份，不能直接认定其具体文风就是用户文风。
- Pika 大幅编辑流程使用独立、只读、针对确定候选版本的语义复核；其第三次失败仍可发布的规则是参考项目的显式定制，不自动继承。

### PDF 方法、版本与本机

- 以下是 2026-10-11 的历史只读研究；因用户 2026-10-12 排除本轮 PDF 处理，不构成引擎安装或处理需求。
- 仍没有实际旧库的 PDF 失败清单；此前代码只实现 pypdf 文字层与页级质量记录，没有运行生产全库提取。
- my-wiki 使用解析器适配、统一中间表示、页级质量、图片与页定位；图像遗漏可补原页渲染，OCR 结果按页和来源指纹缓存，重提取复用原件与原来源身份。
- 其 MinerU 批次使用临时目录并清理，不等于跨重启续跑；Docling 参考 adapter 也没有完整导出图片。学习方法时要补齐这两处边界。
- 参考安装固定 MinerU 3.4.4、Docling 2.113.0、Python 3.11，采用 uv；用户要求 pip/venv，不能照搬。
- 只读实机检查确认 RTX 5060 Ti，8151 MiB VRAM；i5-14600KF，20 个逻辑 CPU，约 15.5 GiB RAM。当前 Python 为 3.14.4，常见安装目录未找到独立 3.11/3.12。
- MinerU 4.x 已正式发布，接口、依赖和输出合同相较 3.x 已改变。`mineru parse` 默认只处理前 10 页，必须明确覆盖范围；完整离线转换入口与旧脚本不同。版本和 CUDA 兼容需要独立环境实测，不能因有 8GB GPU 而承诺任意后端吞吐。
- 参考视觉修复会把选定风险页发给现有模型服务；它独立于本地解析，需要明确决定是否采用。

官方版本和接口依据：[MinerU 迁移说明](https://opendatalab.github.io/MinerU/reference/migration_4/)、[资源与质量档位](https://opendatalab.github.io/MinerU/usage/tiers/)、[PyPI](https://pypi.org/project/mineru/)。
