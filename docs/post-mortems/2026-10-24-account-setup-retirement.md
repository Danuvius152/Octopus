## 08 的约三小时：身份迁移没有一次收齐

**08 存在明显效率问题。** 它实际改变的是全库业务身份前提，而工作安排起初更像
新增一个 setup 入口后，逐组修复邻接测试。大量夹具确实必须迁移，但这只能解释
工作量，不能解释共享错误和同类漏项为什么反复出现。

| 阶段锚点 | 已有事实 | 应如何评价 |
| --- | --- | --- |
| 02:57–03:17 | 空库、双连接 setup、丢响应/目录中断、封门和页面关键检查已有结果；setup 17 项通过；首轮消费者 103 passed / 65 failed | 核心路径较早有了可运行证据，但尚未证明全部要求；65 个失败已经提示这是广泛的身份迁移 |
| 03:17–04:52 | API、浏览器、WS、运行时、凭据和服务夹具逐组迁移；03:50 一次批次出现 130 个 setup errors | 应先收敛共用 helper、bearer、路径和子进程前提，再批量迁移，实际却多次边跑边补 |
| 04:52–05:35 | Wiki 共享 HTTP fixture 涉及 35 个消费者，多个任务 helper 转为显式 client/异步入口；owner 和 readiness 漏项继续出现 | 共享身份接缝及直接、间接消费者的清单建立偏晚 |
| 05:35–05:50 | 处理超长 nodeid 的 E2BIG，明确 08/09 混合运行时断言去向，固定首版检查点 | 选择清单和跨票测试分类应更早准备，避免临近冻结再处理 |
| 05:50–06:01 | 审查发现保留邀请码可越过 setup、workspace 仍暴露旧全局根；修复后固定 r2 | 这两项属于 08 核心封门要求，应进入第一轮入口矩阵，不能依靠最后审查才补齐 |

可以明确追到原因的返工有四类：

1. **低估身份变更的传播面。** 主 fixture 改为真实账户后，辅助 agent、App、MCP
   readiness、实际 run scope、独立 reader、故障 child 和 cold reopen 仍有旧前提。
   首轮 65 个失败后，仍按模块逐组推进，没有先把同类生产者及消费者完整收齐。
2. **共享 helper 未先用真实代表入口验证。** `tests/accounts.py` 把关键字更新接口
   误用为位置参数，一次放大成 130 个 setup errors。另有机械替换到错误的 client
   作用域、猜错 `codex_home_for` 参数和异步 helper 调用方式的错误。这些可以通过
   先读实际签名，再验证账户/访问根/HTTP/冷开代表场景来避免。
3. **同一根因没有触发横向清查。** MCP readiness 的 owner=None 在 03:26 一批修正，
   05:16 的维护消费者又出现同类失败。Wiki 的 `assigned`、`entry`、`active_worker`
   等接缝及其消费者分批修改，遗漏 owner、旧全局路径和迟到签名又各跑一轮。
4. **验证选择与观察点带来额外修复。** `--deselect` 前缀曾额外跳过一个持久化用例；
   巨大 nodeid 直到启动失败后才改用 `@` 清单。控制容量测试则把 create_task 当成已
   交接，后来才等待真实 answer_question 入口。它们都增加了定位和补验成本。

08 也有必须修正的真实产品问题：默认 `changeme` 让未配置 proof 被误判为已配置；
目录和丢响应恢复需要明确语义；邀请码和 workspace 的封门不完整；当前 owned 应用
删除还沿用旧全局根。消费者迁移暴露这些问题是有价值的，不能把它们都算成旧测试
噪声。但缺配置、各类业务入口和 owned 资源路径本可更早纳入行为矩阵。

因此，03:16 的关键检查通过不等于 08 二十分钟就应完成；同样，三小时也不能被
笼统归为必要编码。可避免的成本主要在不完整的身份依赖盘点、共享 helper 错误、
过碎的迁移批次，以及核心反例发现偏晚。记录不足以负责任地给出压缩后的精确工时，
但足以判断执行方式需要改进。

## 联合收尾的约八十二分钟：前两阶段遗漏继续支付成本

首个联合候选后到提交约 82 分钟，主要已是测试和证据收束。这里既有 08 未收齐的
业务生产者，也有 09 新准入规则会拒绝的无账户持久夹具。尤其是给业务行填 owner
ID，并不代表库里已有账户行、wrapped DEK 和原 curator；普通运行可能经过，冷开
才会被正确 guard 拒绝。08 应把这些副本记录为跨票消费者，09 启用 guard 前完成前提迁移。

后面才进行 raw schema 和 secondary database 盘点，分别形成 20 个函数和 73 个 DB
构造点的清单。清单本身只是线索，`explicit_account=false` 也不自动代表缺陷：受控
SQL 关系反例、历史输入检查和不重开的单元测试可以保留 None。

安全存储失败通过 `os._exit(70)` 结束进程，四 worker 门禁又不自动重启 worker。
每次遇到无账户冷开夹具，都可能让后面的模块尚未执行，同类遗漏于是延后到下一轮。
这不能靠放宽 guard、自动重试或认证覆盖修正；应在昂贵门禁前隔离验证这些持久库
和故障 child，并用原 trace/commit/proof 证明确实到达目标故障，而非更早准入失败。

08、09 的行为拆分和先替代后删除顺序仍成立；不足的是把共同夹具迁移当作隐含
收尾，没有在票面和执行清单中充分呈现。两票共用候选解决了临时兼容问题，却没有
自动解决消费者完整性和验证节奏，后者需要单独安排和检查。

## 最终如何收束

测试迁移采用真实账户、原账户 DEK、真实 bearer、明确 owned 资源和该例临时访问根。
冷恢复副本用 SQLite backup 保留原账户及业务关系；故障 child 在原 hook/trace 安装前
完成准备。旧接管专属测试退出，混合用例中的当前输入、Wiki、未知结果、原始字节、
receipt/ACK、进程退役、重复中断和不重放断言继续保留。没有增加产品兼容 flag、
自动开户的全局 fixture、认证绕过、重试或等待预算。

从 r6 保存 JUnit 后，验证收尾按仓库允许的有效证据复用执行：重新收集当前完整选择，
只复用原成功、当前源字节和环境不变、且不受变更与传递依赖影响的节点；失败、未执行
及失效节点按原四 worker/loadfile/no restart 条件补跑。超长 nodeid 使用 pytest `@`
清单传入，原参数内容保持。候选执行前后核验身份，最终按精确 JUnit key 审计并集。

最终 4628 项全部有有效成功结果，零 skip：3261 项来自 r6、645 项来自 r7、675 项
来自 r8、47 项来自 r9。r9 新 JUnit 恰好覆盖最后 47 项，补跑退出 0；旧进程的失败
结果未改写。前端 536 项、离线浏览器 89 项（0 real dispatch）、隔离 supervisor
9 项及 lint/types/contracts/docs index 通过。没有运行真实模型或可选知识/性能评测。

各轮固定快照使审查能够只看新增差异，保留已有结论，并排除继承的 07 和用户原工作。
这保证了交付可核对，但不能弥补前期遗漏消费者带来的多轮冻结和重复交接成本。

## 下次同类变更的做法

1. **先列状态和行为矩阵。** 空安装只允许 setup；非空无账户安装写前拒绝；当前 owned
   安装正常运行；未知旧协议输入保留并封闭。分别写清替代生产者和旧操作删除边界。
2. **在收紧 guard 前盘点身份生产者。** 除 HTTP 主 fixture，还要覆盖 agent/App/install、
   MCP readiness、raw schema、SQL backup、独立 reader、重启和故障子进程。沿导入和
   helper 查消费者，按完整数据关系分类，不只搜索 `user_id=None`。首轮已有大片同因
   失败，或同一遗漏第二次出现，就先横向收齐，不继续只修下一个报错模块。
3. **先证明共用夹具，再批量迁移。** 对真实账户 helper、异步 entry 和 bearer 各做少量
   入口验证；随后按同一根因成组迁移，避免共享 helper 的错误扩散成上百个 setup errors。
4. **把危险冷开提前隔离执行。** 手写旧库、去列迁移、独立恢复库和真实 fail-stop child
   先做定向验证；每个故障用例明确原注入点、proof 和观察点，再进入完整 worker 选择。
5. **保留断言，不保留取消的前提。** 当前迁移正例使用真实 owned 基线；旧无账户接管
   正例改为拒绝与原件保全；混合用例按断言拆解，保留当前恢复、未知效果和隔离行为。
6. **首次完整门禁就保存节点证据。** 固定源摘要、当前选择、JUnit 和执行环境；补验
   必须使改动及传递消费者失效，精确审计节点覆盖，持续保留原失败，不能按通过数相加。
7. **稳定候选后再做完整交付审查。** 先完成消费者和脚本清单，再冻结；后续有界增量
   继续独立复核。类型和收集成功不能代替故障路径、真实 HTTP/WS 和冷重开验证。
8. **分别审计每票耗时。** 08 按核心行为、共享夹具和消费者迁移记录，09 按交接证据、

   一张票的长跨度自动转嫁给另一张，也不凭日志数量估算净工时。
