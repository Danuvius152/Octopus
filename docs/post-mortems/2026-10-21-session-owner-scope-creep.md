# SessionOwner 合并交付的范围失控（2026-10-21）

状态：已收束。交付通过了固定候选验收，但票面边界和验证方式不成立。

## 摘要

一次原本只写“命令和 I/O 回报进入一个 owner”的交付，实际扩到了完成回执、通知送达、
资源退役和多个消费者；套件覆盖 115 个文件、1907 passed / 23 deselected，仍有几处测试
没有真正触发目标故障。根因不是某条代码写错，而是票面切在实现入口、共同接口尚未收敛
就迁移消费者、测试只证明代码路径。真正的教训是：**层完整和绿测试不等于责任完整和
行为正确。**

## 概述

这次交付的目标是把会话命令、I/O 回报和会话生命周期收进一个 `SessionOwner`，让活动
执行、问题、取消、归档和派发状态只有一个写者。按原票面，这像一次局部的所有权收口：
命令进入 owner，owner 负责串行化。

实际交付远大于此：完成回执（receipt completion）、通知送达、资源退役、以及 App/SSE、
delegation、WS/UI、archive 等多个消费者都被卷了进来。完成结果、通知送达和资源退役
的边界在实现中反复变化；每迁移一个消费者，共同接口又被重新定义一次。票面从“命令
进入一个 owner”变成了“完成事实、投递证据、资源生命周期和全部消费者都正确”。

没有已知的生产数据损坏或停机。代价是范围失控、消费者迁移反复、评审和回归成本，以及
绿套件带来的错误信心：如果完成、通知或退役的边界在真实崩溃/重启路径上漏测，绿测试
不会替我们挡住数据竞争或错误完成。

## 时间线

- 交付开始时，票面只要求命令进入一个 owner；计划把它当作局部收口，没有列出完成回执、
  通知、资源退役和消费者清单。
- 实现中，完成回执先暴露：原 receipt 不能只表示“命令被接住”，还要表示业务结果已经
  提交。随后通知送达暴露：业务提交成功不等于用户已经看到。再随后资源退役暴露：
  terminal 已提交不等于旧进程/租约已经退出。每加一个事实，边界就重画一次。
- 多个消费者开始迁移时，共同接口还没有收敛。App/SSE、delegation、WS/UI、archive 各自
  暴露新的完成/失败/迟到事件语义；消费者迁移和接口修改交错，票面继续吸收新事实。
- 测试随之增加，但几处没有命中目标故障：用 clean close 准备“崩溃恢复”，用构造 argv
  的回调次数代表实际 OS spawn，在业务完成后仍假定 child 还在 live map，异步退役没有
  等到目标观察点。测试是绿的，但绿的是执行过的代码路径，不是要防的失败。
- 收束时，固定候选覆盖 115 个文件、1907 passed / 23 deselected，独立复核关闭了 P2/P3；
  实际交付已经明显超过原票面。交付后复盘确认：失败在切票和验证，不在单点实现。

## 影响

没有已知的生产数据损坏或停机。影响集中在交付质量：

- 范围失控：一张票吸收了本应独立切分的完成、通知、退役和消费者迁移。
- 边界反复：共同接口在消费者迁移期间继续变化，每次变化都要重跑回归、重写测试。
- 错误信心：1907 个绿测试和覆盖率证明代码行被执行过，但不证明目标故障被触发过。
- 评审成本：审查者要同时判断 owner 串行化、完成语义、通知证据、资源退役和多个消费者，
  很难在一个上下文里做完。

## 根因

### 根因 #1：票面切在实现入口，不切在责任边界

“命令进入一个 owner”是一个实现动作，不是完整行为。它没有回答：

- 这次交付拥有哪些事实：accepted/claim、业务结果/receipt、投递证据、通知、资源退役；
- 每个事实的唯一写者、提交点、读者是谁；
- 哪些消费者读旧路径，迁移后谁删除旧路径；
- 哪个失败/未知路径必须被观察到。

因此票面在“层”的意义上是完整的：schema、API、UI、测试都碰到了；但在“责任”的意义上
不完整：完成回执、通知、退役和消费者都是同一 owner 边界内的事实，却被当成实现中
自然会发现的东西。发现得越晚，票面吸收得越多。

### 根因 #2：共同接口未收敛就迁移消费者

完成结果、通知送达和资源退役原本需要一个共同接口：谁在什么提交点产生哪个事实、消费者
按什么身份读取、失败和迟到事件如何关联。这个接口还在变化时，消费者已经开始迁移；每个
消费者都带来一个新的边界问题，接口再改一次。

这不是机械性的“wide refactor”，不能靠 expand–contract 的批量迁移自动解决。它是语义
接口没有冻结：先迁移消费者，再让消费者反过来定义接口，边界就会一直漂。

### 根因 #3：测试没有触发目标故障

几处测试的构造方式让目标故障根本不会发生：

- **用 clean close 准备“崩溃恢复”。** 进程是正常关闭的，恢复路径没有被走到；测试证明
  的是“正常关闭后能恢复”，不是“commit 后、通知前崩溃能恢复”。
- **用构造 argv 的回调次数代表实际 OS spawn。** 回调被调用了，不等于真实 `execve`
  成功、进程组建立、后代被捕获；spawn 失败/迟到/部分建立都没有被注入。
- **在业务完成后仍假定 child 在 live map。** 业务完成和资源退役是两个观察点；前者完成
  时后者可能还在进行，测试却按“还在”去断言。
- **观察点选在邻近事件。** 等的是队列变化、状态通知或 UI 卡片，而不是 accepted、claim、
  输入送达、业务提交、通知送达、资源退役这些目标事实；邻近事件先到，测试就提前通过。

这些测试是绿的，但它们证明的是“代码路径执行过”，不是“目标故障被触发且被正确处理”。

### 根因 #4：没有边界漂移的停手规则，也没有完成审计

实现中新增一个事实或消费者时，票面没有“停下来重切或改计划”的触发条件，默认让它吸收。
收束时也没有“计划交付 vs 实际交付”的审计：哪些事实是原票面的、哪些是后来加的、哪些
消费者迁移了、旧路径删了没有、哪些验收只是代码路径。

于是顶部可以写 `Status: done`，正文还留着“仍 in-progress”的旧快照；票面完成了，但
责任边界没有被记录清楚。

### 根因 #5：审查主要看绿，不看边界和故障

独立复核能找到 P2/P3，但流程没有强制问：这张票可能意外拥有哪个相邻事实？哪个消费者
还在读旧路径？哪个失败路径没有被测试真正触发？什么会让它膨胀一倍？审查因此更容易
确认“套件绿、主要路径对”，而不是“责任闭合、目标故障被覆盖”。

## 为什么测试没有捕获（真正的失败）

两个层面的安全网同时失效：

1. **构造层。** 手工 harness、fake argv、clean close、业务完成后的 live map 假设，都
   绕过了真实 spawn、真实协议、真实重启和真实退役。测试跑的是“我构造的世界”，不是
   “生产会到达的世界”。
2. **判定层。** 验收写成“代码路径存在/测试绿”，没有写成“在某个注入点制造目标故障，
   观察某个事实，旧代码必须失败”。1907 passed 证明执行，不证明行为；覆盖率证明行被
   走过，不证明失败被触发。

这和“100% 覆盖率仍然上线崩溃”是同一类错误：测试没有走真实的入口路径，也没有把目标
故障放进路径里。

## 防护措施

以下规则应作为下一次 owner 相邻切分的票面合同；没有合同，不切票。

1. **Contract 块。** 每张票必须写：拥有的事实、每个事实的唯一 writer/提交点、读者和
   消费者、失败/未知路径、旧路径删除、明确不做（out of scope）。只写“命令进入一个
   owner”不算合同。
2. **共同接口先冻结。** 两个及以上票/消费者碰同一完成、通知或退役接口时，先切一个
   contract/prefactor 票；接口冻结前不迁移消费者，迁移票全部 block 在它后面。
3. **故障注入矩阵。** 至少覆盖 accepted、claim、输入送达、业务提交、通知送达、资源
   退役。每个失败验收写清：注入点、观察点、旧代码为什么必须失败；禁止用 clean close
   代替崩溃、用构造 argv 代替真实 spawn、用邻近事件代替目标事实。
4. **边界漂移停手。** 实现中新增事实或消费者，停下来重切或改计划；同一票两次边界变化，
   回到 spec 重定责任模型，不再吸收。完成时审计 planned vs delivered。
5. **完成审计。** 记录交付的事实、迁移的消费者、删除的旧路径、验证证据和残留；顶部
   `Status` 只能在审计后改，不能和正文的 in-progress 并存。
6. **独立审查问边界。** 审查不只跑套件，还要问：这张票可能意外拥有哪个相邻事实？哪个
   消费者还在读旧路径？哪个失败路径没有被真正触发？什么会让它膨胀一倍？
7. **标题写行为，不写机制。** “命令进入一个 owner”应改写成可观察行为，例如“一个命令
   只被接纳一次，业务结果、通知和资源退役各自在正确提交点完成”。机制标题会掩盖责任
   边界。
8. **按事实/消费者切，不按层切。** 如果一张票要迁多个消费者或碰多个事实，按事实/消费者
   拆，而不是按 schema/API/UI 层拆；每张票都要能独立验证完整责任。

## 经验教训

- “完整”是责任完整，不是层完整。schema/API/UI/测试都碰到，不等于完成、通知、退役和
  消费者都闭合。
- 没有命中目标阶段的绿测试不是证据。测试必须能回答“我注入了什么故障、在哪个观察点
  看到了什么、旧代码为什么失败”。
- 共同接口是 prefactor，不是实现中自然发现的细节。接口没冻结就迁移消费者，边界一定
  反复。
- 边界变化两次就停。继续吸收只会把票面变成一张没有边界的实现清单。
- 票面是合同，不是起点。合同里要写“不做什么”，否则相邻事实会以“顺手”为名进来。
- 迟到的边界由每个消费者和每个测试买单；越晚发现，回归成本和错误信心越高。
