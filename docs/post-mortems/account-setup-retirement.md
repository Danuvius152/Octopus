# 开户规则收紧后，身份夹具和启动准入反复遗漏（2026-10-24）

状态：已修复并交付于 `87ce64787cd4a446802c18207de1e28dcebdaee3`。
本文记录该次开发与验证故障；提交时未推送或发布，不描述当前安装。

## 摘要

空安装开户与旧接管退役改变了整个测试库的身份前提，执行时却按新增 setup API
和删除旧模块安排工作。主 fixture 迁移后，独立恢复库、故障子进程和间接消费者
仍保留无账户基线；启动拒绝又只检查了较晚的数据库入口。结果是同类遗漏多次
进入完整门禁，worker 提前退出，剩余测试要到下一轮才有机会执行。

修复保留“先建立 owned 开户，再退出旧接管”的顺序，补全真实账户夹具、最早
数据库打开前的拒绝和旧消费者清单，没有放宽 guard 或增加临时兼容开关。

## 影响与证据

从最早留存红例到提交，可见跨度约 5 小时 53 分钟，包含实现、执行、审查和证据

65 项失败；一次共用 helper 错误又放大成 130 个 setup errors。后续无账户冷开触发

据此确认生产数据损坏；旧链退役也不授权清理生产残留。

证据来自该提交、当次固定候选及日志/JUnit。原任务记录已归档到私有发布记录，

## 根因与修复

### 1. 收紧的是完整身份关系，迁移只先覆盖了主 fixture

业务行有 owner ID，不代表独立库已保有原账户、wrapped DEK 和 protected agent。
普通运行可能经过，冷重开才会被正确拒绝。HTTP 主 fixture 更新后，辅助 agent、
App、MCP readiness、run scope、SQL backup、独立 reader 和故障 child 仍有旧前提。

首批大面积失败后，没有立即按身份生产者横向收齐；同样的 owner=None、旧全局根
和异步入口遗漏继续逐模块出现。共用 `tests/accounts.py` 还把关键字接口误当成
位置参数，批量迁移前未先验证真实签名和代表入口。

修复使用真实账户、原 DEK、bearer 和 owned 资源；恢复副本用 SQLite backup
保留完整关系，故障 child 在安装目标 hook/trace 前完成身份准备。受控 SQL 反例、
历史输入和不重开的单元测试按实际目的分类，不机械禁止所有 None。

### 2. 数据库拒绝放在了较晚入口，漏掉路径和 sidecar

只检查 `Database.initialize` 没有覆盖 InstallationOwner/profile 和更早的 intent
读取。空主文件旁仍有 WAL 时，前置 SQLite 连接也可能触及保留资料。首版 helper
还未统一实际绝对路径，漏掉 relative/alias 指向的 sidecar 与异常父容器。

修复沿最早安装入口核对打开顺序，在第一处可能触及旧资料的连接前拒绝，并纳入
绝对路径、相对路径、alias、断链和异常容器。拒绝必须保留原件；不能靠旧恢复器
稍后报错来证明写前安全。当前规则由[存储合同](../implemented/current-storage-format.md)维护。

### 3. 退役清单按模块名整理，遗漏了仍在调用的消费者

旧演练脚本仍调用已删除 bootstrap，移除 user_label 后又漏掉严格 dotenv 的既有
输入。现场证据最初遗漏通知相关表，schedule 统计也误假设存在 user_id。

修复按真实 schema、入口、脚本和配置消费者核对。退出的是 adoption/rekey、
memory/Wiki 接管及其专属恢复链；现用 memory CRUD 互斥、取消后的完成责任、
Connector 刷新、receipt/ACK、精确 MCP 清理和 CLI handoff/import 继续保留。
删除模块与删除当前职责必须分开判断。

### 4. 完整门禁被用来反复发现同类夹具缺陷

后期才补 raw schema 与 secondary database 清单。无账户冷开触发 `os._exit(70)`，
worker 不自动重启，原选择后半段没有执行。放宽身份检查或重试 worker 会掩盖
问题；应先隔离验证危险持久库，并确认故障 child 确实到达原注入点。

另有验证工具自身的遗漏：`--deselect` 前缀多跳过一个用例，超长 nodeid 触发
E2BIG，容量测试把 create_task 当成交接完成。分别改为精确节点选择、pytest
`@` 清单和等待真实 answer_question 入口，没有提高等待预算。

## 防护与验收

替代开户路径将首管理员、DEK 和初始 agent 放进同一事务。目录在提交后幂等补齐，
成功响应前完成；提交后中断可登录恢复目录，不重复开户或更换 DEK。旧接管退出前
先证明非空无账户安装写前拒绝，当前 owned 安装及交接仍可使用。

旧接管专属正例退出；混合用例继续检查原字节、未知效果、输入恢复、receipt/ACK、
重复中断与实际进程退休。没有添加自动开户的全局 fixture、认证绕过或产品兼容 flag。

当次后端 4628 项、前端 536 项、离线浏览器 89 项（0 real dispatch）、隔离
supervisor 9 项及 lint/types/contracts/docs index 通过。后端结果由源身份、环境
和依赖仍有效的成功节点与受影响补验组成，按精确 JUnit key 审计；未跨轮相加通过
计数，原失败记录保留。未运行真实模型或可选知识、性能评测。

## 教训

- 身份变更先盘点完整数据关系和所有生产者，再批量迁移消费者；同因错误再次出现
  时先横向检查，不继续只修下一个报错模块。
- 共用 helper 先验证真实账户、HTTP、访问根和冷开代表路径，避免一处错误放大。
- 写前拒绝从最早打开入口取证；故障用例要证明到达目标 hook，而非在更早 guard 退出。
- 替代行为与旧链退役可以共享候选，仍须分别列消费者、完成条件和必要证据。
