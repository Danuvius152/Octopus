# Wiki 把观察快照、字节保全和阅读证据当成了更强保证（2026-11-04）

状态：下列准入、身份与读取缺口已有修复，语义保证和未测量成本边界保留。
历史调查窗口为 2026-10-04 至 2026-11-04（Asia/Shanghai），基线为
`0f1570877be4e2ed5903377fe93955c454f43906`。

## 摘要

冻结 selection 保存了可维护文档的观察，却不能保证准备后权限仍在；保留相同字节
也不能证明文件身份没被替换。来源核验曾通过改文章版本表达，互相引用的 A、B、C
因而反复把对方判为待维护。读取链路还可能在最终裁剪前记覆盖，把没有交付给模型
的后半篇算成已读。

修复分别保存当前授权、文档身份、来源确认和实际交付范围。模型判断意图与语义，
程序核对权限、版本、字节和收据；文章存在、任务 completed 或短响应都不能自动
证明语义正确、终稿已冷读或内部成本更低。

## 影响与证据

旧实现与反例支持越过准备后撤权窗口、核验制造版本震荡、阅读覆盖记多，以及
HTTP 用户看不到资源警告等后果。依据为 Git 差异、实现和回归源码，未取得全部
故障发生于生产的记录，也不能从提交顺序推断每次开发者的思考过程。

本次文档改写没有运行产品套件、模型或部署验收。历史测量只在原版本与材料下
成立；显式入口转 auto、共享查询和 Markdown 范围等产品选择变化，不一概算缺陷。
任务结算、派发与旧聊天观察另见[效果专题](wiki-effects-dispatch-and-observation.md)。

## 根因与修复

### 1. 语义分类和观察被误当成写权

“怎样维护”“引用维护规则”“不要维护”和“维护这些文章”不能仅按词面分成同一
动作；交给模型理解也不让模型成为授权源。显式只读、父任务限制和当前操作卡仍
有效，文章内容、生成的 scope、普通委托或已加载指南都不能给 worker 增权。

冻结 selection 只保存观察。准备后撤权、来源变化、索引不再 ready 或 selection
到期，都必须阻止新任务及证据提交。修复在最终 writer 事务核原范围、注册、身份、
版本和来源，实际维护还需有效 assignment。无更窄选择的 checked 默认复核范围
仍限当前 Library Markdown。

原请求限制还要覆盖空 paths 的材料、新页目标和去重复用的实际落点。
[请求限制](../../tests/test_wiki_request_limits.py)构造这些绕行入口；
[准入](../../tests/test_wiki_maintenance_admission.py)在准备后撤权，确认无新任务或
关联证据；[冻结选择](../../tests/test_wiki_maintenance_selections.py)核分页变化、
跨账户隔离及只观察不授写权。

幂等也不能只按 material hash 复用。scope、来源稳定身份、revision 或 location
不同，不能悄悄接到旧载荷；冲突在别名和订阅写入前拒绝，同来源仅改展示路径则
允许合法复用。[任务回归](../../tests/test_wiki_jobs.py)覆盖意图冲突与来源改名。

### 2. 原字节保全、文件身份和终稿语义被混为一谈

original_preserved 返回值不是持久证明。修复随 change 保留材料证明，按真实
copy/insert 映射重建原字节；移动、恢复、保留期与未知元数据都要保全，人工编辑
后不能靠重新格式化补发证明。

同路径 unlink 后重建，即使字节相同也不是原文档，受控 atomic save 则可保留身份。
最终快照或索引重扫都无法证明事件没丢。EventInbox 在内核事件取走前 arm，持久
接收后才应用身份/索引并 ACK；中断造成的不确定历史失败关闭。
[事件回归](../../tests/test_wiki_event_inbox.py)在 arm 后、持久接收前中断，冷开仍
拒绝沿旧身份继续，替换文件字节保留。

发布还要在 prepared 后、replace 前重查文件，保留期间人工编辑的冲突；恢复不能
覆盖后来的人工字节。flock 只协调 Octopus writer，重查不是文件系统 CAS，不能
宣称消除不服从锁的编辑器与最终 syscall 的所有竞争。
[发布边界](../../tests/test_runtime_followup_boundaries.py)在准备后和临时文件同步后
插入外部编辑。

原文保留也不证明终稿含义没变：无新词重排可改变标题归属，删尾部条件可改变断言，
两次稀疏修改必须累计最终区段。真实 writer 的变换因此生成累计 readback ranges，
包括标题、接缝和语境，映射不可靠就扩大范围。
[终稿回读](../../tests/test_wiki_readback.py)验证范围与版本，不认证模型理解；程序
保证上限见下文冷读边界。效果、录制与退休另按[任务结算](wiki-effects-dispatch-and-observation.md)取证。

### 3. 核验事实放进文章版本，制造了循环失效

A、B、C 相互引用，只更新“我已核验来源”的文章字段也会变 revision，让另一篇
再次发现来源变化。增加模型轮次无法使这种表示自然收敛。

修复将后续确认写进现有操作收据，保留原来源声明，另存实际核对的版本与位置，
不改正文/YAML、不造新 revision。纯移动可保留观察身份，编辑、恢复或复制不能
继承旧核验；真实来源变化和磁盘未索引变化仍使依赖失效。

[来源确认](../../tests/test_wiki_source_confirmation.py)的
`test_three_reciprocal_notes_finish_source_review_without_version_churn` 保留三篇原
字节，再改变真实来源验证直接依赖失效，并覆盖移动、复制、恢复与无实际读取的拒绝。
普通保存、索引 ready 或同 revision 均不等于已接受维护；来源警告、录制和索引恢复
也不能靠再制造一次 no_change 掩盖。

### 4. Store 取到全文，被记成模型已收到全文

最终 MCP envelope 可能因 UTF-8 字节预算只交付前缀。若按请求 length 提前留证，
就会把未交付部分记成已读。32,768 字节是完整单次回包预算，不是整篇可读上限或
token 数。

修复在最终裁剪后，仅记录实际返回的 Unicode code point 范围；全文任务沿同一
revision 补缺口。source_cursor 只补来源，不增加正文覆盖。已经交付且当前上下文
仍保留的同版正文可复用，跨任务/身份/版本不能继承，压缩丢正文后也不能继续声称
当前掌握全文。

raw 与提取文本只有程序证明逐字相同才共用坐标，BOM、HTML、换行和 emoji 都可能
使映射不同。正文、revision、来源与坐标在同版私有读取值中捕获，避免消费者自行
拼出混合版本。

[响应裁剪](../../tests/test_wiki_read_response.py)验证单读/批读只记真实 Unicode
前缀并可补完维护；[工作流读取](../../tests/test_wiki_workflow_reading.py)核复用、
缺口、BOM 和来源续页；[同版读取](../../tests/test_wiki_source_read_consistency.py)
在实际读字节前插入外部编辑，检查新正文不混用旧来源。

### 5. 执行 attempt、结果派发与当前观察，是三种关系

A 提交、B 重派后，A 不再自动汇报，但仍应在当前授权下看到新 attempt。通知 ACK
与任务当前可读性不是同一事实；恢复也不能为补通知重新生成内容。完整反例、
修复和回归集中在[效果、派发与观察](wiki-effects-dispatch-and-observation.md#为什么前一次修复还不够)。

### 6. 响应短和领域测试通过，被外推成低成本与用户可见

短 JSON 背后仍可能逐命中搬整篇正文，或构造全量错误后只返回三条。成本要测所属
层的字节、行数、解析和连接。`d3e9049` 的固定对照证明 SQLite 搬给 Python 的
文字减少，不能称物理 IO 或生产延迟下降；不同问题集的模型用量不是严格 A/B，
未观察到实际 read_many 调用也不能宣称批读收益。含 NUL 正文因 SQLite TEXT
substr 行为保留全文投影例外，普通正文收益不能外推。

另一个消费边界是 HTTP typed response：Store 已有 stale/document_too_large，
compact 响应字段未声明，警告仍被过滤。修复同时更新字段与投影，跨普通账户、
App 和模型入口验证。拒绝发生在写副作用前，历史字节与恢复材料保留。
[资源拒绝](../../tests/test_wiki_document_budget.py)检查原字节、收据、旧索引及合规文件；
[搜索投影](../../tests/test_wiki_search_resource_state.py)覆盖 full/compact 和三类
HTTP 消费面。资源限额不是对所有文档均已优化或检索质量已认证的声明。

## 为什么测试没有先拦住

仅在准备前撤权、两次 API 间改文件或稳定单向引用，避开了准备后的权限窗口、
实际读字节时的版本变化和互引震荡。Store 字典断言又避开 typed HTTP 过滤；
fake worker 正常返回不证明原执行录制，hash 和范围生成也不证明语义保真。

测试设施自己也可能失责。`c66b045` 修复 fixture 创建/打开失败、退出时再取消的
清理，join 原 session、assignment 和 callback server，不用清全局注册表伪装干净。
[夹具回归](../../tests/test_wiki_test_runtime.py)保留兄弟 worker，检查原端口、任务
退出及后继实际可用，而非只确认 teardown 被调用。

这些反例说明观察与交接不足，不证明每个旧版本全套测试都曾绿，更不证明所有
未来路径已关闭。语义仍需实际材料与模型判断，机械证据只限定受控修改和阅读范围。

## 仍存边界：流程义务与性能候选

### 终稿冷读是流程义务，不是 completed 的程序硬门槛

[worker 指南](../../server/wiki/prompts/worker-v2.md)要求冷读最终 revision 的全部
受影响区段，[readback](../../server/wiki/readback.py)生成累计范围；
[settle_item](../../server/wiki/jobs.py)核匹配效果、applied、版本、索引及原执行成功
终态，没有把最终阅读覆盖作为 done 硬判定。

因此 completed 不证明程序已核验终稿冷读，更不证明语义理解。写前/来源阅读检查
不能外推成写后检查；回读测试只证明范围和版本。本次没有真实模型终稿语义验收，
也不据此新增阅读账本或状态，文本交付本身仍不是理解证明。

### 同版来源确认历史会增加读取工作，实际影响尚未测量

[source_confirmations.read](../../server/wiki/source_confirmations.py)按当前 revision
倒序扫描收据并解码，以 setdefault 留每个 occurrence 的最新确认，已有所需结果后
仍继续处理历史。核验不改 revision 可避免震荡，也会在同版累积收据。

这是可见成本形态，尚无测量证明已构成用户瓶颈。相关性能工作可固定同版确认数，
测行数、解码和耗时后决定是否优化既有查询或可重建投影，不能为加速删除原 receipt，
也不预先引入第二份权威缓存。

## 教训与当前合同

- 语义、观察和权限分开，最终操作重新核权；指南缓存不能替代当前操作卡。
- 内容、身份、位置与核验事实分别表达，检查持续制造新工作时先检查表示。
- 阅读证明在最终交付边界产生；优化减少搬运和装配，不扩大“已读”的定义。
- 在真实消费者验证承诺，正确性、语义和成本各自举证，保留原文、收据与未知效果。

现行行为归[Wiki 合同](../implemented/wiki-development-summary.md)、
[知识请求](../implemented/knowledge-requests.md)与[存储合同](../implemented/current-storage-format.md)；
评测方法见[测试政策](../testing.md)，未交付产品及启动条件归[Wiki 计划](../plans/wiki-future-plan.md)。
