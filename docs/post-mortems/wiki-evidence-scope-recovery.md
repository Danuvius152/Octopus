# /wiki 连续修改中的证据、范围与恢复边界（2026-11-04）

状态：历史复盘。所列反例有对应修正和回归入口；本文不认证全库语义正确，也不代表
当前安装已部署或重新验收这些修正。

本文回答“意图、写入范围、原文及阅读证据为何不能互相替代”。原执行效果、取消与
恢复、结果派发及旧聊天观察另见[任务效果、派发与观察复盘](wiki-effects-dispatch-and-observation.md)。
两篇采用同一固定代码基线；原第 5 节保留为专题入口。

## 摘要

近一个月，`/wiki` 从显式查询与 Weber 维护，发展到共享查询、原位整理、默认增量、
批量复核、来源确认及跨会话恢复。反复修改并不都是同一个 bug 重现：部分是产品
选择改变，部分是原有保证只覆盖了一段路径，后续才补齐真正的使用和提交边界。

最值得保留的经验是：**把“理解了什么、允许改什么、实际读了什么、已经发生什么”**
**分别交给能证明它们的责任方。**模型判断意图与语义；程序核对当前身份、权限、
版本、字节、收据和恢复。文章存在不证明维护完成，来源确认不必修改正文，任务
完成不代表结果已汇报，响应短也不代表内部工作少。混用这些事实，就会一轮轮修补
相邻边界；单纯增加提示词、状态或测试数量不能消除根因。

## 调查范围与证据

调查窗口为 **2026-10-04 至 2026-11-04（Asia/Shanghai）**，相关功能的主要连续
修改始于 10 月 12 日。代码版本固定为本地 `main` 的
`0f1570877be4e2ed5903377fe93955c454f43906`，检查 Wiki 及其请求、存储、回传和
界面消费者的 Git 差异、当前合同和回归源码。其他工作树改动不作为历史证据。

本文依据的是代码允许的故障、修复前后差异与测试构造，未取得这些故障全部发生于
生产的记录，也不能由提交顺序还原每次开发者的思考过程。原历史调查为文档工作，
未重跑产品套件、调用真实模型或发布；下列用例是该版本可查的回归入口。
历史验收与测量只在其原版本、材料和方法下成立。

## 具体反例与因果

### 1. 意图由模型理解，权限必须在实际操作处成立

早期显式入口逐步变为共享查询；`12f2598`、`3b60b70` 解决续聊可用性和额外开关。
`d24dc77` 再将普通 `/wiki ...` 从固定 read 改为 auto，合并重复 entry 指南：
“怎样维护”“引用维护规则”“不要维护”和“维护这些文章”不能只靠词面当作同一动作。
这部分是入口设计的演进，不能据此说旧 read 模式曾擅自写库。

但模型理解不能成为授权源。该修正仍保留显式只读和父任务限制；没有更窄选择的
checked 默认复核只允许当前 Library Markdown。文章内容、模型生成的 scope、
普通委托或已经加载的指南都不能给 worker 增加写权。实际修改需要有效 assignment，
准入还要在准备后的最终事务内复核原调用范围、注册、身份、版本与来源。

`203f7f3` 已将来源要求与维护限制拆开，限制沿原请求向异步工作传递。检查不能只
看表面的 paths：空 paths 携带的新材料、创建目标和去重复用的实际落点同样是效果，
不能绕过父请求只读或更窄选择。[请求限制回归](../../tests/test_wiki_request_limits.py)
分别构造空路径材料、限制相交和越界 target，检查最终 writer 拒绝。

后半月的冻结 selection 进一步暴露这个区别：它保存观察，不冻结世界。准备阶段后
撤权、来源变化、索引失去就绪或 selection 到期，都必须阻止新任务及关联证据提交。
把检查留在 HTTP 入口，或认为“刚才看见可维护”足够，都会留下等待后的窗口。

幂等也必须保留原意图。`18fe07f` 修正同 material 就复用待处理任务的假设：scope、
来源稳定身份、revision 或 location 不同，不能悄悄接到旧载荷；冲突须在别名和订阅
写入前拒绝。反过来，同来源只是改了展示路径，不该误判为新意图。去重键既不能
仅是内容 hash，也不能依赖当前位置。[任务测试](../../tests/test_wiki_jobs.py)覆盖
意图冲突无新增别名及来源改名后的合法复用。

回归入口：[准入测试](../../tests/test_wiki_maintenance_admission.py)中的
`test_authority_lost_after_preparation_is_rechecked_before_accepting`、
`test_original_mcp_scope_revoked_after_preparation_cannot_accept_or_add_evidence`；
[冻结选择测试](../../tests/test_wiki_maintenance_selections.py)覆盖只观察不授写权、
分页后内容变化和跨账户隔离。

经验：语义分类、观察和授权各有边界。将它们放在各自责任方，比继续增加命令词、
模式镜像或常驻提示更容易维持一致；指南缓存命中也不能跳过当前操作卡与权限检查。

### 2. 原文保全、终稿语义与实际效果，需要不同证据

早期插入式整理已经返回 original_preserved，但这不等于持久证明。
`6ca1fd8`、`7e54e73` 将原材料证明随 change 保存，再按实际 copy/insert 映射重建
原字节；移动、恢复和保留期都要维护证明，人工编辑后不能靠再格式化重新发证。

`5e211c5` 暴露另一个快照不足：同路径 unlink 后重建，即使字节相同，也不是原
文档；受控 atomic save 则可保留身份。最终目录快照不能恢复这段生命周期，索引
重扫也不能证明事件没丢。EventInbox 因此在内核事件取走前 arm、持久接收后才应用
身份/索引并 ACK；不确定历史失败关闭，而非重扫后伪装 ready。其必要性由
[事件接收回归](../../tests/test_wiki_event_inbox.py)的
`test_interrupted_kernel_intake_cannot_rebind_the_old_identity` 验证：在 arm 后或
持久接收前注入中断，冷开仍拒绝沿旧身份继续，替换文件字节保留。

`f0ee698` 又在 prepared 后、replace 前核对当前文件，检测准备期间的人工编辑并
保留冲突。原先读到的版本正确，不代表真正替换时仍拥有同一份前像；恢复同样不能
把后来的人工字节当作可覆盖的中间态。这里的 flock 只协调 Octopus writer，重查
不是文件系统 CAS；不服从锁的编辑器仍可能竞争最终 syscall，不能宣称消除所有
OS 级竞态。[发布边界回归](../../tests/test_runtime_followup_boundaries.py)覆盖
准备后及临时文件同步后的外部编辑。

字节保全依然不能回答终稿是否读过。`9d09703` 明确区分 material origins 和本任务
的变更清单：前者证明原字节怎样留下，后者决定最终新增、修改及重排位置的回读。
不新增文字的重排可以改变标题归属，删掉末尾条件可以改变断言，连续两次稀疏修改
也不能只检查最后一次。修复由真实 writer 的 copy/insert 变换累计最终范围，并加入
标题、接缝与必要语境；没有可靠映射时扩大回读，不能据此宣称没有语义变化。

回归入口：[终稿回读](../../tests/test_wiki_readback.py)覆盖无新词重排、尾部条件
删除与累计稀疏改动。它验证检查范围的生成，不认证实际终稿已完整交付，更不认证
模型对含义的判断正确；具体保证上限见下文“仍存边界”。

模型说“完成”、正文存在或进程退出，也不能单独证明原 job/item 的输出与执行均已
结算。效果收据、原请求录制、索引及退休的因果与回归集中到
[任务效果专题](wiki-effects-dispatch-and-observation.md#为什么前一次修复还不够)。

经验：保全证据、阅读证据、效果收据各自只证明自己的事实；不能将一种证据外推成
另一种保证。

### 3. “文章没变”与“已经维护”，不能共用一个版本号

普通保存、索引 ready、纯改名和真正的维护基线曾需要逐步分清。增量维护要回答的
是“相对哪次已接受、已索引的 worker 输出，还有哪些语义或恢复差异”，而不是
“这份文件最近是否保存过”。同 revision 仍可能有来源警告、录制待核验或索引恢复；
纯移动也不该仅为制造完成记录，再让模型做一次 no_change。

`645b868`、`9d09703` 给出一个尤其明确的反例：A、B、C 相互引用，仅仅更新
“我已核验来源”的文章字段，也会改变文章 revision，让另一篇再次发现来源变化。
核验本身制造待维护项，增加模型轮次也无法让这个表示自然收敛。

修复将后续确认放进现有操作收据，保留原来源声明，另记实际检查的版本和位置，
不改正文/YAML、不造新 revision。纯移动可保留观察身份；编辑、恢复或复制不能
继承旧核验。真实来源变化仍失效，磁盘未索引变化也必须被发现。这里新增确认事实
是为了表达独立核验，由来源确认模块拥有，而不是另造一套文章或循环调度器。

回归入口：[来源确认](../../tests/test_wiki_source_confirmation.py)中的
`test_three_reciprocal_notes_finish_source_review_without_version_churn` 保留三篇
原字节，并验证随后真实来源变化仍使直接依赖失效；同文件还覆盖移动、复制、
恢复、未索引编辑及没有实际来源读取时拒绝确认。

经验：先判断变的是内容、身份、位置还是核验事实，再选择存储位置和失效规则。
当一次“检查”持续制造下一次工作时，应先检查表示和依赖关系，而不是加重试。

### 4. 服务端取过正文，不等于模型实际读到正文

`2e42152` 开始约束模型响应；后续 compact、批读、location 和显式复用逐步降低
重复工作。这里最容易破坏的保证是阅读覆盖：Store 取得全文，最后的 MCP envelope
却因 UTF-8 字节预算只交付前缀；若提前按请求 length 留证，就会把没交付的后半篇
算作已读。32,768 字节约束的是单次完整 MCP 回包，不是整篇可读上限或 token 数。

修复在最终裁剪后只记录实际返回的 Unicode code point 范围；全文任务沿同一
revision 补完缺口。source_cursor 只补来源事实，不增加正文覆盖。相同文本已经
实际交付、当前上下文仍保留时可以复用；任务、身份或版本不同不能继承，压缩后
丢失正文也不能把“交付过”当作此刻仍知道内容。

`9d09703` 同时约束 raw 与提取文本的复用：只有程序证明逐字相同才能共用坐标；
BOM、HTML、换行与 emoji 不能被当成无关细节。`6166de5` 先让正文和来源共用
读取事务，`fd7ab9c` 再将完整正文、revision 与坐标收进同版私有读取值，避免消费
者分开读取后自行配对出混合版本。

回归入口：[响应裁剪](../../tests/test_wiki_read_response.py)中的
`test_byte_clipping_records_only_actual_unicode_prefix_and_can_finish_maintenance`
同时覆盖单读和批读；[工作流读取](../../tests/test_wiki_workflow_reading.py)覆盖
显式复用、补缺口、BOM 与来源续页；[同版快照](../../tests/test_wiki_source_read_consistency.py)
在实际字节读取前插入外部编辑，检查新正文不混用旧来源。

经验：阅读证明在最终交付边界产生。优化应减少重复获取和装配，同时保留新鲜度、
权限与版本检查；不能通过扩大“已读”定义来减少工具调用。

### 5. 执行 attempt、结果派发与当前观察，是三种关系

这组因果已拆到[任务效果、派发与观察复盘](wiki-effects-dispatch-and-observation.md)：
A 聊天提交任务，B 入口重派后，A 不再自动汇报，但用户打开 A 时仍可在当前权限下
查看同一 job 的新 attempt。新文保留原执行恢复、派发交接、ACK 丢失、只读快照及
提交后丢失唤醒的反例和回归入口；维护意图的幂等边界归本篇第 1 节。

### 6. 响应变短、Store 测试通过，都不足以说明完整用户路径正确

后半月的性能工作逐步从少返回 JSON，深入到少搬运全文、少建连接、复用解析及按
变化使派生投影失效。短响应背后若仍逐命中取整篇正文，或先构造全量错误再裁成
三条，成本依然发生。真正需要测的是所属层的字节、行数、解析和连接，而不是只
比较提示词长度或最终响应长度。

`d3e9049` 的固定成本对照保留了一个重要限制：SQLite 搬给 Python 的文字减少，
不能说成物理 IO 或生产延迟下降；不同问题集的模型用量不能当作严格 A/B；当时
未观察到实际 read_many 调用，也不能把预期批读收益写成已经验证。含 NUL 的合法
正文因 SQLite TEXT substr 行为保留全文投影例外，不能把普通正文的收益外推过去。

`6ab383a`、`2358819` 还提供了接口反例：Store 已能标注超限文件的 stale 与
document_too_large，但普通 HTTP compact 的 typed response 没声明相应字段，
仍会把警告过滤掉。领域测试通过，用户却可能只看到上次索引内容。修复同时补字段
与响应投影，跨普通账户、App 和模型入口验证；拒绝发生在写入副作用前，历史字节
与必要恢复材料仍保留。

回归入口：[资源拒绝](../../tests/test_wiki_document_budget.py)检查原字节、收据、
旧索引和其他合规文件；[搜索资源投影](../../tests/test_wiki_search_resource_state.py)
覆盖 full/compact 与三种实际 HTTP 消费面。资源限额是明确支持政策，不能被描述
为对所有文档均已优化或自动认证检索质量。

经验：在真实消费边界验证承诺；正确性和成本分别举证。可重建索引可以优化或重建，
正文、来源、收据与未决效果不能为了清缓存或跑分而丢失。

## 为什么此前验证仍留下缺口

这些反例不说明此前完全没有集成、并发或实机测试；它们说明局部证据被外推了。

- **用相邻事实做判定。** 文件已存在、索引已 ready、模型正常返回、通知已 ACK，
  各自都可能早于消费者需要的事实。测到其中一个，不能结束整条维护或汇报链。
- **准备路径避开目标交错。** 只在准备前撤权、只在两次 API 之间改文件、只测试
  稳定单向引用，都不会触发准备后撤权、实际读字节时版本变化和相互引用的版本震荡。
- **mock 隐去了消费合同。** 只测 Store 字典发现不了 typed HTTP 过滤；只确认
  后端任务完成发现不了旧聊天状态不可达；fake worker 正常返回也不证明原执行录制。
- **测试设施自己失去 owner。** `c66b045` 修正 Wiki fixture 的 setup/teardown：
  创建或打开中途失败、退出时再取消，都要 join 原 session、assignment、callback
  server 和清理；不能清掉全局注册表，让残留或误伤兄弟 fixture 看起来“干净”。
  [夹具回归](../../tests/test_wiki_test_runtime.py)保留兄弟 worker，检查端口、原任务
  及后继 worker 的实际可用性，而非仅断言 teardown 被调用。

从这些连续修补可以推断，原验收在责任交接和消费者上的反例不足；不能再推断每次
历史套件都跑绿，或每一条未来路径都已关闭。内容保真还需要实际语义检查，hash、
读覆盖和机械测试只能为它提供可靠材料及受控修改边界。

## 仍存边界：流程义务与性能候选

以下判断限定在 `0f15708`，不把未测量风险或模型义务写成已发生的生产事故。

### 终稿冷读是流程义务，不是 completed 的程序硬门槛

[worker 指南][worker-cold-read]要求冷读最终 revision 的全部受影响区段；
[readback.response][src-readback]给出累计 ranges、required 与 block_ids。
但[settle_item][src-settlement]核的是匹配原请求的效果、applied、版本、索引及成功
终态，没有把最终 readback 阅读覆盖作为 done 的硬判定。写前及来源阅读的程序
检查，不能被外推为写后覆盖也已强制核验。

因此，**job completed 证明原执行和实际效果满足结算合同，不证明程序已核验终稿
冷读覆盖，更不证明模型理解或语义质量必然正确。** 现有回读测试证明范围生成与
版本规则；本轮没有通过真实模型检查终稿语义。这里记录的是模型流程义务与程序
保证的边界，不据此新增状态或持久阅读账本。只有产品明确选择“缺少终稿交付覆盖
不得完成”，才在既有收据与退出边界讨论最小验证；文本交付仍不能充当理解证明。

### 同版来源确认历史会增加读取工作，实际影响尚未测量

[source_confirmations.read][src-confirmations]按当前文章 revision 查询匹配的
confirm_sources 收据，倒序逐行解码，以 setdefault 保留各 occurrence 的最新确认，
得到所需结果后也继续处理剩余历史。由于核验不改文章 revision 是正确设计，同版
反复核验会积累收据；最终结果很小，不能推出扫描和 JSON 解码成本也很小。

这是源码可见的成本形态，尚无本轮测量证明用户实际数据已构成瓶颈。出现相关延迟，
或明确开展该路径性能工作时，可比较同版 1／100／1000 次确认的行数、解码量及端到端
耗时，再决定是否优化既有查询或可重建投影。不能为加速删除原 receipt，也不预先
引入另一份权威缓存。该候选不同于前文 `d3e9049` 已完成的固定成本对照。

## 后续开发应保留的做法

1. **先列事实及其权威。** 跨权限、持久化或异步链路时，简短写清原请求、文档身份、
   revision、grant、job/item、effect receipt、dispatch 和观察者，指出 writer、提交
   点及消费者。普通局部修改不必新建计划或票据。
2. **用一个反例推翻假设，再决定机制。** 写出“在什么等待点改动什么，应该观察到
   什么”。新状态、缓存、重试或回退必须服务这个真实需求，标明 owner 与验证入口。
   同一假设被连续反例推翻时，重看表示和责任划分，不继续叠条件。
3. **把程序确定的工作收回程序。** 范围合并、版本比较、索引去重、坐标映射、收据
   对账和结算由现有模块负责；模型保留意图、知识整合和表达判断。不要让 worker
   在自己的任务内等待框架确认自己完成。
4. **恢复先问效果，不先问要不要重跑。** 沿原身份核验已保存、索引待修、录制未知
   和仍在退出的资源；已完成部分保留，未知不能冒充未执行。幂等复用还需检查推进
   条件，取消等待也不等于线程或子进程退休。
5. **按完整用户行为收束。** 选中一项共享能力后，完成真实入口、消费者、失败与
   恢复，删除被替代的旧模式/入口/状态；不顺带开启未来产品。原位维护保留人工
   内容与未知元数据，合法 no_change 不必制造补丁或模板壳。
6. **将证据写到它实际支持的范围。** 机械协议用确定性回归，语义用明确选择的真实
   材料和入口，成本用固定语料与环境。保留首轮失败和测量单位；相同版本的有效
   通过项复用，修复后只补受影响项，不因审查轮次重复全套付费或产品验证。

这些做法不要求每次维护跑完整矩阵。按变更选择最能推翻当前设计的路径，达到约定
完成条件便收束；不把“完整”扩大成扫描全库、再造存储或重写所有相邻模块。
