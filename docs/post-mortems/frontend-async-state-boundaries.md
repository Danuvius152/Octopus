# 前端反复修改复盘：防旧、有效结果与等待边界

状态：历史复盘。回看 2026-10-06 至 2026-11-06 的前端修改，以
`0a56386315548b6e9df6251166220749fc0ce4aa` 为代码整理基线；不代表当前部署已验收。

## 摘要

近一个月的前端修复反复碰到同一个问题：**防止旧数据覆盖新数据时，把仍然有效的**
**结果、补全信息和结束等待的机会也一起挡掉了。**请求先发、对象被替换、连接重建、
组件卸载，分别说明不同的事实，不能合成一个通用的“这个结果旧了”。

例如，较晚发出的读取先返回 `running`，不证明较早读取随后带回的 `completed`
无效；执行目标已过期，不证明同份响应中的历史正文也不能补齐；任务 B 的刷新
失败，不应剥夺任务 A 清除旧诊断的资格。只验证“旧结果没有覆盖”，可能留下
任务一直显示运行中、输出不完整、创建成功却没有卡片，以及正文等待辅助接口等问题。

这些修改带来的主要经验是：先分清结果属于谁、它证明什么、允许改变哪些字段，
再决定丢弃、合并或补读；同时验证正确结果能够显示、等待能够结束。集中读取和
更新责任有价值，但不能把不同事实的顺序规则压成一个全局开关。

反过来，结果真实有效，也不自动取得更新当前页面的资格。列表中暂时没有某会话，
不证明它已删除；某会话已删除，也不证明账户凭据失效。防护和清理都要落在原事实
的范围，避免一次局部变化影响其他会话、草稿或共用连接。

## 具体反例与原因

### 1. “请求比较旧”不能直接推出“结果无用”

两个请求都从同一任务的 `running` 基线出发，旧代码有两种误伤方式：

| 交错 | 过度防旧的结果 | 应保留的判断 |
| --- | --- | --- |
| R1、R2 发出；R2 先返回 `running`；R1 后返回 `completed` | R2 结束就淘汰 R1，唯一带回的完成结果消失。 | 同一有效观察中的成功响应仍可贡献合法终态。 |
| R1、R2 发出；R1 返回 `running` 并替换对象；R2 返回 `completed` | 对象引用已不同于请求前基线，R2 被当成会覆盖实时更新。 | HTTP 快照写入不能冒充期间新到的 WS／本地权威更新。 |
| 同一任务已收到 `completed`，后来收到 `running` 快照 | 若简单反向改成“成功响应都采用”，终态又会回退。 | 同一次执行的终态保护继续有效。 |

[`65b5918`][c-snapshots] 将错误提示的读取顺序与成功数据的合并分开，用事件来源
标记区分真正的实时变化和另一份 HTTP 快照。较旧成功可以推进终态，却不能随意
覆盖较新同状态阶段或交付诊断。[辅助读取回归](../../web/src/lib/sessionAuxiliary.test.ts)
直接经过真实读取入口覆盖这些交错；[Research 页面链路](../../web/src/lib/sessionResearch.test.tsx)
还验证完成后取消按钮退出，以及真实 WS 更新仍被保留。

这个规则有明确边界。BG／Research 的一个 id 对应一次执行；委派必须按
`delegation_id + work_id` 区分轮次。同一子会话下一轮可以重新运行，不能按子会话
设置永久终态；应用也可以重新构建，不能套用一次执行的状态单调规则。
[委派读取回归](../../web/src/lib/delegationReads.test.ts)保留了新旧 work 并存的反例。

### 2. 防护应落在对应任务和字段上

接纳旧成功还不够。BG 单条详情和列表共用读取后，又出现了更细的错误：B 的较新
请求先结束，使 A 的旧详情只能“推进状态”，连 A 明确返回的诊断清除也被挡住；
即使 B 返回的是 503，也可能影响 A 的数据资格。

另一个窗口是读取期间收到 `bg_completed`。它证明执行结束，却没有提供完整
stdout/stderr，也不证明交付诊断已经更新。把整张对象冻结，会保住终态却丢掉
完整输出；把整张对象替换，又可能抹掉期间真实到达的 `bg_delivery` 错误。

[`fd7ab9c`][c-bg] 与 [`983ff39`][c-fields] 的修改把这些责任分开：

- 执行终态按原 task id 保留，较完整的 stdout/stderr 可以补齐，短列表不裁掉详情正文。
- 可替换的交付字段按涉及该任务的重叠成功读取排序，其他任务不参与裁定。
- 缺字段与显式 `null` 不同，后者可以证明旧诊断应清除；期间真正的交付事件仍受保护。
- 较新失败可以保留读取错误，但没有取得新任务数据，不能据此否决较旧成功的有效内容。

这里需要的临时读取记录由读取入口持有，只活到重叠请求全部结束，不另存一份任务
状态或永久版本账本。[详情／列表交错回归](../../web/src/lib/hydrateSession.test.ts)
覆盖跨任务成功／失败、同任务乱序、正文补全及诊断清除。

同样的拆分用于执行详情。[`9599150`][c-execution] 保留 WS 已确认的新
request／attempt，拒绝旧执行目标改写 Stop；同份响应里可安全合并的历史和任务
结果仍可显示，配对辅助读取也继续完成。原观察至多追加一次执行确认，首份正文
和导航不等它，确认不再派生轮询。过期账户、连接或服务的响应仍整体失效。

这些合并规则先要有正确的权威来源。[`a780cd1`][c-dispatch] 移除兼容用的
`pendingQueue` 副本，不再拿旧文字数组补造当前队列。活动会话缺少可信快照时
显示加载或 unavailable，只有权威快照明确为空，才能当成空队列。
[推送回归](../../web/src/hooks/useWebSocket.test.ts)与
[队列组件回归](../../web/src/components/DispatchQueue.test.tsx)分别检查旧 revision、
缺失快照和显式空队列。减少错误等待，不能靠把未知状态改成“空闲”来完成。

### 3. 首次知道身份，与身份已经被替换，是两种变化

冷启动时服务代次可以是 `null`。请求发出后，另一个会话先建立 G，原详情随后也
返回 G。如果只比较“请求前代次是否等于现在”，就会挡掉同一服务的合法首份历史。
[`1126d10`][c-cold] 允许详情用自身派发身份确认当前代次，同时保留账户、连接和
已知旧服务的保护。[详情回归](../../web/src/lib/hydrateSession.test.ts)同时覆盖
直接加载和选择会话两个生产入口。

创建操作不能照搬这条规则。Research POST 发出时尚未建代，详情先建立 G，再返回
201；原 `current()` 已失效，若静默丢弃，服务器有任务而界面没有卡片。无条件接纳
201 又可能把旧阶段覆盖回来。[`2358819`][c-create] 为这个窗口沿当前 G 读取一次
Research 快照，以原 job ID 确认；只有第一次建代、原账户／连接／目标／页面仍有效
时才可走此路径。缓存中同名 job 不算本次确认，`null→G→H` 也不能借它放行。

正常观察内，创建回执可以初始化缺失记录或补元数据，不覆盖已经观察到的动态状态。
确认失败或原 job 缺失时，保留“已创建、当前状态待确认”的事实，提供读取恢复，
不重发 POST。[创建交错回归](../../web/src/lib/sessionResearch.test.tsx)与
[离线浏览器用例](../../web/e2e/research.spec.ts)保留一次创建和原身份确认的证据入口。

经验是先解释身份变化的含义，再决定是否重新取证。放宽一个合法首读窗口，不等于
放宽服务替换、账户切换、删除或页面退出后的写入资格。

### 4. 等待范围过大，会把局部慢和局部失败变成整页不可用

[`30f1ada`][c-loading] 前，会话详情与 BG 请求放在同一个 `Promise.all` 中，
详情要等 BG 响应才应用；辅助失败还可能把队列状态标成不可用。数据请求并行发出，
并不意味着用户能够先看到已经取得的正文。

调整后，详情决定正文和导航；BG、Research、委派分别完成读取、显示自己的错误。
配对辅助请求可以先发，但发布仍等待详情确认原服务身份。这保留了必要依赖，
不再让辅助接口的耗时决定正文何时可见。
[手机浏览器回归](../../web/e2e/session-loading.spec.ts)扣住 BG 响应，实际检查
正文已显示、导航完成、连续触摸只发一次创建。

“有超时”也需要观察真正结束点。[`4f1418d`][c-wiki] 的 Wiki 读取覆盖 headers
和 JSON body，期限到达时主动结算本地 Promise、释放合并槽，再中止传输；仅发送
abort 不能证明不响应取消的 transport 已结束等待。旧回报和旧 `finally` 只能
清理原请求，不能清掉重连后的新槽或让“加载更多”一直禁用。
[读取恢复回归](../../web/src/lib/wikiJobs.recovery.test.ts)分别扣住 headers/body，
检查期限、同代重连、旧 finally 和替换请求；它没有用“收到 headers”冒充正文完成。

列表有另一种明确取舍：无服务端 revision 时，冲突的完整列表整体丢弃并合并补读，
可以避免旧行复活，但持续变化下不承诺完整新鲜。`refresh()` 可返回 `pending`，
不必一直等到全域安静；失败结束当前自动读取轮次，保留旧数据和错误，由新事件、
进入、重连或手动刷新恢复。不能把这种有边界的保守策略推广到所有任务结果。

### 5. 写入成功、展示确认和导航有不同结束点

同账户重连后收到旧连接的创建成功回执，原行没有资格直接写入新列表，但原操作
已经成功。正确路径是让当前列表失效补读；确认失败就显示未同步，不把写成功改判
为失败，也不提示用户重新创建。[会话创建回归](../../web/src/lib/openAgentChat.test.ts)
保留“重连已读到旧空列表，随后才收到创建成功”的窗口；[列表回归](../../web/src/lib/sessionList.test.ts)
还检查确认等待在读取失败或范围退出时结束，以及多个创建回执不会过早确认。

Wiki 控制同样如此：POST 已接受，就发布原 attempt 的 accepted 回执，后续 GET
单独刷新事实。GET 503 只造成读取错误，不能吞掉成功回执或重发控制；相同服务
重连可以保留控制回执，原页面已退出的回调则不能污染新观察。
现行[Wiki 观察合同](../implemented/frontend-list-reconciliation.md#wiki-卡片详情与控制回执)
和[离线浏览器回归](../../web/e2e/wiki-job-cards.spec.ts)分别维护语义和真实链路反例。

接纳到 store 也不自动授予导航资格。用户在等待期间去了别的会话，原成功可以
成为列表事实，却不能把焦点抢回来；调用者在 `await` 恢复后仍要核对它拥有的
原观察。读取合并归领域模块，焦点和导航归页面，服务端效果归原业务 owner。

### 6. 页面退出、用户意图和可见位置各有自己的寿命

旧 fork A 的回执到达时，用户可能已经排了 B。按 session id 清理 pending、重试
或 finally 会把 B 一起消费掉。[`6ab383a`][c-fork] 捕获原意图对象，只清理自己
拥有的意图和操作登记；A 的成功、busy、拒绝或网络错误不能把重试与导航转给 B。
[真实 ChatView 回归](../../web/src/components/ChatView.fork.test.tsx)覆盖四种回执，
以及离开后再回来也不恢复原导航资格。

组件结束不总意味着数据应删除。问题答案、原提交身份和不可变提交快照由 store
按原问题保管；unknown 按原提交查询，迟到接纳只清当时提交的快照，保留后来编辑。
这是 [`0a56386`][c-drafts] 及[问题生命周期回归](../../web/src/components/QuestionLifecycle.test.tsx)
补齐的责任。相反，Wiki 页面从聊天切到管理页只隐藏 ChatView，并未卸载；如果
只在 unmount 清理，隐藏页会继续观察。页面退出必须按实际视图变化处理。

展示数据正确，也不足以证明交互正确。`filter + append` 更新详情会把现有会话
挪到侧栏末尾；[`0ca897e`][c-order] 改为原位替换，只有新身份才追加。历史分页
也不能只数“增加了几行”：子任务重分组可能移动现有卡片。应保留实际可见行的
稳定身份和像素偏移。[历史分页浏览器回归](../../web/e2e/history-pagination.spec.ts)
覆盖混合页、仅子任务页及期间新增尾部，检查同一行仍可见且偏移变化不超过 2 px。

### 7. 列表缺席、确认删除与账户失效不能共用一个清理判断

重连只拉 live 列表，原会话没有出现，至少有两种解释：被远端归档，或已删除。
若看见缺行就清空消息和草稿，会误伤仍可读取的归档会话；若永远保留，又会在
真正删除后留下旧输入、卡片和迟到回执的恢复资格。

[`4f82006`][c-deletion] 让 `SessionList` 在有效范围内将缺席 ID 合并到包含 archived
的完整确认读取。归档保留原输入和可读视图；确认删除才统一清除选中项、所属缓存，并
通知页面清理文字、附件和恢复草稿。有效删除事件或成功删除回执也走同一入口，
仅仅发出 DELETE、删除失败或 live 缺行不触发清理。检查覆盖所有先前已知的目标，
不只覆盖当前选中会话。待确认 ID 由列表模块临时持有，成功确认或退出账户后
清除，不过滤新行，也不成为永久删除墓碑。

同一提交还修正了连接层的另一种过度失效。旧发送端把“原 session 查不到”和
“token 已失效”合成一个授权失败，关闭整条账户 socket。于是排队中的旧会话帧
遇到删除，可能连同账户其他会话、计划的持续推送一起中断。

当前[发送端](../../server/ws_delivery.py)分别裁定连接身份和单帧可读性：

| 身份与资源事实 | 发送时的处理 |
| --- | --- |
| 账户凭据有效，原会话仍归该账户，包括归档会话 | 允许发送该帧。 |
| 账户凭据有效，原会话缺失、已删除或不归该账户 | 丢弃该帧；外账户归属记录诊断，共用连接继续服务其他合法帧。 |
| 账户或 bearer 已失效，当前 principal 与原连接身份不符 | 以 4001 关闭连接。 |

这张表只描述身份检查；慢客户端等传输故障仍有各自的关闭责任。账户与会话归属
在发送前最后一次已提交读取中一起核对；已交给 transport 的帧没有撤回保证。
丢弃帧也要释放原帧数和字节预算，否则保住 socket 仍可能逐渐耗尽发送容量。

[传输回归](../../tests/test_ws_delivery.py)扣住真实发送队列，在删除、归档、跨账户
和撤销凭据后释放，观察后续合法帧及预算复用；
[列表回归](../../web/src/lib/sessionList.test.ts)区分归档与删除，
[ChatView 回归](../../web/src/components/ChatView.test.tsx)检查草稿及迟到拒绝不复活。
[双页面浏览器回归](../../web/e2e/session-deletion.spec.ts)经真实 REST→双 WS→页面，
检查两页收到删除、输入和答案草稿退出、账户连接仍在线。后端只测到 Session not
found，或前端只从数组移走一行，都没有证明这段交接完整。

## 为什么需要连续修补

根本问题是把不同维度压成一个“新旧”判断：请求顺序被当成服务端版本，对象引用
被当成事件来源，整张卡片被当成一个不可分事实，组件寿命被当成操作寿命。于是
每补一道保护，都可能顺带剥夺另一个消费者取得合法结果的资格。

前几次修改各自解决了真实问题：权威 dispatch 提供执行事实，列表模块协调 GET、
WS 与操作回执，[`1d026c2`][c-reads] 再把读取身份、基线和结束责任收口。但这些
保证还没有回答“缺行是否授权清理草稿”“单个资源失效能否关闭账户连接”。后来
的消费者暴露的是不同责任，不能仅凭提交连续就认定此前修复又被改坏。这是从
代码与差异推得的工程解释，不是对每次开发过程或开发者动机的断言。

另一个原因是验收容易只看最终 store 或 helper：旧值没有写入、Promise 返回了、
行数正确，都不能证明正确结果已经显示、用户不再等待、原输入没有重复提交、
可见位置没有跳动。上述源码保留了反例和修复，但不能由此声称每个旧版本都曾
通过完整测试；测试数量和提交说明也不能代替对交错及观察点的检查。

下面这些构造会绕过目标窗口，增加测试条数也不会自动弥补：

| 不足的构造或观察 | 应制造的最小反例 | 必须观察的事实 |
| --- | --- | --- |
| 表单提交前已设定服务代次 | 先以 null 发 POST，详情建立 G，再返回 201 | 一次 POST、当前 GET 核原 job；确认失败仍保留已创建事实。 |
| 只测 WS 完成后旧 GET 返回，或成功／失败一对请求 | 无 WS 的双成功乱序，一份 running、一份 completed | 合法终态能进入界面，同时不抹掉较新诊断。 |
| 缺行测试只构造一种列表 | 相同 live 空列表，完整确认分别返回 archived 行和真正缺失 | 归档保留输入；删除清理所有原目标缓存，迟到回执不复活。 |
| 只测试入口返回 Session not found | 帧入队后删除原会话，再释放发送，随后发送合法账户帧 | 旧帧被丢弃、预算回收、连接继续可用；凭据撤销则确实关闭。 |
| 页面退出只用 unmount 模拟 | ChatView 隐藏、重回聊天，期间旧 body／finally 到达 | 原观察结束，返回后是新观察，旧清理不能解除新请求占用。 |

其中 Research 的盲区有直接差异证据：[`2358819`][c-create] 前的表单夹具固定
`generation="service"`，新用例才允许从 null 提交。需要改变的是反例和观察边界，
不是单纯延长等待或一律增加真实模型端到端测试。

## 可迁移的开发经验

1. **先写清每个结果证明的事实。** 标出原账户、服务、连接、任务／轮次／请求，
   谁可以写哪些字段，以及页面需要等到哪里。身份有效、字段可合并、可以导航
   分别判断；普通局部改动不需要新建一套状态机。
2. **防回退与保留有效结果同时验收。** 每个新增防旧条件，既给一个必须拒绝的
   反例，也给一个仍应接受的合法交错。合法成功被丢弃后，说明谁会补取、何时
   结束等待；没有恢复责任的静默 return 可能让页面失去前进路径。
3. **缩小裁定范围。** 账户／连接／服务失效保护整个观察；任务间的数据资格、
   同任务执行结果、输出、交付诊断和读取错误按各自事实合并。不要用全局序号
   冻结所有字段；列表缺席、归档、删除与账户失效分别取证，清理和故障范围不
   超出已经确认的事实。按已证明的冲突划分责任，不为每个字段预建版本系统。
4. **等待只覆盖必要依赖。** 正文不等辅助卡片，成功回执不等状态刷新；期限覆盖
   实际 headers/body 等待。观察结束和旧 finally 只释放原请求，新操作不继承旧
   busy；失败保留数据和准确错误，重试读取不自动重放可能已提交的写操作。
5. **集中责任并删掉绕行入口。** 页面表达领域动作，领域模块负责读取、回执与
   合并，store 保留唯一业务数据。临时读取资格、排序意图或请求登记要说明真实
   需要、持有者和回收点；不为相似外观统一成一个跨领域同步引擎。
   同一种错误假设又出现时，沿现有读取／合并原语核对实际消费者及适用条件，
   再改责任模型；不继续给每个页面分别补一个 current 标志或 fallback。
6. **用能推翻旧解释的交错验证完整体验。** 优先控制双成功返回顺序，再补成功／
   失败交错、首次建代／换代、离开后返回、旧 finally、新编辑和 body 悬挂。
   从真实 hook、页面和模块入口断言正文、按钮、原身份、请求次数及可见位置，
   不只检查 merge helper。复用仍有效的验证证据，不因整理复盘重跑产品套件。

这些方法适用于发生相应交接的改动，不要求在每个 await 后重复核对所有身份，
也不要求每次修复新建计划或扩大成全库审计。检查放在真正发布、清理或交接的
边界；必要反例与旧路径退出得到验证后结束该范围。
