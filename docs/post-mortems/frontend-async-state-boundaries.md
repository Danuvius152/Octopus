# 前端防旧逻辑丢掉了有效终态，也扩大了清理范围

状态：下列观察与合并缺口已有修复。调查窗口为
2026-10-06 至 2026-11-06，历史整理基线为
`0a56386315548b6e9df6251166220749fc0ce4aa`。

## 摘要

两个请求都从 running 出发，较晚发出的 R2 先返回 running，R1 随后返回 completed。
旧防护把 R1 当成旧结果丢弃，唯一完成结果因此无法显示。类似判断又把对象替换、
服务首次建代、组件退出和列表缺席，都简化成同一种失效，连有效正文、创建回执
和用户草稿一起挡住或清除。

修复分别判断身份是否有效、哪些字段可合并、页面是否仍可导航，并验证合法结果
能显示、等待能结束。共用读取入口负责合并，页面保有焦点与意图，store 保存业务
数据；不同领域没有合成一个全局新旧序号。

## 影响与证据

旧实现与回归构造支持以下用户后果：任务一直显示 running、完整输出丢失、创建
成功却没有卡片、正文等待辅助接口、迟到回执清空新草稿，以及一个会话删除中断
全账户推送。没有取得线上损失、完整故障时长或性能测量，提交次数不能当事故数。

证据为 Git 差异、合同与测试源码。下列日期是提交节点，测试是可复查入口；本次
文档改写未运行产品套件、模型或部署验收。

## 根因与修复

### 1. 请求顺序被误当成了数据版本

R2 先结束就淘汰 R1，会丢掉 R1 带回的 completed；R1 先写 running 并替换对象，
R2 又可能因引用不同而被误判为覆盖实时更新。反过来，简单接受所有成功也会让
已完成任务回退 running。

修复分开错误提示的读取顺序与成功数据的合并，并区分 HTTP 快照和真正的 WS/
本地权威变化。合法旧成功可推进终态，不能覆盖较新同状态阶段或交付诊断。
[辅助读取](../../web/src/lib/sessionAuxiliary.test.ts)和
[Research 页面读取](../../web/src/lib/sessionResearch.test.tsx)控制双成功乱序，
核完成能显示、取消按钮退出、真正 WS 变化仍保留。

终态规则必须绑定一次执行：BG/Research 按 id，委派按 delegation_id + work_id；
同一子会话可有新轮，应用也可重建，不能永久冻结。[委派读取](../../web/src/lib/delegationReads.test.ts)
保留新旧 work 并存的反例。

### 2. 全局读取资格和整对象保护误伤了独立事实

B 的新请求先结束，甚至返回 503，都曾影响 A 旧详情清除诊断。bg_completed 又只
证明执行结束，没有完整 stdout/stderr 或交付诊断：冻结整对象会丢正文，替换整对象
会抹掉期间到达的 bg_delivery 错误。

修复将执行终态、完整输出与可替换交付字段分别合并。交付排序只比较涉及原任务
的重叠成功读取，别的任务不参与；缺字段不同于显式 null，失败没有取得新数据，
不能否决旧成功。临时读取登记活到重叠请求结束，不另建永久任务账本。
[hydrateSession 回归](../../web/src/lib/hydrateSession.test.ts)覆盖跨任务成功/失败、
同任务乱序、正文补全与诊断清除。

旧执行目标也不使整份响应无效：保留 WS 已确认的新 request/attempt，不让旧目标
改写 Stop，安全历史和辅助结果仍可补齐。原观察至多补一次执行确认，首份正文与
导航不等它，不派生轮询；账户、连接或服务替换则使整个旧观察失效。

这些判断依赖可信来源。pendingQueue 兼容副本退出后，缺 dispatch 快照显示加载
或 unavailable，只有明确空快照才表示空队列。
[WS](../../web/src/hooks/useWebSocket.test.ts)与[队列组件](../../web/src/components/DispatchQueue.test.tsx)
覆盖旧 revision、缺失与显式空值，不能靠把未知当空闲消除等待。

### 3. 首次知道服务身份不等于服务被替换

冷启动请求时 generation=null，另一个会话先建立 G，原详情也返回 G。仅比较请求
前后的代次会挡掉合法首份历史。`1126d10` 允许详情用自身派发身份确认同一代次，
仍保留账户、连接与已知旧服务的防护。

创建有另一结束点：POST 发出后详情建立 G，201 可能被过严丢弃，服务器已建任务
而页面没有卡片。`2358819` 只在首次 null→G、原范围仍有效时，以当前 G GET 核
原 job ID，保留一次 POST。确认失败留下“已创建、状态待确认”，不重建；正常
创建回执只补身份/元数据，不覆盖动态终态。

[Research 测试](../../web/src/lib/sessionResearch.test.tsx)及
[浏览器用例](../../web/e2e/research.spec.ts)覆盖首次建代、确认失败和缺 job。
null→G→H、账户/连接替换、删除或页面退出均不适用这一窗口，详见
[Research 创建复盘](research-completion-boundaries.md#5-创建成功之后浏览器仍可能没有可信的当前状态)。

### 4. 等待范围把局部慢变成了整页阻塞

详情与 BG 放在同一个 Promise.all，辅助慢或失败便拖住正文、导航甚至队列判断。
修复由详情决定正文，BG/Research/委派各自结束读取和显示错误；辅助请求可先发，
发布仍等详情确认原服务身份。[手机加载回归](../../web/e2e/session-loading.spec.ts)
扣住 BG，观察正文与导航先完成，连续触摸只创建一次。

Wiki 期限还必须覆盖 headers 和 JSON body。超时主动结算本地 Promise、释放合并槽
再 abort，避免 transport 忽略取消后继续占用。旧回报和 finally 只清原请求，不能
解除重连后的新槽或让加载更多永久禁用。
[读取恢复](../../web/src/lib/wikiJobs.recovery.test.ts)分别扣住 headers/body，核超时、
同代重连和旧 finally。

无服务端 revision 的完整列表采用另一取舍：冲突时整份丢弃并合并补读，refresh
可返回 pending；读取失败结束本轮，保留旧数据和错误，由新事件、进入、重连或
手动刷新恢复。持续变化下不保证完整新鲜，不能将该策略套到每条任务成功结果。

### 5. 写成功、展示确认和导航被合成了一个动作

同账户重连后旧创建成功，原行不能直接写新列表，原操作却已成功。修复让当前列表
失效补读，失败显示未同步，不改判写失败或诱导再创建。
[会话创建](../../web/src/lib/openAgentChat.test.ts)和[列表回归](../../web/src/lib/sessionList.test.ts)
覆盖重连空列表后迟到成功，以及确认失败、范围退出和多创建回执。

Wiki POST accepted 也先发布原 attempt 回执，后续 GET 503 只记读取错误，不吞成功
或重发控制；同服务重连可保留回执，退出页面后的回调不能污染新观察。
[浏览器卡片](../../web/e2e/wiki-job-cards.spec.ts)固定该链路。

数据可以进入 store，不代表页面仍能导航。await 后核原观察，用户已去其他会话时
不能抢回焦点。合并归领域，焦点归页面，服务端效果归原业务 owner。

### 6. 组件、用户意图和可见位置有不同寿命

旧 fork A 回报时用户可能已排 B，按 session ID 清 pending/finally 会消费掉 B。
修复捕获原意图对象，A 的成功、busy、拒绝和网络错误只结算 A。
[ChatView fork](../../web/src/components/ChatView.fork.test.tsx)还检查离开再回来不
恢复旧导航资格。

问题答案、原提交和快照在 store 按原问题保存，unknown 查原提交，迟到接纳只清
原快照，保留新编辑。[问题生命周期](../../web/src/components/QuestionLifecycle.test.tsx)
覆盖卸载重挂载。Wiki 管理页则只是隐藏 ChatView，观察结束必须跟实际视图走，
不能只等 unmount。

详情用 filter + append 会把现有会话挪到侧栏末尾，修复为原位替换。历史分页也
不能只数新增行，子任务重分组会移动卡片；[分页浏览器回归](../../web/e2e/history-pagination.spec.ts)
核原可见行身份和像素偏移，覆盖混合页、仅子任务页与期间新增尾部，偏移不超过 2 px。

### 7. 列表缺席、确认删除与账户失效共用了清理判断

live 列表缺行可能只是归档。修复将缺席已知 ID 合并进包含 archived 的完整确认；
归档保留输入，可读；确认删除才清选择、缓存、文字、附件与恢复草稿。有效删除
事件/成功回执共用入口，仅发 DELETE、删除失败或 live 缺行均不清理。待确认集合
属临时列表责任，不过滤新行，不是永久删除墓碑。

发送端也曾把 Session not found 当账户授权失败，关闭共用 socket。当前
[ws_delivery](../../server/ws_delivery.py)在发送前一起核账户和单帧归属：有效账户下
合法或归档会话可发送；缺失、删除或外账户会话丢该帧，外账户归属记诊断，连接
继续；账户/bearer 失效或 principal 不匹配才按身份规则以 4001 关闭。慢客户端等
传输故障另判，已交 transport 的帧没有撤回保证，丢帧也回收帧数/字节预算。

[传输回归](../../tests/test_ws_delivery.py)扣住发送队列后删除、归档、换归属或撤权，
检查后续合法帧及预算；[列表](../../web/src/lib/sessionList.test.ts)、
[ChatView](../../web/src/components/ChatView.test.tsx)与
[双页面浏览器](../../web/e2e/session-deletion.spec.ts)检查草稿退出、迟到回执不复活，
以及删除原会话不切断账户连接。

## 为什么测试漏检

旧构造常提前设好服务代次，只覆盖成功/失败乱序或 WS 后的旧 GET，用 unmount
模拟所有页面退出，只检查 helper/store、行数或入口的 Session not found。
这些都避开双成功乱序、首次建代、隐藏视图、实际发送队列和像素位置。

问题在于把请求顺序、对象引用、组件寿命和列表缺席当成所需事实的证明。验收
既要有必须拒绝的反例，也要有仍应接纳的合法交错，观察正文、按钮、请求次数、
原身份与位置；无需为此一律增加真实模型调用或延长等待。

## 教训与当前边界

- 按原账户、服务、连接、任务/work 判资格，再按字段合并，导航单独判断。
- 防回退与合法结果前进成对验收；丢弃成功后必须有明确恢复和等待终点。
- 清理范围不超出已确认事实，原 finally 只释放原请求，读取重试不重放写操作。
- 读取与合并由领域持有，页面保有意图，避免逐页补 current/fallback 或另造同步引擎。

现行细节见[前端任务导航](../implemented/frontend-list-reconciliation.md)和
[WebSocket 交付](../implemented/multi-tenancy.md#websocket-delivery)。
无服务端版本和可靠补发时，前端不能仅凭请求顺序保证全局最新；列表收敛依赖变化
最终停止、缺失变化被观察和后续必要 GET 成功。验证范围与证据复用归[测试政策](../testing.md)。
